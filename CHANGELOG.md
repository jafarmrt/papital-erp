## Version 11.x Series (Active — see `src/data/changelogs/11.ts`)

### Unreleased
- Install, update and health (v11 phase 5.2, findings O8 to O12 and O17 of the server evaluation; card ت۵۴ items 3 to 5): running `install.sh` again on a working install stops before it changes anything and says to run `update.sh`; `update.sh` adds `ERP_SECRETS_KEY` and `METRICS_TOKEN` when `.env` lacks them and rewrites the cron file with its times right before the restart (so an older server gets the jobs and keys of a new install, and a run stopped by a missing tool leaves `.env` as it was), and a git update with nothing new takes no backup and does not restart (unless the service does not answer as started); `/health` no longer shows the database error, the Docker health check reads `/health/ready` on `PORT`, `verify-startup.sh` names the steps a started server left out and `setup-domain.sh` waits for it; `go-live-verify.sh` counts the failed events not yet replayed or dismissed (it always said the queue was empty) and probes the `PORT` of `.env`; the boot runs the migrator once; the Docker header says to take a `pg_dump` before a new image. Vitest `installUpdateHealthPhase5_2.test.ts`, recovery `rec_obs_r1_22_update_noop_and_lock`.
- Backup and monitor scripts (v11 phase 5.1, findings O3, O7, O11, O13 to O16 and O18 of the server evaluation; card ت۵۲-۷ allows them): every cron job runs its script through `bash` and every shell script is executable in git and after a manual sync, so a zip without unix modes no longer stops the backup and the monitor silently; the monitor alerts on a failed or 26-hour-old copy of the media library when `MEDIA_RCLONE_REMOTE` is set, and `scripts/restore-media.sh` brings the originals back from the crypt remote as the service's user; the scripts see each other through two lock files (`scripts/ops-lock.sh`: `.update.lock` and `logs/.ops-busy.lock`) instead of process names, so an editor that names a script no longer skips the nightly check, a daily backup waits for a running update and an update for a running backup; an exported `PGPASSWORD` no longer beats the scripts' password file; a real restore unpacks and checks the file archives before it swaps the database and puts them into the folder it names, says it kept a previous database only when there was one and lists the kept copies with their `dropdb` command; the server writes its logs private (umask 027, folder 0750, files 0640, no colour codes in the journal) and the update, install and domain logs are readable by root only, kept 90 days. Vitest `opsScriptsPhase5_1.test.ts`, recovery `rec_o15_restore_log_says_what_it_did`.
- CI on Ubuntu 26.04 (v11 phase 5.4, TD-1355, O19): every CI job runs on `ubuntu-26.04`, the release a new server gets; `scripts/ci-start-postgres.sh` installs PostgreSQL 16 from the PostgreSQL apt repository there and keeps only its cluster on port 5432, and the database jobs stop when `pg_dump` is not version 16; `@playwright/test` 1.64.1 (Ubuntu 26.04 is known from 1.61); `npm audit fix` raised fast-uri, ip-address and serialize-javascript to their fixed patches (no server step). Vitest `ciParallelJobs.test.ts`.
- Input guards (v11 phase 6.1a, card ت۵۶): a manual voucher is dated neither after today nor before the books' first fiscal year (M9); a paid cheque is due on or after its issue day (a received cheque already due is recorded) and each cheque step follows the previous one, and a payslip is paid on or after its voucher's day (M12); amounts and quantities above 14 whole digits or 4 decimals are refused, as text or as a number (a computed number's float noise is read as its value), an overflowing line value is 422 instead of 500, a treasury amount a number cannot hold is refused, and the Kardex values the rounded quantity (M16, S10, S12); the year-close preview adds in decimals (M15); a work log is not dated after today and a reviewed log whose text changes goes back to «ارسال‌شده», and a review of an older version of a log is refused (C10).

### v11.3.0 — پایان فاز ۴: پایهٔ پایگاه‌داده
- Server timestamps with a time zone (v11 phase 4.2, card ت۵۳): migration `0001_server_timestamps_timestamptz` turns the 141 server timestamp columns (created, updated, locked, expires and the like) into `timestamptz` with `USING col AT TIME ZONE 'UTC'`, so every stored instant stays the same and a wrong clock setting can no longer shift them (a value sent with another offset, such as `+03:30`, is now stored as that instant instead of its wall-clock digits), and then analyses the converted tables again; the business dates `documents.date` (and its `ref_fiscal_year_corrections` twin) and `transactions.date` stay Tehran wall-clock `timestamp`. Drizzle still reads them as the UTC text without an offset (`ServerTimestampClient`), so API answers keep their shape; SQL compares with `now()` instead of `now() AT TIME ZONE 'UTC'` (sessions, drafts, delegations) and casts a time bound to `timestamptz` (delegation overlap, CRM funnel), and the issued-materials sort key turns the stored instant into the display time zone in one step. The schema drift check requires `timestamptz` in Drizzle and the database for every other timestamp column. Vitest `timestamptzText.test.ts`, regression `reg_schema_drift_td_613`.
- Update disk check for the database (v11 phase 4, card ت۵۳ question 5): a migration that changes a column type rewrites its table and PostgreSQL keeps the old copy until it commits, so `update.sh` now also stops when the disk of the database (`/var/lib/postgresql` for a database on the same server, or `UPDATE_DB_DATA_DIR`) has less free space than twice the database, beside what the update itself needs on a shared disk; it checks before the backup and again after the source step, so the first update from an older `update.sh` (which hands over to the new one) checks too; a database on another server is not checked. Vitest `updateDatabaseSpace.test.ts`.
- One migration baseline (v11 phase 4.1, card ت۵۳): `drizzle/0000_v11_baseline.sql` replaces the 136 series-10 migrations (`0000_v3_baseline` .. `0135_event_privacy_settings_notice`, their text at commit 41e9644) and builds the same schema and the same seed rows (schema dump and sorted data rows of both paths identical; a fresh install migrates in about 2 s instead of 4 s). `src/db/v10MigrationHistory.ts` keeps their tags, `when` and hashes; `foldSquashedHistory` counts a database holding all 136 (every install on v11.2) as having the baseline, so nothing runs again there, and refuses one holding only some of them with the instruction to update to the latest 11.2.x first. The upgrade tests that replayed an old migration on old data went with the files; their end-state checks now run on the migrated database. `update.sh`'s rollback fallback compares the newest migration `when`, not the entry count. New migrations number from `0001`. Vitest `migrationPlan.test.ts`, `updateSafetyPhase3_3.test.ts`.
- Demo database removed (v11 phase 4.1): the in-memory demo database (`src/db/mockPool.ts`, `ERP_DEMO_MODE=1`) is gone, so PostgreSQL is the only database; a leftover `ERP_DEMO_MODE=1` without a database is refused with a reason that names the removal (`DEMO_MODE_REMOVED`), `/health/ready` always reports `postgresql`, and the `any` and role-code ratchet baselines drop with the file; the V11 roadmap and `docs/rules/release.md` take the final phase order (cards ت۵۲, ت۵۳: 3 urgent fixes done, 4 database base, 5 server and CI, 6 features and findings, 7 closing). Vitest `databaseModeTd616.test.ts`, regression `reg_database_mode_td_616`.
- Dashboard: the «تازه‌های این نسخه» card no longer shows on the پیشخوان after an update (owner's request); `WhatsNewCard` and its two client hooks are removed. With it users no longer see any release notes in the app (the changelog page itself left in 10.1). The `/social/whats-new` routes, their regression case and the `users.whats_new_seen_version` column are kept unused for now, so the card can come back without a migration.
- Update memory check (after the failed v11.2.0 server update, whose build the kernel killed for lack of memory on a server without swap): `update.sh` adds RAM available and free swap before the backup and again before the build and stops with the swap file steps below 2048 MB (`UPDATE_MIN_MEMORY_MB`), and a build or `npm ci` killed for lack of memory (`oom_kill` of `/proc/vmstat`) is named as such instead of a bare «Build failed» or three network retries; README and the go-live checklist give the swap steps. Vitest `updateMemoryCheck.test.ts`.

### v11.2.0 — پایان فاز ۳: رفع فوری پول، انبار و به‌روزرسانی سرور
- Update safety (phase 3.3, findings O1, O2, O4 and O5 of the independent evaluation): the built server reads its migrations only from its own `dist/drizzle`, never from the source `drizzle/` update.sh pulls before the swap (a restart of the old build in that window used to run the new release's migrations under the old code); after a failed update the rollback steps follow the database (no migration newer than the previous build: code back with no restore; else go forward or restore the backup, never the previous build on the migrated database); `npm ci` regenerates the lock only on npm's own lock mismatch and never one git tracks, retries network failures and never writes a lock into the checkout (a lock an earlier update changed is put back before the pull); every script reads `.env` through one reader, `scripts/env-file.sh`, the way the service does (`node --env-file`: the last line wins, `export`, inline comments), also `backup.sh` and `monitor.sh` (only that one line, with the owner's leave from card ت۵۲). The pull of the first update after this change is still done by the previous update.sh and the previous build's migrator, so these protections start with the update after it. Vitest `updateSafetyPhase3_3.test.ts`.
- Stock fixes (phase 3.2, findings S1 and S3 of the independent evaluation): an Excel row no longer changes the type of an item with stock or a Kardex row (the stock sat in the inventory account of the old type, so the raw material and product accounts drifted apart); an item with an open BOM allocation or a finalized project's reservation is not deleted (409 `ITEM_HAS_OPEN_ALLOCATION` / `ITEM_HAS_PROJECT_RESERVATION`), the release of an allocation whose item was deleted is refused (409 `ALLOCATION_ITEM_DELETED`, it can still be consumed) and the stock engine records no movement on a deleted item (409 `ITEM_DELETED`) except a stock count decrease; the financial health check lists deleted items that still hold stock or an open allocation (`item_deleted_with_stock`), and such stock is written off by a stock count to zero. Regression `reg_item_excel_type_change_with_history_s1`, `reg_item_delete_open_allocation_s3`, `reg_bom_release_deleted_item_s3`.
- Urgent money fixes (phase 3.1, evaluation findings M1, M2, M4, M5/S6/M23): a voucher correction issues its replacement as a manual draft that another approver approves (before, a user who may only draft vouchers posted any amount straight into the books); the opening voucher of a treasury account and its opening-balance adjustments are sourced vouchers, changed only from the account form, where a draft opening voucher now moves with the start date; a misplaced group separator («12,5», «1٬00٬0», «0,500») is refused by every server number field (prices, work log quantities and piecework rates included) instead of being read as 125; the fiscal-year lock holds on treasury rows, transfers and cheques without a voucher, cheque steps, warehouse transfers and draft documents, a proforma turned into a draft included (a proforma itself is exempt). Regression `moneyUrgentFixesV11Tests.ts`, vitest `moneyUrgentFixesV11.test.ts`.
