# خط پایه کارایی و روشن کردن `pg_stat_statements`

> کار I-04 نقشه راه نسخه ۱۰ (موکول به نسخه ۱۰.۱). این راهنما دو بخش دارد. بخش اول، اندازه‌گیری خودکار روی داده آزمایشی است که در محیط آزمون اجرا می‌شود و به سرور اصلی دست نمی‌زند. بخش دوم، کار یک‌باره و دستی روی سرور اصلی است.

## ۱. اندازه‌گیری روی داده واقعی‌نما (محیط آزمون)

```bash
source scripts/ci-test-env.sh
npm run perf:baseline -- [--steps=3000] [--users=8] [--activity-logs=300000] [--items=2000] [--customers=1000] [--samples=20] [--report=dist/perf-baseline.md] [--enforce]
```

- ابزار در یک اسکیمای جدا کار می‌کند و آن را در پایان پاک می‌کند. ابتدا شبیه‌ساز «یک سال کاری» را اجرا می‌کند تا هزاران سند، سند حسابداری و ردیف کاردکس ساخته شود. سپس کالا، شخص و ردیف‌های گزارش رویدادها را یک‌جا می‌افزاید.
- پس از آن، API اصلی هر صفحه را با یک نشست مدیر و از راه همان برنامه واقعی صدا می‌زند: دو بار برای گرم شدن، سپس `--samples` بار با زمان‌گیری.
- خروجی یک گزارش Markdown و یک فایل JSON کنار آن است. گزارش حجم داده، میانه، p95 و بیشینه زمان پاسخ و هدف هر API را نشان می‌دهد. اگر `pg_stat_statements` بارگذاری شده باشد، پرهزینه‌ترین پرس‌وجوها را هم فهرست می‌کند.
- اگر یک API خطا بدهد، هرچقدر هم سریع باشد «در هدف» شمرده نمی‌شود.
- `--enforce` باعث می‌شود اگر یک API از هدف بگذرد، ابزار با کد ۱ پایان یابد.
- فهرست APIها و هدف‌ها در `scripts/perf/perfBaseline.ts` است و آزمون Vitest `perfBaseline.test.ts` از آن نگهداری می‌کند.

### هدف‌ها (صدک ۹۵ زمان پاسخ)

| نوع | هدف | نمونه |
|---|---:|---|
| نوار بالا (روی هر صفحه) | ۳۰۰ میلی‌ثانیه | تعداد اعلان‌های خوانده‌نشده، شمار کارهای کارتابل |
| فهرست یک‌صفحه‌ای | ۸۰۰ میلی‌ثانیه | اسناد، کالاها، اشخاص، اسناد حسابداری، گزارش رویدادها |
| گزارش روی کل سال | ۲٬۰۰۰ میلی‌ثانیه | پیشخوان، تراز آزمایشی، دفتر روزنامه، اقلام رزروشده |

این هدف‌ها برای همان شکل استقرار است: یک سرور و حداکثر ۲۰ کاربر هم‌زمان (AGENTS.md §22).

### نخستین اندازه‌گیری (۲۰ مهر ۱۴۰۵، نسخه ۱۰.۰.۲۶۱)

- داده: ۳٬۰۰۰ گام شبیه‌ساز با ۸ کاربر هم‌زمان، ۱٬۸۵۴ سند با ۲٬۸۵۱ ردیف، ۳٬۲۶۳ ردیف کاردکس، ۲٬۱۲۹ سند حسابداری با ۶٬۵۳۴ ردیف، ۲٬۰۱۰ کالا، ۱٬۰۰۲ شخص و ۳۰۰٬۵۳۲ ردیف گزارش رویدادها.
- همه ۲۵ API در هدف بودند و p95 همه‌شان زیر ۳۰ میلی‌ثانیه بود. تنها استثنا «پالایه‌های گزارش رویدادها» (`/api/activity-logs/filters`) بود با p95 برابر ۱۰۷ میلی‌ثانیه، که با بزرگ شدن جدول رویدادها رشد می‌کند و ارزش پیگیری دارد.
- این عددها روی محیط آزمون و بدون شبکه به دست آمده‌اند. روی سرور اصلی، زمان شبکه و مرورگر هم به آن‌ها افزوده می‌شود.

### پیگیری (۲۳ مهر ۱۴۰۵، نسخه ۱۰.۱.۱۲)

- «پالایه‌های گزارش رویدادها» دیگر کل جدول رویدادها را نمی‌خواند. هر فهرست (کاربر، عملیات، بخش) با پرش روی نمایه همان ستون خوانده می‌شود و برای هر مقدار متمایز یک بار به نمایه سر می‌زند (TD-1267).
- اندازه‌گیری دوباره با همان حجم داده (۳٬۰۰۰ گام، ۸ کاربر هم‌زمان، ۳۰۱٬۰۵۴ ردیف گزارش رویدادها): p95 این API از ۱۰۷ به حدود ۴ میلی‌ثانیه رسید. همه ۲۵ API در هدف ماندند و کندترینشان «اسناد حسابداری» با p95 حدود ۴۲ میلی‌ثانیه بود.

## ۲. روشن کردن `pg_stat_statements` روی سرور اصلی (کار دستی، یک بار)

این افزونه زمان اجرای هر پرس‌وجو را روی همان سرور اصلی و با داده واقعی جمع می‌کند، تا معلوم شود کدام بخش برنامه کند است. برای روشن کردنش باید پیکربندی PostgreSQL را تغییر داد و آن را یک بار دوباره راه‌اندازی کرد. هیچ ابزاری این کار را خودکار انجام نمی‌دهد.

**پیش از شروع:** وقتی را انتخاب کنید که کسی با برنامه کار نمی‌کند. برنامه حدود یک دقیقه در دسترس نخواهد بود.

**گام ۱: افزودن افزونه به پیکربندی** (روی سرور، در پوشه `/opt/papital-erp`):

```bash
sudo -u postgres psql -c "SHOW shared_preload_libraries;"
```

اگر خروجی خالی بود:

```bash
sudo -u postgres psql -c "ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';"
```

اگر خروجی مقداری داشت، مثلاً `abc`، آن مقدار را نگه دارید و افزونه را به آن اضافه کنید: `'abc,pg_stat_statements'`.

**گام ۲: راه‌اندازی دوباره PostgreSQL و برنامه:**

```bash
sudo systemctl restart postgresql
sudo systemctl restart papital-erp
```

**گام ۳: ساختن افزونه در پایگاه‌داده برنامه:**

```bash
sudo -u postgres psql -d papital_erp -c "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"
```

**گام ۴: بررسی:**

```bash
sudo -u postgres psql -d papital_erp -c "SELECT count(*) FROM pg_stat_statements;"
curl -s http://localhost:3000/health/ready
```

دستور اول باید عددی بزرگ‌تر از صفر نشان دهد. دستور دوم باید پاسخ «آماده» بدهد. اگر برنامه آماده نشد، `sudo journalctl -u papital-erp -n 50` علت را نشان می‌دهد.

**پس از یک هفته کار عادی**، این دستور پرهزینه‌ترین پرس‌وجوها را نشان می‌دهد. فقط می‌خواند و چیزی را تغییر نمی‌دهد:

```bash
sudo -u postgres psql -d papital_erp -f scripts/sql/top-statements.sql
```

**برگرداندن کار:** دستور `ALTER SYSTEM RESET shared_preload_libraries;` را اجرا کنید و گام ۲ را تکرار کنید.

خود افزونه داده برنامه را تغییر نمی‌دهد. فقط آمار پرس‌وجوها را نگه می‌دارد و سربار آن ناچیز است.
