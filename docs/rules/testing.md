# Tests

Test layers, the critical path, business invariants and how tests are run.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md` at commit `c3c9858` (archives removed in v11.1.0), and a «§N» below refers to that file's numbering.

- **Vitest for New Unit & Frontend Tests:** New pure-unit and React component tests are Vitest files in `src/tests/vitest/*.test.ts(x)` (jsdom + Testing Library), run with `npm run test:vitest` (CI lint job). Vitest runs in the `vmForks` pool (one jsdom per worker, each file in its own context) with 30 s test and hook timeouts, and `findBy*` / `waitFor` wait 5 s by default (`src/tests/vitest/setup/testingLibrary.ts`); a test file never passes a timeout below 10 s, and a ratchet test scans the repository once per file (Vitest `vitestCiStabilityTd1261.test.ts`). Database and domain suites stay on the existing runner. The test bootstrap waits for the seed lock (`runSeedWithLock({ waitForLock: true })`), because the lock is one key for every schema of the database, and a catalog read in code or tests names its schema (`current_schema()`, a `regclass` / `regnamespace` cast or a schema column; Vitest `catalogSchemaScope.test.ts`).

- **Playwright Critical Path:** `e2e/critical-path.spec.ts` drives login → final sales invoice → its journal voucher against the production bundle (`dist/server.cjs`) on an empty database (`E2E_DATABASE_URL`, `npm run test:e2e`, CI job `e2e`; the web server is awaited on `/health/startup`, not `/health/ready`, because migrations and seed run in the background). UI changes on these pages must keep it green. The four business flows have their own specs in `e2e/flows/`: purchase (stock page receipt and procurement delivery), project production and delivery (material allocation and «ورود به انبار»), payslip and payment, and treasury and cheque (invoice settlement and a received cheque to cleared). The browser runs the step under test, the API (`e2e/support/flowKit.ts`) prepares its data with names unique per run, and the spec reads `E2E_DATABASE_URL` only to check stock, Kardex and the voucher rows; a change to these screens, their routes or their vouchers keeps them green. Every CI job has its own `timeout-minutes` (never GitHub's 360-minute default), the e2e job caches the Playwright browser by the lock file and prints the page snapshot of a failed test in its log, and every tracked shell script passes `shellcheck --severity=error` in the lint job, and `npm run test:coverage` fails below 90 % lines and statements, 88 % functions and 73 % branches (`c8 --check-coverage`; the floors only go up) (Vitest `ciGatesI06.test.ts`). The CI check jobs (lint, database tests, coverage, e2e, build, Docker build) start at once and none has `needs` on another, so a PR result waits for the longest job, not the sum; only the image push (`docker-publish`) waits for every check job; CI has no staging deploy (the empty staging jobs were removed in v10.1.65), and the database jobs start the runner's own PostgreSQL 16 with `scripts/ci-start-postgres.sh` instead of a service image; every job runs on `ubuntu-26.04`, where that script installs version 16 from the PostgreSQL apt repository and the database jobs stop when `pg_dump` is not version 16 (v11, TD-1355) (Vitest `ciParallelJobs.test.ts`).

- **CI Images From the Mirror:** CI service images and the Dockerfile base images come from the Google mirror of the Docker official images (`mirror.gcr.io/library/<image>:<tag>`; Amazon ECR Public until v11.0.2, when its anonymous data limit failed the Docker build), never anonymously from Docker Hub, whose pull limit stops jobs before any test runs (Vitest `ciImageMirror.test.ts`).

- **Business Invariants & Known-Findings Baseline:** `src/tests/invariants/businessInvariants.ts` holds the executable business invariants (read-only SQL) and `src/tests/simulation/` the seeded one-business-year simulator (`npm run simulate:year`, one isolated schema per seed). The `business_invariants` suite (last in the runner) requires zero violations on clean flows and exactly the finding classes listed in `src/tests/simulation/knownFindings.ts`, each tied to an open `TD-###`. The baseline only shrinks: a release that fixes a finding removes its class there and closes its TD row in the same change; a new class is a regression and is never added without a new TD row. Since v10.0.10 the catalogue also holds I7 (project reservation releases), I8 (party receivable), I9 (cheque transition chain and vouchers), I11 (closed fiscal year), I12 (unique numbers in their own year), I17 (rial balance with a rate on every foreign row), I18 (rows only on posting accounts), I19 (reservations within stock, `checkGuardedReservations`, outside `checkBusinessInvariants` because a stock count or a void may lower stock below a reservation) and I20 (VAT payable = invoice VAT − return VAT); each is scoped by the watermarks of `InvariantScope` and has a check (`invariantCatalogScenarios.ts`) that breaks a row by hand and expects its key. Since v10.0.11 the simulator also runs treasury receipts, payments and voids, received cheques and their transitions, payslips with payments and payment voids, a requisition through order and delivery, material allocation and release and a sales proforma approved through the document workflow (project-side operations move on business today, on items of their own), checks I19 after each step that passes the sellable gate, and `npm run simulate:year -- --close-year` approves the year's drafts and closes 1404 in its own schema (I11). Since v10.0.36 `--users=N` runs the steps in rounds of N concurrent operations, a deadlock or a non-business error is a finding (`I0_deadlock` / `I0_unexpected_error`), and the `inv_i03_*` concurrency checks race delivery with «دریافت کالا», allocation with a remittance and two settlements of one invoice.

- **Test Runs:**
  - **While working:** verify with `npm run lint` and run ONLY the tests relevant to the change (`npx tsx scripts/run-tests.ts --suite <name> --filter <id-or-keyword>`), plus the same test on the previous code to prove it fails there. A run whose suite is unknown or whose filter matches no test fails (exit 1), and the environment check runs before any schema is written.
  - **Before every push:** run the fast checks (lint and typecheck, every ratchet, `check:version`, the tests that touch the change) and `npm run build`; CI runs the full suite (`npm test` with the environment of the `test` job in `.github/workflows/ci.yml` against PostgreSQL 16) and a pull request merges only when every required check is green. A new fix still has its failing test first. Locally: `source scripts/ci-test-env.sh && npm test` (the CI test job's values). In Claude Code on the web the session-start hook (`.claude/hooks/session-start.sh`, registered in `.claude/settings.json`) runs `npm ci` when `node_modules` is missing or older than the lock file, starts PostgreSQL 16, sets the `postgres` password to the CI value and creates `erp_test` / `erp_e2e`.
  - **Otherwise:** a full run happens only when the user explicitly asks for it.
  - **No Polling Loops:** never poll long background jobs repeatedly; wait for the completion notification.
