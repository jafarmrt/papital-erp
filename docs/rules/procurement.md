# Procurement

Requisitions, purchase orders, delivery and the raw material request queue.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md`, and a «§N» below refers to that file's numbering.

- **Raw Material Request Queue:** The review window of «مواد اولیه در انتظار تأیید» sends one form for «ذخیره فقط تغییرات» and «تأیید و افزودن به انبار» (`PendingMaterialForm` in `src/lib/pendingMaterials/pendingMaterialForm.ts`), whose keys are those of the route schemas (`src/routes/pendingMaterials.schemas.ts`); the approve and edit bodies are `strict`, so any other key is 400 instead of being dropped. Sending a request needs `pending_materials.create` (requires `pending_materials.view`; migration 0087 gave both to every role holding `products.create`); its numbers go through non-negative `decimalInput`, an inline image becomes a file through `uploadBase64ToStorage` and a request without a code stays without one (no `TEMP-` code). Approving, rejecting, editing and deleting a request each run in one transaction under its row lock `FOR UPDATE` and only from `pending` (409 `PENDING_MATERIAL_NOT_PENDING`); the approval needs a code (422 `PENDING_MATERIAL_CODE_REQUIRED`) in the raw-material pattern with its category's prefix (422 `PENDING_MATERIAL_CODE_FORMAT`) and a raw-material category (422 `PENDING_MATERIAL_CATEGORY_INVALID`; `assertApprovableMaterial`, rule `pendingMaterialCodeError` in `src/lib/pendingMaterials/materialRequestRules.ts`, which also holds the one unit list `MATERIAL_UNITS` of the request form and the approval window), creates the item through `ItemCatalogService.createItem` (TD-653 code and name rules, code counter) and keeps its id on the request (`pending_materials.item_id`), and every write has its audit row with `tx` (`PendingMaterialsService` in `src/services/pendingMaterials.service.ts`). The page shows approve and reject by `pending_materials.approve` and delete by `pending_materials.delete`, on pending requests only. Project control's «درخواست ماده اولیه جدید» (`AddMaterialModal`, shown by `pending_materials.create`) sends a request to this queue (`pendingMaterialRequestOf` in `src/lib/pendingMaterials/customMaterialRequest.ts`), never an item and never opening stock; the request's project must be live (422 `PENDING_MATERIAL_PROJECT_INVALID`) and its title is read from the project. A request starts the active `pending_material` workflow in its create transaction (`maybeStartWorkflow({ tx })`); the domain action `registerPendingMaterialWorkflowAction` (`src/services/inventory/pendingMaterialWorkflowAction.ts`) approves the request on a step `approved` or the action `APPROVE_PENDING_MATERIAL` and rejects it on a step `rejected`, inside the transition's `tx` and with `pending_materials.approve` from the signer, and a direct approve, reject or delete closes the open instance in the same transaction (`terminateOpenWorkflows`).

- **Procurement Delivery Is Stock-In Only:** `ProcurementService.deliverOrderToWarehouse` and the linked-document finalize of a requisition accept only incoming documents (`receipt`, `purchase`); a purchase proforma is a `receipt` with status `proforma` (never type `proforma`, which finalizes into a sales invoice); `finalizeDocument` treats `purchase` as stock-in like `createDocument`. Delivering an order finalizes it and updates its requisition in one transaction: the requisition row is locked first and the document status re-read under that lock (a repeated delivery adds nothing); each item's received quantity is the sum of all active document lines, filled across the requisition rows of that item in order (`applyDeliveredLines` in `src/services/procurement/requisitionReceipt.ts`). Delivery and «دریافت کالا» finalize an order on the delivery day (`atFinalizeDay`, `finalizeDayTarget` in `src/services/documents/proformaInvoice.ts`): the document, its Kardex rows and voucher take that date, its number stays unless the fiscal year changes, and the order date stays in its notes. `POST /procurement/requisitions/:id/convert-to-orders` validates exactly the body the split-order form (`SplitOrderModal`) sends: the requisition row id is optional, and each package keeps its target warehouse, type and status (draft or proforma only; stock enters only through delivery); an order group has no currency and its lines no discount: the group and its lines are `strict`, so either key is 400, never dropped into an IRR order without discount. Ordering more than a requisition's remaining quantity is allowed only with a reason: `convertToPurchaseOrders` refuses it without `overOrderReason` (422, `OVER_ORDER_REASON_REQUIRED`, the message lists the items and excess; `findOverOrders` in `src/services/procurement/requisitionOrder.ts`), the split-order form warns and requires the reason (`OverOrderWarning`), and the reason is recorded on the requisition row (`overOrders`), in the requisition and order notes and in the activity log; the conversion runs in one transaction under the requisition row lock. Voiding a linked order locks its requisition before the items and rebuilds the ordered and received quantities of that order's items from the live documents (`rebuildOrderRows` in `src/services/procurement/requisitionReceipt.ts`, wired through `registerLinkedOrderHooks` in the composition root, since the documents package does not import procurement); a received requisition left with an open row takes new orders without a new approval. Editing a linked order's lines (`PUT /documents/:id`) follows the same over-order rule: an edit that raises an item's excess needs `overOrderReason` (else 422 `OVER_ORDER_REASON_REQUIRED`), recorded on the row, in the requisition and order notes and in the activity log, and the requisition's ordered quantities follow the new lines (same decision). A requisition workflow action (`executeWorkflowAction`) runs in one transaction under the requisition row lock too; «دریافت کالا» (`receive_items`, `receiveRequisitionItems` in `src/services/procurement/requisitionReceiveAction.ts`) finalizes the requisition's open orders and refuses a catalog row that was never ordered (409 `REQUISITION_ROWS_NOT_ORDERED`, «ابتدا سفارش خرید با تأمین‌کننده و قیمت صادر کنید»; before, such rows entered stock with one final receipt from «تامین‌کننده تدارکات» at the estimate), a finalize error refuses the whole action, and the received quantity is rebuilt from the requisition's final documents; a requisition then left with a row neither received nor closed (`isSettledRequisitionRow`) is refused with 409 `REQUISITION_ROWS_NOT_SETTLED` naming the rows and the whole transition into `received` rolls back, from every path; a received or rejected requisition is never received or converted to orders again (409). The project page's purchase window records no document itself: it records the project's purchase requisition, and its direct mode, shown only to holders of `procurement.create` / `projects.edit`, `procurement.order` and `procurement.approve` / `procurement.manage`, converts that requisition at once into one draft order with the server number, a supplier picked by id and a listed warehouse (`src/lib/projects/projectPurchaseOrder.ts`). A new requisition starts its workflow in its create transaction and a start error refuses it. A requisition is converted to orders and delivered only from its approved workflow step: a holder of `procurement.approve` (only that key since v10.0.48) first runs the approve transition in their own name (`ensureRequisitionApproved` in `src/services/procurement/requisitionApproval.ts`), anyone else gets 409 `REQUISITION_NOT_APPROVED`; its step moves only through `executeTransition`, and no production file outside `src/services/workflow/` writes the workflow tables (Vitest `workflowTableWrites.test.ts`). The default purchase requisition workflow guards every action (`PURCHASE_REQUISITION_STEP_GUARDS` in `src/services/workflow/purchaseWorkflowGuards.ts`): approve, reject and cancel `procurement.approve`, with «آغازکننده تأیید نکند» on approve, so the requisition's creator never approves it (403 `WF_INITIATOR_EXCLUDED`; the system admin is exempt), receive `warehouse.in` and reopen `procurement.create`; an install still holding the old unguarded seed is upgraded at boot (`upgradeLegacySeedGuards`), and an edited definition with an action without role or permission is only listed by the financial health check (`workflow_unguarded_purchase_action`, `src/services/accounting/unguardedPurchaseActionHealth.ts`); the procurement page shows approve, reject and cancel by `procurement.approve` only and reopen by its route keys plus `procurement.create` (`canReopen` of `useProcurementAccess`). A requisition is received only when every row is received or closed (`isSettledRequisitionRow`), and delivery and its receive transition run in one transaction with the user's role and permissions. Goods enter stock only with the permission that records the receipt final (`warehouse.in`, `PROCUREMENT_RECEIVE_PERMISSION` in `src/lib/permissions/procurementPermissions.ts`), on every path: the requisition's domain action asks it as `requiredPermissions` of a transition into the `received` step (`receivePermissionsOfStep`; transition route, inbox task, «دریافت کالا» and delivery's receive transition, from the signer or the delegator's role, 403 `WF_ENTITY_PERMISSION_REQUIRED`), and order delivery asks it on top of its route keys with `can()` before its transaction (`assertMayReceiveIntoStock`, 403 `PROCUREMENT_RECEIVE_PERMISSION_REQUIRED`); the procurement page shows the delivery and receive buttons only with it (`useProcurementAccess`). A requisition with a live order is neither deleted nor edited; deleting one terminates its workflow, and editing is allowed only before approval, keeping the stored row ids, quantities and links. A procurement order is a live document whose `documents.procurement_requisition_id` is set (written by convert-to-orders; legacy orders were linked only from an unambiguous `[تدارکات: درخواست …]` tag, the rest is listed by the financial health check as `procurement_order_link_unresolved`): the order list, the desk summary and delivery read only such documents (another document is 422 `PROCUREMENT_ORDER_NOT_LINKED`), and the list filters, counts and pages in SQL (`listProcurementOrders` in `src/services/procurement/procurementOrderList.ts`). Consolidation takes only unapproved requisitions without orders (`canConsolidateRequisition` in `src/lib/procurement/requisitionFields.ts`), locks them in id order and refuses a missing one; in one transaction it creates the consolidated requisition and marks each source `consolidated` with `purchase_requisitions.consolidated_into_id` and a workflow terminated through `terminateOpenWorkflows`, and a consolidated requisition takes no action (409 `REQUISITION_CONSOLIDATED`); open sources of older consolidations are only listed by the financial health check (`procurement_consolidation_open_sources`).
