# Production Projects

Project reservations, material allocation, delivery to stock, the progress matrix and project screens.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md` at commit `c3c9858` (archives removed in v11.1.0), and a «§N» below refers to that file's numbering.

- **Project Reservation Deduction:** A final `out` document with `projectId` deducts the project's reservation inside its own create/finalize transaction (`releaseReservationsForDocument` → `ItemStockReservationService.releaseProjectReservations`, project row lock + OCC); a failed deduction rejects the document, drafts deduct nothing. Each line is deducted across all matching reservation rows, from the quantity field the reservation report reads (`reservationQtyField`). The browser never writes `inventory_control` for this. Voiding/deleting such a document restores the same quantities to the same project in the void transaction: each deduction is recorded in `project_reservation_releases` and `deleteDocument` locks the project before the document and calls `restoreReservationsForDocument`; deductions before v7.0.105 have no record and restore nothing. A material allocation (both paths) deducts the project's reservation the same way in its own transaction and records each deduction with its allocation id (`releaseReservationsForAllocation`; `project_reservation_releases.bom_allocation_id`, migration 0095, one source per row by `chk_project_reservation_releases_source`); releasing the allocation locks the project before the allocation row and restores exactly those quantities (`restoreReservationsForAllocation`); allocations before v9.0.452 restore nothing. Only a remittance or waste of the project consumes its reservation and passes the sellable gate with the project's own reservation free (`consumesProjectReservation` in `src/lib/transactions/projectIssueTypes.ts`); a sales invoice with a `projectId` neither deducts it nor sells it. Finalizing a project again reserves its need minus what its live final remittances and waste and its open or consumed allocations already issued (`projectIssuedQuantities` in `src/services/projects/projectIssuedQuantities.ts`), and the procurement order of a project requisition carries `documents.project_id`; all three are product-owner decision ت۱۰ of phase 5. The reservation itself (`inventory_control.reservedItems`) is written only by the server: project create/update ignore `reservedItems` / `isReserved` / `finalizedAt` from the body, and read the rest of `inventory_control` through `projectInventoryControlInput` (`src/routes/projectInventoryControl.schemas.ts`: sections, rows and purchase lists are objects and arrays; the quantities the finalize reads (a row's `requiredQty` and `qtyPerUnit`, a manual row's `totalRequiredQty`) are non-negative numbers read with the number field's rule `readDecimalInputText` (Persian digits stored as the number, «٬» only between groups of three digits, so «۱٬۲», «12,5» and «1 2» are 400, and so are ZWNJ, LRM and RLM between digits since v10.2.32), an empty text or null kept except an empty `qtyPerUnit` (400), and a 400 names the section and the row; `isFinalized` a boolean, other fields (stock, rate, browser-computed figures) passed through; v10.2.30, TD-1326, OBS-R1-92); finalizing (`isFinalized` false → true) builds the reservation from the inventory control sections and item stock (`buildProjectReservation` in `src/lib/projects/projectReservation.ts`, via `resolveServerInventoryControl`); a section in the preset shape (materials in `items`) is turned into project rows before it is saved or reserved, in the project inventory tab and on the server: per product for a code-by-code check, one global row otherwise, each material required 1 with its stock status (`projectSectionsFromPreset` in `src/lib/projects/inventoryControlSections.ts`; a code-by-code row one per unit since v10.2.26). A code-by-code row holds its quantity per unit of the product (`qtyPerUnit`, a number ≥ 0) and its need is that quantity × the product's order quantity (`perItemRowRequiredQty` / `productOrderQuantity` in `src/lib/projects/materialQuantity.ts`: a positive quantity, else 1; four decimals), read again from today's order quantity by the finalize, «تکمیل رزرو», the purchase list and the materials tab, so a changed order quantity changes the need and a stored reservation follows only through «تکمیل رزرو»; a row without `qtyPerUnit` (earlier projects, the `itemsSchema` stand-in) keeps its stored `requiredQty` total and the tab shows it «کل» with «برای هر عدد» to turn it into total ÷ order quantity, a new code-by-code row and a preset row of a project without sections start at one per unit while a section still stored or sent in the preset shape keeps one in all (`projectSectionsFromPreset` `perUnit`), a whole-order section keeps totals, and a product's rows are keyed one way everywhere (`perItemProductKey`: the product row's id, else `prod_<item id>`, else its position), saving a finalized project keeps its current (possibly deducted) reservation, and unfinalizing clears it; the project row is locked during the update. A material row of the inventory control sections, the purchase list or the reservation finds its warehouse item only through `findProjectItemMatch` (`src/lib/projects/projectItemMatch.ts`, shared by the server and the project screens): the warehouse item id, then the code key `upper(btrim)`, then the exact name key `lower(btrim)`; never a substring, never an empty code or name. A project's progress matrix (item × stage) has one rule, `computeProgressMatrix` / `matrixProducts` in `src/lib/projects/progressMatrix.ts` (the project's `products`, else its main item; optional stages from `selected_optional_stages`), loaded by `loadProjectProgressMatrix`: the matrix view, the ticks, the completion check (422 `PROJECT_MATRIX_INCOMPLETE`, inside the project save or delivery transaction) and the status sync all read it. A cell also carries the done work of its workshop schedule rows (`work`: each row's live linked work log of the project up to the row's quantity, rows of one unit added and several units averaged by share; `workProgressOf` in `src/lib/workshop/scheduleWorkProgress.ts`, which the workshop panel reads too; a single-item project's `prod-main` rows reach its main item), and a product's and a stage's percent are the average share of their cells, a ticked cell whole, any work at least 1, 100 only when every cell is ticked (`cellsPercent`); completion still reads the ticks only, and a cell of several units carries no quantities. Writing, editing the quantity of, deleting or moving a schedule-linked work log syncs the stage percents in the log's transaction (`syncScheduleProgress`, registered by the composition root), but never decides a project's course: a completed, cancelled or paused project is left alone, a completed stage keeps its percent, status and time, a blocked stage stays blocked (a later tick of another cell keeps it blocked too; only a tick of its own cells unblocks it), and only a waiting stage or a planned project starts, so a stage started by work stays started at 0% when that log is deleted, until the next tick save (`workSyncHoldsProject` / `workSyncStageStatus` / `workSyncProjectStatus` in `src/lib/projects/projectStatus.ts`); the workshop panel reads below 100 until the stage is complete, and the desktop matrix takes no tick while a save runs. Reading a project never writes it: the stage and project status sync (`syncProjectFromMatrix` in `src/services/projects/projectStatusSync.ts`) runs only inside the matrix tick, stage add / edit / delete and project edit transactions, after the project row lock (`lockLiveProject`); it never changes a `paused` or `cancelled` project (`matrixProjectStatus` in `src/lib/projects/projectStatus.ts`) and writes a «پروژه تولید» audit row with the status before and after. In a project with a progress matrix (`hasMatrixProducts`) a stage's status and percent come only from the matrix: a different manual value is 422 `STAGE_STATUS_FROM_MATRIX`, and the stage form asks for them only in a project without products (`StageStatusField`). A new stage takes one more than every number the project has used, its deleted stages and progress rows included (`nextStageOrder`, under the project row lock); deleting a stage soft-deletes its progress rows and a tick needs a live stage; migration 0084 adds the partial unique index `uq_project_stages_order_active` (project, number) and the foreign key `fk_project_stages_project`, each only on clean data, and the financial health check lists what is left (`project_stage_integrity`). A stage edit reads its number (a whole number 1 to `MAX_STAGE_ORDER`) and percent (a whole number 0 to 100) with `decimalInput`; a number another live stage holds, or one a deleted stage left progress rows on, is 409 `STAGE_ORDER_TAKEN`, and a renumbered stage moves its live progress rows (`moveStageOrder`). A project status, a project priority and a stage status (initial stages included) come only from `PROJECT_STATUSES`, `PROJECT_PRIORITIES` and `STAGE_STATUSES` (`src/lib/projects/projectStatus.ts`, shared with the forms; anything else is 400), and legacy free-text values are only listed by the financial health check (`project_status_values`). The delivery quantity and unit price and the project quantity go through `decimalInput`; a delivery line without an item, with a quantity not above zero or a negative price refuses the whole delivery with 422 `PROJECT_DELIVERY_LINE_INVALID` naming the row (`deliveryLine` in `src/services/projects.service.ts`), never a silent skip, and a project quantity not above zero is 422 `PROJECT_QUANTITY_INVALID`. A stage completion time and a matrix tick time are the server UTC time (`systemNowUtcIso`) on every path (`stageCompletedAt` in `src/services/projects/projectStatusSync.ts`): a completed stage keeps its time and a stage leaving «completed» has none. Every project audit row is written in `src/services/projects/projectAudit.ts` with the write's `tx`: a project edit with before and after of the changed fields, and each stage add, edit and delete under the retained entity «مرحله پروژه تولید» with the project id and the stage before and after. A project edit never changes its stages: the edit form shows them read-only with a button to the stages section, sends no `initial_stages`, and `PUT /projects/:id` refuses them with 422 `PROJECT_STAGES_READ_ONLY`; stages change only through the stage routes. `PUT /projects/:id` requires the project's `version` (400 without it) and refuses a stale one under the project row lock with 409 `OCC_CONFLICT` and «پروژه را کاربر دیگری تغییر داده؛ دوباره باز کنید.» (`assertProjectVersion` in `src/services/projects/projectVersion.ts`); every save, a status change by the progress matrix and the completion at delivery raise the version, and the edit form and the project tabs send the version they were built from and remember each save's answer (`useProjectVersion`). A stale version is still accepted when every part the body writes has the token it was read with: the project record and each save answer carry `partTokens` (specs with the managers, status, attachments, inventory control without the keys only the server writes, the workshop schedule without its work-log links; `projectPartTokens` in `src/services/projects/projectPartTokens.ts`, contract `src/lib/projects/projectParts.ts`), each tab sends them back with its version (`writeBase` of `useProjectVersion`) and takes from a save answer only the tokens of the parts that save wrote (`remember(answer, parts)`), a changed part is 409 `OCC_CONFLICT` naming it (`assertProjectPartsWritable`) whatever version a body with tokens sends, a finalize also needs the specs token, since it reserves from the products, a version above the stored one is 409, a schedule that drops a logged row is the schedule's conflict, also for a body without tokens at the current version, a body without tokens otherwise keeps the old rule, and «تکمیل رزرو» checks the inventory part the same way, so a remittance, an allocation or a workshop approval no longer blocks an open tab. A production project is a page, `/projects/<id>/<tab>` (`ProjectDetailPage`; five tabs in `src/lib/projects/projectWorkspaceTabs.ts`, the earlier window's tab names still read and replaced): its step bar reads the record and `GET /projects/:id/steps` (`loadProjectStepCounts` in `src/services/projects/projectSteps.ts`: requisitions, allocations, live final remittances and waste with a live line (`projectIssueLineConditions`, the rows the issued quantities read), deliveries; counts only, never an amount), its specs are edited on the page (`?edit=1` only opens the editor and is dropped from the address at once, so the editor adds no history entry), a stage's personnel come from the personnel list, and a tab with an unsaved change asks before another tab, the list, an in-app link, the browser's back button (an extra history entry of the same address), the global search, a notification or closing the browser tab (`useUnsavedChangesGuard` / `confirmLeaveIfDirty` in `src/hooks/useUnsavedChangesGuard.ts`; code that navigates elsewhere awaits `confirmLeaveIfDirty()` and navigates with `leaveNavigateOptions()`). Narrower than 768 px (`usePhoneWidth`) the page has a phone layout: a short header (`ProjectPhoneHeader`), the summary of the project instead of the first tab (`ProjectPhoneSummary`: progress, customer, delivery date with `projectDueNote`, current step and the open steps of `pendingProjectSteps`, stage statuses) and one card per product with a 44 px button per stage instead of the progress matrix (`ProjectPhoneProgress`); the desktop table and the phone list read, tick and save through one hook, `useProductProgressTicks` with the rules of `src/lib/projects/progressTicks.ts`, so both send the same `PUT /projects/:id/product-progress`; «نمای کامل مشخصات و مراحل» shows the desktop layout, a layout holding an unsaved change or a running tick save is kept when the screen width changes, and «نمای کامل» asks only before it would drop unsaved ticks, and the phone bottom bar has «پروژه‌ها» for `projects.view`, with at most `MOBILE_NAV_MAX_ITEMS` (5) page buttons beside «فهرست» in `MOBILE_NAV_ITEMS` order.

- **Project BOM Allocation From a Receipt:** Materials enter stock only through a purchase receipt and are then allocated from stock with `allocateMaterialsForProject` (the allocation's source movement is its own `out` row); the unused allocation-from-receipt path was removed. `releaseAllocation` brings the materials back at the Kardex unit cost of the allocation's own `out` movement, never the current WAC; an allocation whose source movement is an `in` (a receipt allocation before v8.0.32) is released without a stock movement. Every allocation issues a draft voucher Dr work in progress (1402, detailed project) / Cr raw materials or finished goods (by item type) at the Kardex cost of its out movement, linked by `journal_vouchers.source_bom_allocation_id` (migration 0049, `src/services/accounting/bomAllocationVoucher.ts`); releasing the allocation voids it through `voidSourceVoucher`; consumption posts nothing, the materials stay in 1402. Delivering a project's finished goods to stock («ورود به انبار», `ProjectService.addProjectToInventory`) issues, in the same transaction, a final `production_receipt` document linked to the project, whose voucher debits finished goods and credits work in progress (detailed project), at the entered unit price, else the item's current WAC; it never moves stock directly. Its production receipt's CREATE audit row (`createdAudit` of `createDocumentWithDetails`) and the project's delivery row, and the rows of a material allocation, its consumption and its release (`src/services/inventory/bomAllocationAudit.ts`), are written with their own transaction. That delivery is the only way a production receipt naming a project is recorded: `POST /documents` refuses one with a `projectId` with 422 `PRODUCTION_RECEIPT_PROJECT_ONLY` (`assertNotProjectDelivery` in `src/services/documents/documentRecordRule.ts`). A finished product made outside any project enters stock from the stock page as a production receipt without a project: final only (a draft, and finalizing any draft production receipt, is 422 `PRODUCTION_RECEIPT_FINAL_ONLY`, `assertProductionReceiptNotFinalized`), rial only (422 `PRODUCTION_RECEIPT_RIAL_ONLY`) and finished products only (422 `PRODUCTION_RECEIPT_PRODUCTS_ONLY`), checked after the item locks by `assertStandaloneProductionReceipt` (`src/services/documents/standaloneProductionReceipt.ts`); it has no party, its unit cost is the entered material cost, else the item's current weighted average cost, it is recorded only with `warehouse.production_receipt` (`PRODUCTION_RECEIPT_PERMISSION`, requires `warehouse.in`, granted to no role by default), and its draft voucher debits finished goods and credits «مصرف مواد بی پروژه» (mapping `unassignedConsumptionAccountCode`, default 6003) instead of work in progress; the stock page offers it to holders of that key, rial, without a party and picking finished products only. Delivery is capped by the project's planned quantity: under the project lock the sum of the project's final `production_receipt` lines per item (`deliveredProjectQuantities` in `src/services/projects/projectDeliveryCap.ts`) plus this delivery may exceed the planned quantity (`products`, else the main item and quantity) only with `overDeliveryReason` (else 422 `OVER_DELIVERY_REASON_REQUIRED`, the «ورود به انبار» tab asks for the reason and resends); the reason goes into the receipt notes and the activity log; a cancelled project or an item outside the project's products is refused. A project with an open (`allocated`) BOM allocation is not deleted: `deleteProject` locks the project row and refuses with `PROJECT_HAS_OPEN_ALLOCATIONS` until the allocations are released; nor is one with a live document or a work-in-progress (1402) balance in rials over vouchers of any status (409 `PROJECT_HAS_LEDGER_ITEMS`, `assertProjectDeletable` in `src/services/projects/projectDeleteGuard.ts`, `projectWipBalances` in `src/services/accounting/projectWipBalance.ts`), and the financial health check lists the 1402 balance of each completed, cancelled or deleted project (`project_wip_closed_balance`); piecework labour stays a period expense, so the delivery price is the materials cost only and the «ورود به انبار» tab says so; cancelling such a project is refused the same way (`assertNoOpenAllocations` in `src/services/projects/projectOpenAllocations.ts`), and materials are never allocated to a cancelled or completed project (422 `PROJECT_CLOSED_FOR_ALLOCATION` under the project lock, `isProjectOpenForAllocation` in `src/lib/projects/projectStatus.ts`; the allocation form offers only open projects), while releasing its earlier allocations stays possible. A cancelled project takes no new document either: a final document with its `projectId`, the finalize of a draft one and a new or moved work log on it are 422 `PROJECT_CANCELLED` (`assertProjectNotCancelled` in `src/services/accounting/projectCancelledGuard.ts`), while voiding earlier ones stays possible. Both allocation paths pass the remittance's sellable gate after the item locks and before any movement (`assertOutflowWithinSellable` with the project's id, `assertAllocationWithinSellable`): the reservations of another project or a sales proforma are never allocated, the project's own reservation is free, and a shortage is 400 `INSUFFICIENT_STOCK` with nothing moved. Allocation moves stock out and asks the remittance's `warehouse.out` only (`BOM_ALLOCATE_PERMISSIONS`); releasing an allocation and the project delivery bring stock in and ask the receipt's `warehouse.in` as a second guard besides their own keys (`PROJECT_STOCK_IN_PERMISSIONS` in `src/lib/permissions/projectPermissions.ts`), and their buttons follow both guards (`canReleaseAllocation`, `canDeliver` of `useProjectPermissions`); no migration grants the warehouse keys. `GET /inventory/allocations` searches (Arabic letters folded), filters and counts in SQL; with `page` it answers one page `{ allocations, total, page, limit, statusCounts }` (counts of every status under the other filters), without it every filtered allocation for the Excel export (`listBomAllocations` / `bomAllocationStatusCounts` in `src/services/inventory/bomAllocationList.ts`), and the finalize reads only the stock items its need rows and preset materials name by code or name key, trimmed as JavaScript trims and case-mapped under the «C» collation, plus every item whose code or name holds a character outside ASCII and the Arabic script, so each row gets the lowest-id match, by code then by name (`readStockItemsForRefs`); a NUL in a search or filter is dropped (`normalizeSearchText`, `withoutNul` in `src/lib/search/searchText.ts`).

- **Project Free Stock, Delivery Cost and Issued Materials:** The project materials tab, the purchase list and «سفارش خرید بخش» judge each material row with the finalize's own rule: free for the project = total stock − the reservations of sales proformas and other finalized projects (never below 0), and the need less what the project already received (`projectIssuedQuantities`), read from `GET /projects/:id/material-availability?itemIds=` (quantities only, `READ_PERMISSIONS.projectRecord`; `projectMaterialAvailability` in `src/services/projects/serverInventoryControl.ts`) and turned into a row state by `buildMaterialAvailabilityView` (`src/lib/projects/materialAvailability.ts`, which runs `planProjectReservation` on the unsaved sections): «موجود», «کسری», «تبدیل واحد لازم» and «بی کالای انبار» are automatic and a row keeps only «در حال سفارش» by hand (`procurementStatus`); without those figures no row is «موجود», the readiness is unknown and the purchase list keeps the earlier total-stock rule. The «ورود به انبار» tab reads `GET /projects/:id/delivery-cost` (the project's 1402 balance from `projectWipBalances`, every voucher status, and each planned product's delivered quantity; the balance and the average cost only for item cost readers, `ITEM_COST_READ_PERMISSIONS`) and, for a single-product project, prefills the unit cost with balance ÷ max(remaining plan, this delivery) at four decimals (`suggestedDeliveryUnitCost` in `src/lib/projects/deliveryCostSuggestion.ts`); the user may change or clear it, and a cleared field still posts no price (the current average cost). Before posting it shows the balance, what this delivery credits and what remains, and warns for several products or a balance left at plan completion; right before each post it reads the balance again (after a failed read too; it skips the read only when a successful read said the cost is hidden), refuses a suggestion that changed meanwhile and asks a confirmation when the delivery would leave the 1402 balance below zero once rounded to the rial, half away from zero like the voucher (`checkDeliveryPrices`, `wipOverdrawn`); the over-delivery resend is priced and checked for the quantities it sends, and changing a quantity closes its reason prompt; the server's posting rule and every existing voucher and balance are unchanged. «سفارش خرید بخش» groups a section's rows by warehouse item when the finalize turns them into its unit, else by item and row unit, never adding quantities of different units, orders min(the project's shortage of the item, the section's need) in the item unit and marks «در حال سفارش» only the rows it orders (`buildSectionPurchaseList` in `src/components/project/projectInventoryUtils.ts`), and a finalized project whose stored shortage is now covered says «تکمیل رزرو» reserves it (`storedShortagesNowFree`). The materials tab lists «مواد گرفته‌شده از انبار» from `GET /projects/:id/issued-materials` (open or consumed allocations and live final remittances and waste of the project, the newest 500, the Kardex cost only for item cost readers; `projectIssuedMaterials` in `src/services/projects/projectIssuedMaterials.ts`).
