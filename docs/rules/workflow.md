# Workflow Engine

Definitions and versions, transitions and their actions, inbox tasks, SLA and reminders.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md`, and a «§N» below refers to that file's numbering.

1. **Rule Engine (`ruleConditionsJson`):** Evaluate context variables using operators (`eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `in`, `contains`). A document's `amount` / `finalAmount` / `totalAmount` is its payable amount in IRR — net of active lines + VAT + service charge, times the document's exchange rate, else the `exchange_rate_<cur>` setting (`workflowDocumentAmount`); a foreign document without any rate has amount `NaN`, so no amount comparison passes. The stepper shows that amount in IRR and a foreign document's own amount in its currency beside it. A transition's rule is validated when the design is saved (422), and a stored node that is neither a rule (`field` + `operator`) nor a group (`conditions` / `rules` array) evaluates closed (`INVALID_RULE_OPERATOR` in `src/services/ruleEngine.service.ts`); only an empty expression (`null`, `[]`, `{}`) means no condition. A numeric comparison (`gt` / `gte` / `lt` / `lte`) reads both sides with Persian or Arabic digits and thousands separators, and `eq` / `neq` compare a numeric value with a typed number as numbers (`ruleComparableNumber` / `numericRuleEquality` in `src/lib/events/ruleConditionValue.ts`, built on `normalizeDecimalString`); text keeps its exact comparison, and the rule editor saves a numeric comparison's value as a number and refuses one that is not a number (`checkRuleConditionValue`).

2. **Parallel Approvals (`approvalProgressJson`):** Support `SINGLE`, `AND_ALL`, `OR_ANY`, and `K_OF_N` multi-signature rules.

3. **Immutable DSL Versioning, Drafts and Publishing (`snapshotDsl`; drafts v10.1.21):** Every definition save (`saveWorkflowDefinition` / `createDefinition`) writes states, transitions and a new `workflow_definition_versions` row in ONE transaction (`recordDefinitionVersion` in `src/services/workflow/workflowSnapshot.ts`: snapshot of the tables with database ids, `workflow_definitions.version` bumped). The first save of a new definition (designer, template, seed) is published at once; every later save of an existing definition is a draft (version status `draft`; the live step and action tables hold it) that no new record sees until it is published. A design is saved only with exactly one initial step, at least one terminal step, unique step keys, every action's source and target found and no action out of a terminal step except the `rejected` one (`workflowDesignErrors` in `src/lib/workflow/workflowDesignRules.ts`, also checked by the designer before saving; else 422). `startInstance` stores the snapshot of the published version on the instance (`workflow_definitions.published_version`, `publishedVersionOf`; one `published` row per definition by `uq_wdv_definition_published`, migration 0114, which published every existing definition's latest version), a published version without a usable snapshot is 409 `WF_PUBLISHED_VERSION_UNUSABLE`, and a running instance keeps executing against its own snapshot. An entity has at most one `IN_PROGRESS` instance: `startInstance` takes the transaction advisory lock (namespace `WORKFLOW_ENTITY_START` 91009, `hashtext(type:id)`) before looking for one (same definition returns it, another definition is 409 `WF_INSTANCE_ALREADY_OPEN`), backed by the partial unique index `uq_workflow_instances_open_entity` (migration 0056, created only on data without duplicates; the financial health check lists duplicates as `workflow_open_instance_uniqueness`). The workflow tables carry foreign keys only among themselves (migration 0059: steps, actions, instances and versions to their definition, action endpoints to steps, history, tasks and pending approvals to their instance with `ON DELETE CASCADE`; added `NOT VALID`, validated only on clean data, gaps listed by the financial health check as `workflow_reference_integrity`); step, action and user ids held by instances, history, tasks and approvals have none, because they are snapshot ids or users that may be removed. A version number is unique per definition (`uq_wdv_definition_version`) and `recordDefinitionVersion` takes it under the definition row lock `FOR NO KEY UPDATE`, which does not block the foreign-key lock of an instance start. A snapshot without database ids (pre-v7.0.87 version 1 rows holding the raw designer payload) is never used (`isUsableSnapshot`; the current tables are read instead). Version history (`GET /workflow/definitions/:id/versions[/:version]`, «تاریخچه نسخه‌ها» on the workflow page) shows each version's status (draft, published, retired) and is never rewritten; `GET /workflow/definitions/:id/draft` gives the draft and what it changes against the published version (`workflowVersionDiff` in `src/lib/workflow/workflowVersionDiff.ts`: steps by key, actions by their steps and key, never by id). Only `workflow.admin` (`WORKFLOW_SWITCH_PERMISSION`) publishes the draft it looked at (`POST /workflow/definitions/:id/publish` with `draftVersion`: a draft saved meanwhile 409 `WF_DRAFT_CHANGED`, none 409 `WF_NO_DRAFT`, one against the design rules or naming a missing role 422) or reverts to an earlier version (`POST /workflow/definitions/:id/revert`: that version's snapshot becomes the design and is published as a new version, any draft set aside, the audit row naming the version reverted from; a version without a usable snapshot or of another record type is 422 `WF_VERSION_NOT_RESTORABLE`), each in one transaction under the record type lock and the definition row lock with its audit row written with `tx` (`src/services/workflow/workflowVersionPublish.ts`). The lifecycle switches, the role delete guard, the boot seed guard upgrades (which skip a definition with a draft) and the unguarded-action health checks read the published version, never the draft (`publishedDesignOf`, `ensurePublishedSnapshot`, `publishedWorkflowActions`).

4. **Canvas Position Persistence:** Persist node coordinates (`positionX`, `positionY`), `slaHours` and `stepOrder` in `workflow_states`; a step saved without a positive `stepOrder` takes its list position, and the designer keeps the stored order. `POST /workflow/positions` takes the definition id and moves only that definition's steps, in one transaction under the definition row lock with an audit row (another definition's step is 422); the write routes `/transition`, `/definitions`, `/positions` and `/delegations` validate their bodies with the Zod schemas in `src/routes/workflowRouteSchemas.ts`. A workflow approval or transition invalidates the documents, procurement, accounting and inventory queries (`workflowChange` in `src/lib/queryInvalidation.ts`), and saving a design or step positions refetches the definition detail (`QUERY_KEYS.workflow.definition`).

5. **SLA Analytics:** SLA compliance and bottleneck states derived from `workflow_history_logs`: time in the current step counts from the latest history row that entered it (`currentStepEnteredAt` in `src/services/workflow/workflowSlaEvaluator.ts`; a partial signature `<action>_SIGN` is no entry, so it never restarts the count), compared with `slaHours`, and history is read in (`created_at`, `id`) order. A running instance's step and its `slaHours` come from the instance's own snapshot, counted under the current step with the same key. The report is counted in PostgreSQL (`getSlaAnalytics`: counts, each running instance's entry into its current step, step durations with `lead()` over the step entries, the step of each instance from its own snapshot grouped by `md5(snapshot_dsl)`, hashed once per instance), never by loading every instance and history row (reg_workflow_sla_in_sql_td_1323 compares it with the earlier loop). Every `WorkflowEngineService` facade method is bound to its own class (`.bind`), so a static method's `this` is never the facade.

7. **SLA Reminder, No Auto-Expiry:** A task whose `due_at` passed stays `pending`; `WorkflowSlaReminderService` (every minute, advisory lock 91006) sends its assignee — assigned / candidate users plus their active delegate, else the users of the task's role (a roleless `ALL` task: only admins and holders of `workflow.approve` / `workflow.execute`), in both cases only those holding the transition's required permission, read from the instance's snapshot — ONE in-app notification and stamps `sla_reminded_at` (no repeats, no admin copy, no SMS/email). Tasks auto-expired before v7.0.101 were reopened (current step of a running instance) or kept, all listed in `workflow_task_reopen_log` and the SLA analytics tab. Never reintroduce automatic expiry.

6. **Instance API Contract:** `GET /workflow/instance/:entityType/:entityId` returns `{ instance, definition, currentState, allStates, availableTransitions, history, approvalProgress, entityContext }` (`WorkflowInstanceData` in `useWorkflowQueries.ts`, read by `WorkflowStepperWidget`), or `{ instance: null }`; `allStates` come from the instance's own snapshot ordered by `stepOrder`. Signature progress shows the server's `requiredCount`. Transitions the user's role allows but whose `ruleConditionsJson` fail come back in `blockedTransitions` with Persian `unmetConditions`; every transition carries Persian `conditions` (`src/lib/workflowRuleText.ts`, also used for rule-failure errors) — never English field/operator text.

8. **Inbox Tasks Run Their Own Transition:** `executeTaskById` approves with the task's own transition (a task no longer of the current step gets 409 `WF_TASK_STALE`) and rejects only with a reject transition of the current step, read from the instance's snapshot (`transitionsFromState`): the chosen `transitionId`, else the only one the user may run; a step without one is refused (422 `WF_TASK_NO_REJECT_TRANSITION`), never approved. The task closes only when its transition fires: a signature that does not meet the quorum, or a repeated one, leaves it pending in every signer's inbox. Tasks and the deadline of a newly entered step come from the instance's own snapshot (`refreshPendingApprovals` with `snapshotDsl`), never from the live tables, whose ids change on every design save. Entering a step clears the signatures of that step's transitions, so after a return or rejection the same user can act again and an old signature never counts toward a new quorum. A step with a required role passes only for that exact role (case-insensitive) and the system admin; no equivalent role, department posting permission or `*` passes it, and who may sign is the transition's `requiredPermission` (`checkUserRoleMatch`; same-department roles and posting permissions passed from v8.0.94). A design is saved only with defined roles, stored with the roles table's code (`resolveTransitionRoles` in `src/services/workflow/transitionRoles.ts`, else 422 `WF_UNKNOWN_ROLE`), and catalog permission keys (`workflowDesignErrors`); a role named by a live transition or an unfinished instance's snapshot is not deleted (409 `ROLE_USED_BY_WORKFLOW`); the default journal-voucher workflow asks permissions only (approve, finalize and back to draft `accounting.vouchers_approve` since v10.0.27; reject `accounting.vouchers`). Migration 0065 turned each stored guard that only the removed rules made work into its permission and listed in `activity_logs` every role step whose role is missing or that another role used to sign, for the admin to decide; the financial health check shows those still standing (`workflow_role_review`, `src/services/workflow/workflowRoleReview.ts`). A live or published action whose `requiredPermission` is not a catalog key (such as the removed `audit.create`) is listed by the financial health check until its design names a catalog key (`workflow_unknown_permission_action`, `src/services/accounting/workflowUnknownPermissionHealth.ts`). Since v10.2.0 the boot rewrites `audit.create` to `audit.apply` in a published definition without a draft, publishing a new version with a «طرح گردش کار» audit row in its transaction (`replaceRemovedWorkflowPermissions` in `src/services/workflow/removedPermissionKeys.ts`; its failure is logged and never stops the boot seed), a definition holding a draft is left alone and stays listed, and a running instance's snapshot that still asks the removed key is signed by the holders of its replacement (`REPLACED_PERMISSION_KEYS`, read only through `effectivePermissionKey`, an own-property lookup used by `holdsRequiredPermission`, the inbox and its counts and the task recipients, and a refusal names the replacement). The engine reads the signer's role permissions itself (`signerPermissions`, never only `req.user.permissions`, which the token does not carry), and the inbox, its counts and task execution apply the same `checkUserRoleMatch`; only the `admin` role signs every step — `workflow.manage` / `workflow.admin` are design permissions and sign no one else's step. The default document workflow is guarded by permissions only — warehouse review and its reject `warehouse.out`, accounting review and its reject `accounting.vouchers`, direct approval `workflow.admin` (`DOC_APPROVAL_STEP_GUARDS` in `src/services/workflow/docApprovalGuards.ts`); an installed definition is upgraded only when it is exactly the old seed, otherwise the financial health check lists document approvals with neither role nor permission (`workflow_unguarded_document_approval`). A step that runs a domain action also needs the entity's own permission from the signer (or the delegator's role): finalize `documents.edit` / `warehouse.in` / `warehouse.out`, voucher status `accounting.vouchers` (approved, permanent or back to draft `accounting.vouchers_approve`), item opening `products.create`, bank opening `accounting.treasury`, a purchase requisition entering `received` `warehouse.in` (`requiredPermissions` of the domain's registration, 403 `WF_ENTITY_PERMISSION_REQUIRED`). The inbox tabs (`GET /workflow/tasks/my-tasks?status=`, `MY_TASK_FILTERS`) are pending, overdue (pending with `due_at < now()` in SQL, `isOverdue` in each row), delegated (pending tasks reached only through a delegation) and completed (the user's own step actions and signatures from `workflow_history_logs`, paginated in SQL); `/tasks/stats` counts each with the same rule. The inbox has only this tasks view: the instances view and `GET /workflow/inbox` were removed. Opening or closing an inbox task resets its decision, comment and chosen reject action. Each inbox row carries the current step's reject actions (`rejectTransitions`: id, title, from the instance snapshot); with more than one, the task form asks which and sends it as `transitionId`. The task form reads its document or requisition through `useApprovalTaskEntity` (`src/hooks/useApprovalTaskEntity.ts`), which aborts the previous task's request and ignores a late response. An inbox row carries `currentStepTitle` (from the instance snapshot), `delegationInfo`, `instance.startedByName` and a numeric IRR `amount` (`inboxEntityFields` in `src/services/workflow/workflowInboxRows.ts`). Task execution locks the instance row before the task row, the same order as a direct transition. An AND_ALL step passes when every non-deleted user holding its required role has signed (`andAllMemberIds`); a signer outside the role never fills a member's place, and a step without a role (or a role without members) needs the designer's K (at least 1). During an active delegation (not revoked, within its window, scope `ALL` / `*` / the workflow code, neither user deleted) the delegate sees and runs the delegator's tasks — assigned, candidate or the delegator's role (`delegationForTask`, `WorkflowDelegationService.activeDelegations`); a transition the delegate's own role does not cover is signed through `resolveSigner` in the delegator's name with `signedBy` = the delegate, and neither of them signs that step again. A new delegation's scope is `ALL` / `*` or the code of a defined workflow (else 422), and the delegation form offers only these. Only the delegator or an admin revokes a delegation (403 otherwise, under the delegation row lock); invalid delegation input is a `ValidationError` and a missing delegation or user a `NotFoundError`. Workflow API responses send server timestamps with a `Z` (`withUtcTimestamps` in `src/services/workflow/workflowTimestamps.ts`), and a delegation given as days runs from the start of its first day to the end of its last day in the display time zone. A purchase requisition workflow action runs only a transition from the instance's current step (`executeWorkflowAction`; otherwise 409 `WF_ACTION_NOT_IN_STEP`, never a direct status change), and the requisition status comes only from the transition's target step; a `REJECTED` instance continues only through a transition drawn out of its rejected step (reopen), a `COMPLETED` one never. The action never rewrites the instance's step from the requisition status, and a received requisition takes no workflow action (409). A transition with a `requiredPermission` runs and is offered only for an admin or a user whose role (read with the same `tx`) or own permissions include it (`holdsRequiredPermission`, 403 `WF_PERMISSION_REQUIRED`; a delegate is checked against the delegator's role), and the designer shows and keeps the field. Receiving an unapproved requisition first runs the current step's approve transition in the receiver's name through `executeTransition` (role and permission checked, recorded in the history), then receives; without approval rights it is refused and nothing enters stock. A transition with `is_initiator_excluded = 1` (migration 0050, designer option «آغازکننده تأیید نکند», off by default) is refused (403 `WF_INITIATOR_EXCLUDED`) for the instance's `started_by` — signing for themselves, as someone's delegate or through their own delegate — and is left out of their inbox, task count and offered transitions (`initiatorExcluded`); an admin is exempt. A transition with `is_initiator_only = 1` (migration 0099, designer option «فقط آغازکننده اجرا کند», off by default, never together with «آغازکننده تأیید نکند») runs only for the instance's `started_by`, in their own name or through a delegate signing in their name; it is refused for anyone else with 403 `WF_INITIATOR_ONLY` and left out of their offered transitions and inbox (`initiatorOnlyRefused`), an instance without a starter runs it only for the admin, and the admin is exempt. The default document workflow's «ارسال به انبار» asks `documents.create` and is initiator-only, so only the seller who recorded a proforma sends it, and its «بازگشایی» asks `documents.edit`; an untouched installed definition is upgraded at boot (`DOC_APPROVAL_SUBMIT_GUARD_UPGRADE`), an edited one is only listed by the financial health check (`workflow_unguarded_document_step`, `src/services/accounting/unguardedDocumentStepHealth.ts`) (guide test finding B-01).

9. **Transition Actions Run in the Approval Transaction:** What a transition does to its entity — finalizing a document on `approved` / `POST_INVOICE`, the item and bank-account opening vouchers, a journal voucher's status, a purchase requisition's status and goods receipt — is registered by its domain with `registerWorkflowTransitionAction` (`src/services/workflow/workflowTransitionActions.ts`; composition root `registerWorkflowDomainActions` in `src/services/system/workflowDomainActions.ts`, called by `server.ts` and the test bootstrap) and run by `executeTransition` with the transition's own `tx` before its outbox records; its error refuses the transition and the caller's transaction and reaches the approver. A domain's `lockEntity` locks the entity row before the instance row (`executeTransition` and `executeTaskById`). There is no in-process workflow emitter: the transition's audit log is written with `tx`, and `WorkflowTransitioned` / `WorkflowCompleted` / `WorkflowRejected` go only through the outbox. A requisition entering `received` by any path is received with `receiveRequisitionItems` unless already received; a missing user id is never replaced with 1.

10. **Definition Lifecycle, One Active per Record Type:** A record type has at most one active workflow definition (partial unique index `uq_workflow_definitions_active_entity_type`, migration 0110, built only on clean data; the financial health check lists duplicates as `workflow_active_definition_uniqueness`). A definition is turned on, off, archived and restored only through `setWorkflowDefinitionActive` / `setWorkflowDefinitionArchived` (`src/services/workflow/workflowDefinitionLifecycle.ts`; `POST /workflow/definitions/:id/activate|deactivate|archive|restore`, `WORKFLOW_SWITCH_PERMISSION` = `workflow.admin`), each in one transaction under the record type's advisory lock (`WORKFLOW_DEFINITION_TYPE` 91070) and the definition row lock, with its audit row (entity «طرح گردش کار») written with `tx`; activating beside another active definition needs `replaceActive` (else 409 `WF_ACTIVE_DEFINITION_EXISTS` naming it) and turns that one off in the same transaction; an archived definition is never activated (409) and an active one never archived (409); a definition is never deleted. The purchase requisition workflow is never turned off (409 `WF_REQUIRED_WORKFLOW`, `WORKFLOW_REQUIRED_ENTITY_TYPES` in `src/lib/workflow/workflowLifecycle.ts`), and a requisition starts with the active definition of its type, never a fixed code. A new definition is active only when its type has none, otherwise saved inactive with a notice; the designer shows the record type (`WorkflowEntityTypeField`) and the save changes it only on an inactive definition no record ever entered (422 `WF_ENTITY_TYPE_LOCKED`, `workflowEntityTypeChangeRefusal`); every design save writes its audit row with `tx`. Running instances keep their own snapshot whatever happens to the definition. Part B: «ساخت از الگو» (`POST /workflow/definitions/from-template`, `workflow.manage` / `workflow.admin`, `makeDefinitionFromTemplate` in `src/services/workflow/workflowTemplateDefinition.ts`) makes an inactive definition from one of the four templates of `src/lib/workflow/workflowTemplates.ts` (item, bank account, purchase requisition, journal voucher; actions guarded by permission keys only; the purchase requisition and journal voucher seeds read the same templates), and the definition form offers only `WORKFLOW_ENTITY_TYPES` (`WorkflowCreateModal`). A workflow starts only on the server, in its record's create transaction: `POST /workflow/start` and the widget's start button are gone. A manual draft voucher (`POST /accounting/vouchers`) enters the active journal voucher workflow in its create transaction, and while that workflow runs the voucher page does not approve, finalize or put it back to draft (409 `VOUCHER_IN_WORKFLOW`, `assertVoucherNotInWorkflow` in `src/services/accounting/voucherWorkflowLock.ts`; a batch leaves it out with that reason); the voucher list and detail carry `inWorkflow` and the page shows «در گردش کار»; reversing or correcting a voucher closes its workflow (`terminateVoucherWorkflows`). Part C: an approver gives a deputy from the inbox («تفویض کارهایم», `MyDelegationsWindow`, shown by `WORKFLOW_DELEGATE_PERMISSIONS`) with the one delegation form (`DelegationForm`, users from `/users/list-simple`, scopes from `GET /workflow/delegation-scopes`: workflows not archived) and reads «تفویض‌های من» (`GET /workflow/delegations?mine=1`, given and received, revoke only what one gave); a delegation whose window and scope (`ALL` meets every scope) meet a live delegation of the same delegator is 409 `WF_DELEGATION_OVERLAP` naming it, checked under the transaction advisory lock `WORKFLOW_DELEGATION_FROM_USER` (91080) and written with its audit row in one transaction (`findOverlappingDelegation` in `src/services/workflow/workflowDelegationService.ts`); a deputy signing in the delegator's name is the delegator for a domain rule about who may act (`actingForUserId` on `WorkflowTransitionEvent`), so the maker rule of a journal voucher is checked for both and a maker never approves their own voucher through a deputy. The system admin closes a running record that cannot move on («بستن فرایند» in the workflow widget; `POST /workflow/instances/:id/terminate`, `workflow.admin`, a reason of at least `WORKFLOW_TERMINATE_REASON_MIN` characters): under the instance row lock only, instance `TERMINATED`, pending tasks canceled, one `terminate` history row with the reason and an audit row with `tx` (`terminateWorkflowInstance` in `src/services/workflow/workflowInstanceTerminate.ts`); only a sales document, a journal voucher or a raw material request is closed (`workflowTerminateRefusal` in `src/lib/workflow/workflowLifecycle.ts`), a purchase requisition, item or bank account is 409 `WF_INSTANCE_TERMINATE_REFUSED`, since its orders, receipt or opening voucher come only from its workflow.
