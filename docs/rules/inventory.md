# Inventory

Stock, weighted average cost, Kardex, reservations, warehouses and stock reconciliation.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md`, and a «§N» below refers to that file's numbering.

- **Single Source of Truth for Stock (audit P2-1 / TD-214):** Per-warehouse stock lives ONLY in `item_warehouse_stocks` (one row per item × warehouse, CHECK non-negative); a missing row means zero. The `items.stocks` JSONB column was dropped (old values kept in `items_stocks_archive`). `items.current_stock` is maintained ONLY by the database (`trg_iws_refresh_item_current_stock` on `item_warehouse_stocks` and `trg_items_current_stock_from_table` on `items`): application code must never write it — a direct write is replaced by `SUM(item_warehouse_stocks)`. API responses that need a per-warehouse map build `stocks` / `stock_<code>` from `ItemWarehouseStockService.getStocksForItems` (canonical warehouse codes via join); availability / count / transfer checks read the table.

- **Weighted Average Cost (WAC):** Updated ONLY on stock 'in' — including the return of a voided outflow, which comes back at that outflow's own Kardex cost (`applyStockReversal`; a cost of 0 leaves WAC unchanged). If current stock <= 0, new WAC equals the new unit price. An incoming movement at price 0 leaves WAC unchanged and its Kardex row records the current WAC as its cost; a production receipt voucher takes such an item's cost from the document's own Kardex `in` rows (`kardexInCostByItem`). A receipt or purchase line with no net price (free goods: price 0 or a full line discount) is posted at that Kardex cost — debit inventory, credit «درآمد کالای اهدایی» (5204, mapping `donatedGoodsIncomeAccountCode`); the supplier is credited only with the priced lines. An item without a weighted average cost never enters stock at zero cost: a final receipt, purchase or production receipt (create and finalize, so procurement delivery and project delivery too) refuses a line whose net IRR unit cost is zero for such an item with 422 `INCOMING_LINE_WITHOUT_COST` naming the items, before any movement (`assertIncomingLinesHaveCost` in `src/services/documents/incomingLineCost.ts`); a zero line of an item that has a cost stays the donated-goods case. WAC and Kardex amounts are in IRR: a foreign-currency document's unit price is converted with the document's own exchange rate (`stockUnitPriceInIrr` in `src/services/documents/documentExchangeRate.ts`) before `applyStockMovement`.

- **Purchase Line Discount in Cost:** An incoming line (receipt, purchase, production receipt — not a sales return) enters stock at its net unit price, (quantity × price − line discount) ÷ quantity floored at 0 (`netLineUnitPrice` in `src/services/documents/purchaseLineCost.ts`), the same net the purchase voucher posts; a foreign-currency line is converted on the net price without intermediate rounding.

- **No Outflow Without Cost:** An `out` movement records the item's WAC as its cost. If WAC <= 0 the movement is rejected (`ValidationError`) — sales invoices, remittances/waste, project material allocation, WooCommerce orders — except stock-count and Excel adjustments (`documentType = 'audit'`), which are recorded at cost 0. The document price (sale price) or a price-list price is never used as cost. The financial health check values stock at WAC only too: an item with stock and no WAC counts 0 and is listed. A final sales invoice whose gross is zero (free sample, gift) still gets its voucher: cost of sales at the Kardex cost of its `out` rows against inventory, with no revenue or customer row (`syncSalesInvoiceVoucher` writes no zero row).

- **Sales Return Cost:** A sales return (`return`, stock in) enters stock at the cost of the original sales invoice's Kardex `out` rows (`documents.return_of_document_id`, `resolveSalesReturnUnitCosts` in `src/services/documents/salesReturnCost.ts`), or at the item's current WAC when no original invoice is linked — never at the sale price. Its voucher reverses cost of sales with the return's own Kardex `in` cost. A return with an original invoice is capped per item at the invoice's active Kardex `out` quantity minus the active Kardex `in` quantity of that invoice's earlier returns (`assertReturnWithinSold`: items then the invoice are row-locked; checked on final create and on finalize; voided or draft returns do not count). An invoice with a sales return that is not voided, in any status, is not voided: `deleteDocument` refuses with 409 `DOCUMENT_HAS_ACTIVE_RETURNS` naming the returns, after the document lock and before any write (`assertVoidHasNoReturns` in `src/services/documents/voidDependents.ts`). Nor is a document with a live treasury receipt or payment (completed, not a reversal): 409 `DOCUMENT_HAS_TREASURY_ROWS` naming them (`assertVoidHasNoTreasuryRows`, same file); the treasury user moves such a row on account or to another active document of the same party and currency with `PUT /accounting/treasury/:id/document` (`relinkTreasuryDocument` in `src/services/accounting/treasury/treasuryDocumentRelink.ts`, `accounting.treasury`, the TD-501 link rules, bank → document → row locks, audited with `tx`; the voucher is unchanged; the treasury table offers «علی‌الحساب» and «انتقال به سند دیگر», whose targets come from `GET /accounting/treasury/:id/document-options` (`listTreasuryRelinkOptions`, active documents of the same side, currency and party)) (same decision). A return with an original invoice takes that invoice's currency, exchange rate and net unit price per item — (quantity × price − line discount, floored at 0) summed over the item's lines ÷ their quantity, rounded to four decimals (`invoiceReturnTerms` in `src/lib/documents/returnUnitPrice.ts`, shared with the stock page) — with no line discount; a return that completes an item's invoiced quantity together with the earlier final returns puts the exact remaining net of the invoice on one unit of that item's last line (`completeReturnLines` in `src/services/documents/salesReturnCompletion.ts`, the completion price accepted by the price check); another currency, rate or price, a line discount or an item not on the invoice is 422 (`RETURN_CURRENCY_MISMATCH` / `RETURN_EXCHANGE_RATE_MISMATCH` / `RETURN_PRICE_MISMATCH`), and a field not sent is filled from the invoice (`enforceReturnInvoiceTerms` in `src/services/documents/salesReturnPrice.ts`, on create, on draft edit and on finalize, where a stored draft that differs is 422); the stock page fills and locks them. The stock page finds the original invoice with `GET /documents/by-ref/:ref?type=invoice` and an optional `fiscalYear`: one query for an active final document of that type and number (`findFinalDocumentIdByRef` in `src/services/documents/documentRefLookup.ts`), the type is required (400 without it), none is 404 `DOCUMENT_REF_NOT_FOUND`, and a number with final documents in several fiscal years is 409 `DOCUMENT_REF_AMBIGUOUS` listing them, so the page asks for the year, and `GET /documents/:id` reads only a positive whole id (a number there is 400); the page shows each lookup error's own message (`returnInvoiceLookupError` in `src/lib/documents/returnInvoiceLookup.ts`). A return without an original invoice keeps the user's price.

- **Stock Movement Date and Kardex Replay:** The date of a stock movement (document create, finalize, warehouse transfer) may not be earlier — by day — than the item's last ledger movement (rows of voided documents and their reversals do not count, so void + reissue with the original date stays possible). The only exception is the permission `warehouse.backdate` (granted to no role by default), computed in the route with `userHasRoleOrPermission` and passed as `allowBackdate` (never read from the request body); a workflow transition whose domain action moves stock (document approval, requisition receipt; route, inbox or procurement) reads it in `executeTransition` from the signer's own role permissions, for a deputy the delegator's role, the system admin always, unless the caller passed `allowBackdate: true` (`STOCK_BACKDATE_PERMISSION` in `src/lib/permissions/documentPermissions.ts`); a backdated `out` is then accepted only when the warehouse's balance in (day, id) order stays non-negative from that date on (`assertStockMovementDate` in `src/services/inventory/stockMovementDate.ts`, called by `applyStockMovement` and the transfer service). No stock movement may be dated after the business today, for any user (422 `STOCK_MOVEMENT_FUTURE_DATE`, same function); future-dated Kardex rows recorded earlier are never rewritten and are listed by the financial health check (`stock_future_movements`, `src/services/inventory/futureStockMovements.ts`), and a transfer date goes through `requireStorageDate`. The Kardex rebuild replays WAC with `replayKardexWac` (`src/services/inventory/kardexReplay.ts`): registration (id) order and exactly the live engine's formulas (voided rows in place, reversal via the `applyStockReversal` formula, transfers quantity-only), starting from WAC 0 — the item's current WAC is kept only when the replay reaches no positive WAC; the I13 invariant uses the same function. The rebuild («بازسازی موجودی از کاردکس») only rebuilds quantities and reports a WAC that differs from the replay (`replayWac`, `wacDifferences`); setting the WAC to the replay is the separate «اصلاح بهای میانگین» (`POST /inventory/correct-wac`, permission `inventory.wac_correct`, granted to no role by default), allowed only when the stock equals the Kardex balance, which issues in the same transaction a draft voucher for stock × (replay − old WAC) against 7012 (`correctItemWacFromLedger`, `src/services/accounting/wacCorrectionVoucher.ts`). The initial Kardex backfill («ثبت موجودی اولیه کاردکس», `KardexBackfillService`) only adds rows for items with stock and no incoming Kardex row and never reprices an existing row. Voiding a document whose incoming rows were consumed by later-dated outflows is refused: `assertVoidKeepsStockHistory` (`src/services/inventory/voidStockHistory.ts`, called first in `deleteDocument`) rejects a void that would make a warehouse's (day, id) balance negative and names the consuming documents; voiding an outflow is never refused. Voiding a receipt that empties the item's stock or leaves a negative remaining value keeps the WAC, and the void posts in its own transaction a draft rial voucher for the value left in the inventory accounts against «کسری و اضافات انبار» (7012), reference `VOID-RESIDUE-<number>` (`postVoidResidueVoucher` in `src/services/accounting/voidResidueVoucher.ts`).

- **Stock Reservations:** Only a sales proforma reserves stock: type `invoice` or `proforma` in status `proforma` (`RESERVING_DOCUMENT_TYPES` / `isReservingDocument` in `src/lib/documents/reservingDocuments.ts`); a purchase proforma (a `receipt` in `proforma` status), a receipt, purchase, remittance and any draft reserve nothing, and a sales proforma does not expire. A project reserves only the stored `inventory_control.reservedItems` of a finalized project (`isFinalized === true`; `reservingProjectRows` in `src/lib/projects/projectReservationState.ts`, shared with the stock document page): no reader rebuilds a reservation from the sections, the purchase list or the manual items, so a draft or unfrozen project reserves nothing and a consumed reservation stays consumed; legacy projects that disagree (finalized before the server wrote reservations, or not finalized with a stored reservation) are only listed by the financial health check (`project_reservation_integrity`, `src/services/projects/projectReservationHealth.ts`). Finalizing converts each control row to the item unit before summing per matched item (`planProjectReservation` in `src/lib/projects/projectReservation.ts`): a row whose unit (trimmed, case-insensitive; empty is «عدد», as the form shows) differs from the item's is divided by its own `conversionRate` when the rate is positive and `convertedUnit` is empty or the item unit — the rounded `convertedQty` is never read or stored — and any other row in another unit refuses the finalize with 422 `PROJECT_RESERVATION_UNIT_MISMATCH`; the conversion form keeps a directly entered rate unrounded (`directConversionRate`), and legacy unconverted reservations are listed by the same health check. Finalizing reserves per item min(need, total stock − the reservations of others) (first come, first served): under the transaction advisory lock `PROJECT_RESERVATION_FINALIZE` (91011, taken after the project row lock) the server reads the others' reservations of the project's items only (a read error refuses the finalize) and writes each item reserved below its need to `inventory_control.reservationShortages` (ignored in the body, cleared on unfreeze), which the response carries and the purchase tab shows (`ReservationShortageList`); items reserved above their stock are only listed by the financial health check (`stock_reservation_exceeds_stock`), since a stock count or a voided receipt may still lower stock below a reservation. A finalized open project's reservation is brought to today's materials list only through «تکمیل رزرو» (`GET` / `POST /projects/:id/reservation-reconcile`, `projects.edit`; `previewReservationReconcile` / `applyReservationReconcile` in `src/services/projects/projectReservationReconcile.ts`, contract `src/lib/projects/reservationReconcile.ts`): the need follows the finalize rule (`planReservationWithOthers`, its items read like the finalize's with `readStockItemsForRefs`, the stored reservation rows by id too) and the project keeps what it holds up to that need (`ownReserved` of `planProjectReservation`: kept = min(own, need), free = stock − others − own, reserved = min(need, kept + free)), so a later proforma never shrinks it, the shortfall comes only from unreserved stock and the excess is released; the browser shows each item's change and asks before it is posted, and the post runs under the project row lock, the version check (409 `OCC_CONFLICT`) and lock 91011 and only for the plan whose `planToken` was shown (else 409 `PROJECT_RESERVATION_PLAN_CHANGED` with the fresh preview, nothing written); unchanged rows and rows that reach no live item are kept, a changed item's rows become one, and its «کنترل موجودی پروژه» audit row (before, after, each change) is written with `tx`; a list row that names no live item is matched through the code and name a stored reservation row keeps for its item (`itemAliases` of `planProjectReservation`: the live code, a stored row's code, the live name, then a stored row's name, so an old code is tried before a live name and the reconcile may reach another item than a new finalize, which reads no alias; a code or name stored rows give to several items is no alias), a row still unmatched is listed in the preview (`unmatchedRows`), and a plan that would release while one is listed is 422 `PROJECT_RESERVATION_ROWS_UNMATCHED` naming them (`reconcileBlockedByUnmatched`), while a plan that only reserves goes through and keeps the stored shortage of an item outside the plan; the reservation report reads the items of project rows with the same condition (`itemRefKeyCondition` in `src/services/items/itemRefKeyRead.ts`). The sales invoice item picker of an open proforma being edited asks `GET /items/options?reserved=1&excludeDocumentId=<id>`, so «رزرو» leaves out that proforma's own reservation like the sellable gate (`itemPickWithReservedUrl`, `othersReservations`). The reservation summaries, `getReservedStocksMap` and the item list key a reservation by item id, never by the upper-cased code, and a project reservation row finds its item by id before code and name. Every reservation reader fails closed (`getReservedStockDetails` takes only `throwOnError: true`): the item list, the online shop sync and the reservation report pass a read error on and never show zero reservations, and the report page shows an error panel; a stored project row is read as text (`rowText`), and a row that reaches no live item reserves nothing and is listed by the financial health check (`reservation_row_unmatched`, `unmatchedProjectReservationRows`). The reservation report reads only what it is asked for: the sales proforma lines in one joined query (scoped to the asked items), only active finalized projects with stored rows, and only the items those rows name by id, code key or name key, never every item; a scoped read keeps only the project rows that may reach its items, and the online shop sync is scoped to the items it pushes. Every reservation in the report is valued at the item's cost in IRR, the reservation quantity × the item's weighted average cost (`unitCost` / `totalCost`, summed as `totalReservedCost`), for a sales proforma in any currency and for a project alike; the proforma's sale price is never reported (contract `src/lib/inventory/reservedItemsReport.ts`, shared with the report page). `GET /inventory/reserved-items` sends the report as its reader may see it (`reservedItemsReportForAccess`, same file, with `access`): cost and value only to item cost readers (`ITEM_COST_READ_PERMISSIONS`: `products.view`, `products.edit_price`, every `warehouse.*` and `accounting.*` key, P05 decision ت۱۰-۲) and a proforma's buyer only to `documents.view`; other readers get quantities and sources, and the page hides the cost column. The reorder alert page filters by stock status «همه», «بی موجودی» or «زیر نقطه سفارش» (stock above zero, up to the reorder point; `stockStatusOf` / `STOCK_STATUS_FILTER_LABELS` in `src/lib/reorderAlerts/reorderItems.ts`). The reserved items report's «خروجی اکسل» writes an xlsx file «اقلام-رزروشده-<Jalali date>.xlsx» with the `xlsx` library, its cost columns labelled in rial and only for cost readers (`reservedItemSummaryRows` / `reservationEntryRows` / `reservedItemsExportFileName` in `src/lib/inventory/reservedItemsExport.ts`); a proforma's link opens the documents list searched by its number, which reads `?search=` from the address (`invoiceListSearchFromAddress`), and a project's link its inventory control page (`reservationSourcePath`). The reorder alert's purchase form records a final receipt with a line at price zero only after «کالای اهدایی» is ticked, and never for an item without a weighted average cost, which would enter stock without cost and block every outflow (`reorderReceiptPriceError` in `src/lib/reorderAlerts/reorderPurchaseReceipt.ts`); its destination warehouse comes from the active warehouses and its date from `JalaliDateInput` in ISO (`ReorderOrderFields`). The stock-issue reorder monitor (`reorderAlertForIssue` in `src/services/events/domainEventHandlers.ts`) compares the same free stock and carries it as `freeStock`. The reorder alert (`GET /items/reorder-alerts`, `listReorderAlerts` in `src/services/items/reorderAlerts.service.ts`) compares free stock — stock minus the reservations of `getReservedStocksMap`, whose read error refuses the request — with the reorder point; the deficit and «بی موجودی» come from free stock, and the quantity on open purchase documents (receipt or purchase in draft or proforma, `inTransitQuantities`) is only shown as «در راه».

- **Centralized Stock Movements:** All stock operations, warehouse locations, and WAC calculations MUST route through `DocumentService.applyStockMovement` in `src/services/document.service.ts` (item creation and opening stock included). Warehouse-to-warehouse transfers that must not change WAC move both rows through `ItemWarehouseStockService.applyMovement` and then rebuild the cache. Every transfer is a final `transfer` document (own number series through `DocumentRefNumberService.assignDocumentRefNumber`, one line at the source warehouse, both Kardex rows linked by `document_id`; source and destination are read from those rows by `transferLocationsByDocument`) and is voided only through `deleteDocument`, whose reversal of transfer rows moves quantity only (`applyStockReversal` with `quantityOnly`, the same rule in `replayKardexWac`); transfers recorded before v9.0.80 stay without a document.

- **Default Warehouse:** The default warehouse is the ACTIVE warehouse with the LOWEST id. Any query that picks a default/first warehouse MUST `orderBy(asc(warehouses.id))` (or use `getDefaultWarehouseCode` in `src/services/inventory/warehouseResolver.ts`); PostgreSQL row order without `ORDER BY` changes after updates. The Kardex location codes `''` and `default` always mean the default warehouse (`LEDGER_RESERVED_WAREHOUSE_CODES` in the same file), so a new warehouse with such a code is refused with 422 `WAREHOUSE_CODE_RESERVED`, a void's reversal of a row without a location writes the default warehouse's code, and a legacy warehouse with such a code is left unchanged and listed by the financial health check (`warehouse_reserved_code`).

- **Warehouse Deactivation:** Deactivating or reactivating a warehouse runs in one transaction with its audit row, under the transaction advisory lock `WAREHOUSE_ACTIVE_SET` (91010) and the warehouse row `FOR UPDATE`; every stock movement locks its active warehouse row `FOR KEY SHARE` in `ItemWarehouseStockService.applyMovement` (an inactive warehouse is 422 `WAREHOUSE_INACTIVE`), so the «no stock» check sees in-flight movements. The last active warehouse is never deactivated (422 `WAREHOUSE_LAST_ACTIVE`); only the system admin reactivates one (`POST /warehouses/:id/reactivate`, «انبارهای غیرفعال» in «مدیریت انبارها»), and creating an inactive warehouse's code again is 409 pointing to reactivation.

- **Stock Direction From the Document Type:** A document's stock direction comes only from its type (`DOCUMENT_STOCK_DIRECTIONS` / `documentStockDirection` in `src/lib/documents/documentDirection.ts`, shared by the server and the stock document page): receipt, purchase, production receipt and sales return move stock in; invoice, proforma, remittance and waste move it out; a stock count moves each line by its count. Create and finalize use it (`stockDirectionOf` in `src/services/documents/documentRecordRule.ts`), and every outgoing document recorded or finalized as final passes one sellable gate, `assertOutflowWithinSellable` (`src/services/documents/documentSellableGate.ts`): the quantities of each item and warehouse are summed and checked once against min(warehouse stock, total stock − other reservations), the reservation report is read for the document's items only and a report error refuses the document; the stock document page caps an exit with the same rule for its source warehouse (`itemReservationSummary` in `src/lib/documents/stockReservations.ts`); an `inOut` against the type is 422 `DOCUMENT_DIRECTION_MISMATCH` (`assertRecordableDocument`, checked by `POST /documents` before the permission and by `createDocumentWithDetails` for every caller), a transfer is never recorded there and a document of any other type or status is never recorded, with or without lines (`DOCUMENT_TYPE_NOT_RECORDABLE` / `DOCUMENT_STATUS_INVALID`; transfers only through `transfers.routes.ts`; the route accepts only recordable types). The database holds the same rules: `chk_documents_type` and `chk_documents_status` on a live document, and a live line's quantity, unit price and discount are never negative (`chk_document_items_*`; a stock count line may hold a counted zero, the services refuse a zero quantity on any other line); each constraint was added `NOT VALID` and validated only on clean data, a soft-deleted row is exempt, and the financial health check lists what is left (`document_integrity_constraints`, `src/services/documents/documentConstraintHealth.ts`).

- **Soft Delete & Reversal:** Never HARD DELETE stock transactions. Set `is_deleted = 1`, issue an atomic reversal transaction with `reversal_of_id`, and recalibrate balances via `DocumentService.applyStockMovement`. No business row is deleted physically; the exceptions are listed in `scripts/ratchets/HARD_DELETES.md` (§21).

- **Negative Stock Policy:** Negative stock is **always forbidden**. Reductions (`out`) must fail with `InsufficientStockError` before committing; the database constraint `chk_iws_current_stock_non_negative` on `item_warehouse_stocks` is the final safeguard. The legacy `warning` / `allowed` options are removed and must not be reintroduced without dropping that constraint in a new migration.

- **Event-Driven Verification:** Calculate true stock balances from sequential `stock_movements` log.

- **Three-Way Invariant:** `item_warehouse_stocks` (truth) = `items.current_stock` (database-maintained sum) = Kardex ledger balance (active rows, excluding reversals of soft-deleted rows). Kardex locations and legacy JSON keys map to warehouses with one rule (`createLedgerLocationResolver`: '' / 'default' = default warehouse, then code, then name, all warehouses). The Kardex rebuild refuses (never silently drops) items with movements in an unresolvable location or a negative per-warehouse balance.

- **Running Kardex Report:** The item Kardex report (`buildItemRunningKardex` in `src/services/inventory/runningKardex.service.ts`, `GET /inventory/item-kardex/:itemId`) lists rows in (day, id) order and shows a voided document's original row on its own date (`isVoided`, label «باطل‌شده») and its reversal on the void date (`isReversal`, «معکوس ابطال»); the running balance counts both, the in/out totals count only ledger rows, each row's WAC is the live engine's WAC right after that row was registered (`createKardexReplayer`), and warehouses are keyed with `createLedgerLocationResolver`. The stock movement chart (`getMonthlyMovementTrends`) counts the same ledger: `LEDGER_ROW_FILTER`, only `in` / `out` rows, no warehouse transfer, from the first day of the window to the end of the current Jalali month. The warehouse dashboard counts the same ledger (`src/services/inventory/dashboardMovementStats.ts`): «recent documents» are distinct documents of `LEDGER_ROW_FILTER` rows, fast-moving, slow-moving and dead stock read only ledger `out` rows without warehouse transfers, and «the last N days» are the business today and the N − 1 days before it. `GET /stats` and `GET /dashboard-bi-stats` are read by `src/services/inventory/warehouseDashboard.service.ts` and carry no reorder alarm list, low-stock count or user count; the page's reorder alarm reads `GET /items/reorder-alerts` (free stock).

- **Warehouse Stock Reconciliation:** `WarehouseStockReconciliationService` compares `item_warehouse_stocks` with the Kardex ledger (active rows, excluding reversals of soft-deleted rows). Repairs are manual only, dry-run by default, correct quantities only (never WAC), never auto-adjust negative ledger balances or items with unresolvable Kardex locations, and log every change/refusal to `inventory_reconciliation_anomalies`. Data-fixing migrations must never clamp or overwrite silently: add (`existing + EXCLUDED`) and record anomalies.
