# Server, Startup and Operations

Startup, base data, attachments on disk, errors and logs, health probes, backups and the single-instance deployment.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md` at commit `c3c9858` (archives removed in v11.1.0), and a «§N» below refers to that file's numbering.

- **Port 3000 Ingress:** `server.ts` MUST bind and listen on port 3000 immediately. Until migrations, seed and the engines finish, every `/api` request except `/api/health/*` and the WooCommerce webhook answers 503 `SYSTEM_STARTING` with `Retry-After` and `/health/ready` is 503 (`startupGate` in `src/middleware/startupGate.ts`, turned on only by `server.ts` with `beginStartup`); the browser shows a waiting page and resends the request (`fetchThroughStartup` in `src/lib/systemStarting.ts`, `SystemStartingOverlay`).

- **Background Seeding:** Seeding (`runSeed()`) must run asynchronously in background IIFE without blocking server startup. The boot runs its data steps through `runBootSequence` (`src/services/system/bootSequence.ts`, steps in `bootDataSteps`): only the migrations are essential and stop the process after their attempts; a non-essential step (base data, default engines, the time zone cache) that keeps failing is left out, the server starts and `/health/ready` / `/health/startup` name it in `degradedSteps`. `runSeed` names each failed section in `failedSections` with `success: false`, never a silent success; the factory reset answers 409 `FACTORY_RESET_SEED_INCOMPLETE` then.

- **Attachments on Disk:** Attachment files of documents, journal vouchers, cheques, treasury transactions, projects and payrolls live in `public/uploads/.attachments/` (never served by `/uploads`; `public/uploads` never enters `dist/`, the Docker image or a source package: `copyPublicAssets` in `scripts/publicAssets.ts`) and are registered in `file_attachments`; the JSONB `attachments` columns hold metadata and `/api/attachments/<id>` only — never Base64. Every save path passes incoming attachments through `AttachmentStorageService` (`attachToNewRecord` after insert, `normalizeForRecord` on update). Files are downloaded only via `GET /api/attachments/:id`, which requires the read permission of the owning record (`RECORD_READ_PERMISSIONS` in `src/lib/recordReadPermissions.ts`, also used by those records' read routes). In the browser, attachment images and downloads go through `AttachmentImage` / `downloadAttachment` (`src/lib/attachments/attachmentDisplay.ts`), which add the Bearer header when the token is held in memory. A stored file that cannot be read answers 404 (missing or not a file) or 500 `ATTACHMENT_READ_FAILED` and never stops the server (`openAttachmentFile` in `src/routes/attachments.routes.ts`). A JSON body is at most 5 MB, except the save routes of records with attachments (`acceptsAttachmentBody` in `src/lib/attachments/attachmentBodyLimit.ts`: 14 MB, for files of at most 10 MB, the same limit as the upload box); a larger body is 413 `PAYLOAD_TOO_LARGE` with a Persian message. An image field (`uploadBase64ToStorage` in `src/lib/storage.ts`) takes only a JPG, PNG, WEBP or GIF data URL of at most 3 MB; anything else is 422 `IMAGE_FORMAT_INVALID` / `IMAGE_TOO_LARGE` and is never stored as text. Such an image is served by `/uploads` only with a session; without one only the public asset folders and a legacy company logo file at the root (`logo-<uuid>.<image>`) are open (`isPublicUploadPath` in `src/lib/attachments/publicUploadPath.ts`, matched only on the decoded, normalized path: an encoded slash or backslash, a backslash or a `..` segment is 404), and the site root static handler of `public/`, mounted in `createApp`, refuses any path that decodes and normalizes into `/uploads` (`isUploadsRequestPath`).

- **Orphan Attachment Cleanup:** Files whose save transaction rolled back have no `file_attachments` row. Only the manual `npm run attachments:cleanup` / `POST /api/attachments/cleanup-orphans` (admin, dry-run by default, advisory lock 91005) removes them: `<uuid>.<ext>` files with no row at all, older than 60 minutes. A requested minimum age is never below 5 minutes (`MIN_ORPHAN_AGE_MINUTES`), so a file of a save still in progress is never removed. Files of attachments detached from their record (`is_deleted = 1`) are kept and only counted. The image files of `public/uploads` (names `<optional prefix->uuid.<jpg|png|webp|gif>` written by `uploadBase64ToStorage`, top level only) are handled only from «تصویرهای بی‌صاحب» of «عملیات سامانه» (`POST /api/system/orphan-uploads`, system admin, a preview unless `apply`, advisory lock `ORPHAN_UPLOADS_CLEANUP` 91042, never scheduled): a file is named while its UUID appears anywhere in a row of any base table of the current schema (the row read as text, so any address form, a soft-deleted or copied record, a setting, a draft or a queued event), only the audit log not read (nor bytea values or other schemas); a run acts only on the files of the preview the admin sent back, re-reads the rows for them just before acting (each table read once, kept only for the UUIDs at hand), never deletes a file outright: it moves an unnamed file older than 60 minutes to `public/uploads/.orphaned/<day>/` (never served, still in the backup; a quarantine or day folder that is not a real folder inside the uploads folder is 422 `ORPHAN_UPLOADS_QUARANTINE_INVALID`), removes a held file only after `ORPHAN_UPLOAD_HOLD_DAYS` (30) days and, on the next run after a row names it again, moves it back (a held copy whose same bytes are already back is removed; a different one is never overwritten); each chunk of at most 200 names writes its «تصویرهای بارگذاری‌شده» audit row inside the lock, moved and failed names apart (`cleanupOrphanUploads` in `src/services/system/orphanUploadsCleanup.service.ts`, rules in `src/lib/system/orphanUploads.ts`).

- **AppError Hierarchy:** Typed subclasses (`ValidationError`, `NotFoundError`, `UnauthorizedError`, `ConflictError`, `DatabaseError`). In production `errorHandler` keeps the `details` of a 4xx answer and hides only 5xx messages and details; body-parser errors get a Persian message and their own code (`BODY_PARSER_ERRORS` in `src/errors/customErrors.ts`, e.g. `INVALID_JSON_BODY` 400; the 413 keeps its TD-641 message). A database error that no rule names answers the code `DATABASE_ERROR` with no stack in every environment, with «خطای پایگاه‌داده در انجام درخواست رخ داد.» (`DATABASE_ERROR_MESSAGE`, `internal`) outside production and «خطای داخلی سرور» in production like every 5xx; the SQL and its parameters stay in the log files, and the log entry (`database`) and the terminal line carry the database's own reason (SQLSTATE, table, constraint and message, `logDetails`), never the answer.

- **AsyncHandler & Global Error Handler:** Routes wrapped in `asyncHandler` return uniform error schema with `traceId`. Every async route handler and every async middleware factory (`authorizePermission`, `validate`, `idempotency`) MUST go through `asyncHandler`; Express 5 also passes a rejected handler to the error handler, so `express-async-errors` was removed. Enforced by unit test `unit_route_async_handler_td_229`. Express 5 keeps the Express 4 request shapes through `src/lib/express5Compat.ts`: Express 4's qs query parser (`arrayLimit` 1000, `parseExpress4QueryString`), `req.body` `{}` when no parser ran, and the mount paths the route table reads (`recordMountPaths`, the app's own `use` only); `validate` sets the parsed query as the request's own property, a catch-all path is `/{*splat}`, the app page is sent relative to its root (`sendFile('index.html', { root })`), and a listen error such as a busy port exits the process with 1 (`listenCallback` in `src/lib/serverListen.ts`) (Vitest `express5RequestShapes.test.ts`).

- **Structured Logging:** Winston logger with daily rotation into `logs/application-%DATE%.log` and `logs/error-%DATE%.log`.

- **Recursive Sanitization:** Sensitive fields scrubbed with `[REDACTED]`.

- **Lifecycle Probes:** Kubernetes probes at `/health/live`, `/health/ready`, `/health/startup`. The system health page (`GET /system/health`, system admin) measures the event queue, voucher balance and workflow each on its own (`collectSubsystemMetrics`, contract `src/lib/system/subsystemHealth.ts`): a failed query is `status: 'unknown'` with null counts and a Persian message, never zeros and `ok`, and the page shows it as «نامعلوم». Its storage card checks the directories the app writes to, the attachment root (`getAttachmentsRoot`) and the image uploads (`getImageUploadsDir`), each with its path, by permission only: the directory, or its nearest existing parent, must be a writable directory, and the check creates and writes nothing. The event queue buttons replay the failed events or the events stuck in processing only after a confirmation («… دوباره اجرا شوند؟», «اجرای دوباره / انصراف») and are shown only when `outbox.dlqCount` / `outbox.stuckCount` is above zero; the stuck count uses the reset's own condition (`stuckOutboxCondition`). `/health` gives everyone only `version`; its `buildInfo` (commit and build time from `dist/build-info.json`, written by `npm run build`) goes only to the `METRICS_TOKEN` or a live system-admin session (`metricsReaderStatus`).

- **Prometheus Metrics:** System metrics exposed at `/metrics` and `/api/metrics`.

- **Graceful Shutdown:** Handles `SIGTERM`/`SIGINT` with a 10s force-exit timeout.

- **Backup, Restore and Upgrade Rehearsal:** `scripts/backup.sh` locates the app directory itself and reads `DATABASE_URL` / `ATTACHMENTS_DIR` from its `.env` (cron from any directory), writes the dump and a content manifest (`scripts/sql/backup-manifest.sql`: rows and content hash of every table, every constraint) from one exported snapshot, and archives `public/uploads` — attachment records without the attachment directory fail the backup. A failed run removes the partial files it wrote and a database before its first migration is backed up. Backups are private: the backup directory is `0700` and every file `0600` (`umask 077`), and `scripts/go-live-verify.sh` fails readable ones. `scripts/restore.sh` drill compares the restored database with that manifest; creating databases needs `RESTORE_ADMIN_URL` or `sudo -u postgres` (the install.sh role has no CREATEDB); `apply` never restores over the live database: it builds and verifies a new one, refuses while sessions are connected, swaps names and keeps `<db>_before_restore_<ts>` and the previous uploads directory. `update.sh` installs and builds the new version in the side folder `.build-next` (its `.env` and `.env.*` linked to the live ones, the upgrade rehearsal run from there; one run at a time under `flock` on `.update.lock`; free disk checked before the backup with the backup and, with `--rehearse`, twice the database counted; free RAM plus free swap checked before the backup and again before the build (`update_memory_check`, at least `UPDATE_MIN_MEMORY_MB`, default 2048: the build peaks near 1.5 GB), and a build or `npm ci` during which the kernel killed a process for lack of memory (`oom_kill` of `/proc/vmstat` grew) named as such with the swap file steps, never retried as a network failure (v11, Vitest `updateMemoryCheck.test.ts`); a source unchanged since `dist/` was built (`dist/.source-fingerprint`) skips build and swap unless `--rebuild`; a changed `update.sh` re-executes itself after the pull or sync) and swaps `dist/` and `node_modules/` in only right before the restart, keeping the previous ones as `dist.prev/` and `node_modules.prev/` until the next update, the swap ignoring HUP/INT/TERM and marked by `.update-swapping`, which makes the next run refuse and print the idempotent repair (`update_restore_build_command`); a manual update (`--source` / `--zip`) first keeps the current source in `.previous-source/`, then syncs the new one with `--delete --checksum`, the live state (`update_state_excludes` in `scripts/update-steps.sh`: `.env`, `.git`, logs, uploads, media library, backups, `node_modules`, `dist`, folders `.env` moves inside the app) neither copied nor deleted, and a source inside the application directory is refused; `bash scripts/update-steps.sh restore-source <app-dir>` puts that source back. `update.sh` reports success only when `/health/startup` answers on the `PORT` of `.env` and the running version is the built one (`scripts/verify-startup.sh`); a failed build puts the previous `dist/` back without restarting, and any failure after the source changed prints the rollback steps once. After the restart they follow what the run did to the database (v11, O2): `update.sh` counts the rows of `drizzle.__drizzle_migrations` newer than the newest migration of `dist.prev/` (`update_migrations_changed` in `scripts/update-steps.sh`, the condition `migrationPlan.ts` refuses, whoever applied them; when the database cannot be read, the migration journals of `dist/` and `dist.prev/`); with none the steps put the previous build and source back with no restore, otherwise they never offer the previous build on the migrated database (it refuses a database newer than itself, `migrationPlan.ts`) and give two choices: go forward (keep the database, wait for a corrected version) or go back completely with the pre-deployment backup, which erases later writes. The rollback step resets the branch to the previous commit (`git reset --hard <commit>`), never a detached checkout. `npm ci` (v11, O4) regenerates the lock file only on npm's own lock mismatch (EUSAGE) and never one git tracks (a released lock that does not match stops the update: a fault of the release), retries any other failure (`NPM_CI_ATTEMPTS`, default 3), never copies a lock into a checkout that tracks it, and before the pull puts back a tracked lock an earlier update changed when it is the only local change. Every shell script reads `.env` through the one reader `env_file_get` of `scripts/env-file.sh` (v11, O5): Node's own parser (`util.parseEnv`, the parser of `node --env-file`) when a node that has it is found, else a fallback with the same rules for one-line values (the last line of a key wins, `export` and leading spaces count, an unquoted value ends at `#`); `.env` is never run as shell code (Vitest `updateSafetyPhase3_3.test.ts`). The built server reads its migrations only from its own `dist/drizzle` (v11, O1, `resolveMigrationsFolder` in `src/db/migrator.ts`), never from the source `drizzle/` of its working directory, which update.sh replaces before the swap; tsx and the tests read the source `drizzle/`. The daily backup and the five-minute monitor run from one cron file written by `scripts/install-ops-cron.sh` (install.sh), every job through `bash` so a script whose executable bit a zip dropped still runs (v11, O3; a manual sync and install.sh also make the shell scripts executable again, `update_fix_exec_bits`, and git keeps every one at 100755); a daily backup is copied with the `.env` (and so `ERP_SECRETS_KEY`) only to an rclone `crypt` remote (`scripts/backup-offsite.sh`, `BACKUP_RCLONE_REMOTE`; a failed copy exits 3), and `scripts/monitor.sh` alerts on readiness, disk, backup age and the `erp_*` queue gauges of `/metrics` through a bot or SMTP, its Persian texts in `scripts/ops/monitor-messages.fa.txt` (`docs/OFFSITE_BACKUP.md`). The same cron file runs `scripts/nightly-verify.sh` each night at least 60 minutes after the backup: it restores the dump `.last_daily_ok` names into an `erp_restore_drill_*` copy after a free-space check, runs the financial health check and the business invariants on it (`scripts/nightly-verify.ts`, read-only, refused on any other database) and compares them with the last healthy night (`src/lib/system/nightlyVerify.ts`: only a count that got worse fails; a check the baseline lacks is listed as new; the same worse counts for `NIGHTLY_VERIFY_ACCEPT_AFTER_NIGHTS` (3) nights, or `--accept-baseline`, become the new normal); the same dump checked again after 12 hours is `no_new_backup`; it writes `logs/nightly-verify.json`, read by the «بررسی شبانهٔ پشتیبان» card and, since v10.3.24, by `scripts/monitor.sh`, which alerts on a failed, worse or 36-hour-old night (and, since v11 (O7), when `MEDIA_RCLONE_REMOTE` is set, on a failed or `MONITOR_BACKUP_MAX_AGE_HOURS`-old copy of the media library, read from `logs/media-offsite.json`; `scripts/restore-media.sh` brings the originals back from a crypt remote, never overwriting a file the server has), never touches the live database, keeps the password only in a private pgpass file and the environment, and a re-run of `install-ops-cron.sh` keeps the times the cron file holds. `update.sh --rehearse` / `scripts/upgrade-rehearsal.sh` run the new migrations on a restored copy first (`src/db/upgradeRehearsal.ts`, only on `erp_restore_drill_*` databases) and stop before the restart when they fail or change ledger totals per account, stock per item and warehouse, bank balances or the financial health check.

- **Operation Locks (v11, O13 / O18):** the operations scripts see each other only through two lock files of the application directory (`scripts/ops-lock.sh`), never through process names: `update.sh` holds `.update.lock` for its whole run, and every backup, restore and upgrade rehearsal holds a shared lock on `logs/.ops-busy.lock`. The nightly check skips its night while either is held; a daily backup that starts during an update lets its lock go and waits for the update (at most `BACKUP_UPDATE_WAIT_SECONDS`, 3600, then it runs anyway), because its pg_dump would hold up the migration of the restart; `update.sh` waits for a running backup, restore or rehearsal before it changes anything (at most `UPDATE_OPS_WAIT_SECONDS`, 1800, then it stops with nothing changed). The scripts' password file is not beaten by an exported `PGPASSWORD`: it becomes the file's last line for any server and leaves the environment (`pg_password_fold_env`, O14). A real restore unpacks the files into the folder it names whatever name the archive holds, says it kept a previous database only when one existed and lists every database earlier restores kept with its `dropdb` command (O15, O11).

- **Private Logs (v11, O16):** the server runs with umask 027 (`src/lib/processFileMode.ts`, imported before the logger): its log folder is 0750 (an older 0755 one is tightened at start) and its log files 0640, the console has no colour codes off a terminal (the journal), and `update.sh` makes log files an older version left readable by others private. The logs of `update.sh`, `install.sh` and `setup-domain.sh` are readable by their user only, and `update.sh` removes those older than 90 days.

- **Data Export:** `GET /api/export-backup` (system admin) streams a zip (`ZipStreamWriter` in `src/lib/zipStream.ts`, no extra dependency): one NDJSON file per table, read in primary-key batches of `DATA_EXPORT_BATCH_SIZE` rows with back-pressure (`DataExportService.writeExport`), and `manifest.json` with each table's row count; `activity_logs` only with `activityLogs=1` and a business-day range (`from` / `to`, both required, 400 otherwise; `dataExportQuerySchema`). The tables come from one list shared with the settings card (`DATA_EXPORT_TABLES` in `src/lib/system/dataExportTables.ts`, read by `DATA_EXPORT_TABLE_SOURCES` in `src/services/system/dataExportSources.ts`): every Drizzle table is exported, the optional `activity_logs`, or left out with a reason written to the manifest (`DATA_EXPORT_EXCLUDED_TABLES`), so a new table is classified in the same change (Vitest `dataExportTables.test.ts`), and the card lists the list's groups. It is never a restorable backup and carries no password hash, token state, Nobitex password, webhook signing key or secret setting. Every exported row passes `scrubExportRow` (`src/lib/system/exportSecretScrub.ts`): a secret-like key (password, secret, token, API key, authorization, cookie) holding text, at any depth of the row's JSON, and every header value under `headers` / `customHeaders` are written as «********», so a webhook rule's `actionConfigJson.secretToken` never leaves in clear.

- **Base Data at Boot:** The seed runs at every boot in every environment, production included (the old `ALLOW_SEED_IN_PRODUCTION` flag is retired and ignored), under advisory lock (`pg_try_advisory_lock(89345)`). It only inserts what is missing: each kind of base data (the categories of `DEFAULT_CATEGORIES` in `src/data/defaultCategories.ts`, default settings, piecework tasks, the standard chart of accounts) is inserted only into a database that holds none of that kind, and no existing row (role permissions, category, account, setting) is ever edited, so nothing an admin removed or changed comes back. It creates no role: a fresh install has only the system admin role (migration 0066), and every other role is made by the admin with «ساخت نقش از الگو» from `ROLE_TEMPLATES` (`src/lib/permissions/roleTemplates.ts`; a template only fills the role form, and its permission list is closed under `requires`); test schemas get the template roles from the test bootstrap. `GET /categories` only reads. The boot data steps live in `prepareDatabaseAtBoot` (`src/services/system/bootData.ts`); its default workflows, event rules and webhook subscriptions (`seedDefaultEngines`, each only when missing) also run after a factory reset, which wipes them and keeps the roles, and the reset card says so (`src/lib/system/factoryReset.ts`).

- **Database Mode Decided Once, Never a Silent Demo:** `resolveDatabaseMode` (`src/db/databaseMode.ts`) decides the process's database once: `SQL_HOST` with `SQL_USER` / `SQL_PASSWORD` / `SQL_DB_NAME`, else a real `DATABASE_URL` (not empty, not the `.env.example` placeholder). Anything else is refused: `server.ts` logs the reason and exits 1 before listening and every query rejects with it. PostgreSQL is the only database: v11 (phase 4.1) removed the in-memory demo database (`mockPool`, `ERP_DEMO_MODE=1`), and a leftover `ERP_DEMO_MODE=1` without a database is refused with `DEMO_MODE_REMOVED`, which says so. `/health/ready` reports `database: 'postgresql'`, and the test runner accepts only PostgreSQL.

- **The Boot Never Touches Passwords:** a stored password that is not a bcrypt hash never logs in and no boot step rewrites it. The one-off `npm run users:lock-plain-passwords` (`lockNonBcryptPasswords` in `src/services/users/plainPasswordLock.ts`) lists such users by the kind of value (a preview by default) and with `--apply` replaces each value, deleted users included, with `PLAIN_PASSWORD_LOCK_MARKER`, sets `must_reset_password = 1`, advances `token_version` and writes one audit row per user without the value, in one transaction under the user row locks; the system admin then gives the user a temporary password.

- **Single-Instance Deployment:** The system runs as ONE server process (one workshop, at most 20 concurrent users). In-memory caches, rate limiters and process-level locks assume a single process; do not add multi-replica infrastructure (Redis, object storage, cross-instance cache invalidation). The Kubernetes manifest (`deploy/k8s/erp-deployment.yaml`) is an unsupported example, not tested or kept in step with the app (no `ERP_SECRETS_KEY`, backup path or `securityContext`); the supported install is `install.sh` on one Linux server. Its image tag is a placeholder and it sets no `APP_VERSION`, so it is no version location. It keeps `replicas: 1` with `strategy: Recreate` and no autoscaler.

- **Business Clock Invariant:** Server-side dates must use `src/lib/businessClock.ts`.
