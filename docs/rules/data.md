# Data, Concurrency and Migrations

How data is written and locked, numbering, dates in storage, idempotency and optimistic locks, migrations and database settings.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md`, and a «§N» below refers to that file's numbering.

1. **NO WHOLE RAW SQL WRITE STATEMENT:** Never use `tx.execute(sql\`UPDATE ...\`)` or any other whole `UPDATE … SET` / `INSERT INTO` statement in SQL text for writes; write with `tx.update().set()` / `tx.insert()`. A `sql` fragment inside a Drizzle write for an atomic calculation (`set({ version: sql\`${t.version} + 1\` })`, `now()`) is allowed; cast a bound value whose type PostgreSQL cannot infer (`operator is not unique: unknown * unknown` in node-postgres). Guard: ratchet `rawSqlWrites` (v11 product-owner decision), which reads the SQL text written in place (`sql\`...\``, `.raw()`, `.query()`, `.execute()`) in the production files under `src`; SQL built in a variable is kept by review.

2. **Update Pattern (Read-Calculate-Update):** Always fetch row via `tx.select()`, compute mutations in TypeScript, and save via `tx.update().set()`.

3. **Row Locking:** For data updated within the same transaction, use `.for('update')` (NOT `.forUpdate()`).

4. **Explicit Text Casting for WHERE Queries:** For code columns (e.g. `project_code`), cast with `sql\`${table.projectCode} = ${String(code)}::text\``.

6. **Atomic Sequence Numbering:** Sequential numbers (vouchers, treasury transactions, document references, project codes — `assignProjectCode` in `src/services/projects/projectCode.ts`) MUST use PostgreSQL Sequences (`SELECT nextval('...')`) or atomic counter tables (`document_ref_counters` / `item_code_counters`, row lock or UPSERT), NEVER `COUNT(*)` or `MAX() + 1`. A sales invoice or sales return number comes only from the server series: `POST /documents` and `PUT /documents/:id` refuse another number with 422 `DOCUMENT_REF_SERVER_SERIES` (`assertManualRefAllowed` in `src/services/documents/documentRecordRule.ts`, rule shared in `src/lib/documents/documentRefRules.ts`) and the forms show the number read-only and send `auto`; any other document may take a manual number, but one already held in its type and fiscal year is 409 `DOCUMENT_REF_TAKEN` (`assertRefNumberFree` in `src/services/documents/documentRefNumber.service.ts`, never silently replaced), a manual number never moves the series counter, and the automatic number skips numbers already taken (`firstFreeSerial`). The forms send `auto` for the untouched suggested number (`refNumberToSend`), and the audit row and the response carry the stored number.

9. **Flag and Date CHECK Constraints (audit P3-14 / P3-15):** Integer `is_*` / `has_*` flags carry `chk_<table>_<column>_flag CHECK (col IN (0,1))`; text date columns carry `chk_<table>_<column>_datefmt CHECK (erp_date_text_ok(col, 'iso' | 'any'))` (migrations 0028 and 0030; `*_iso` columns are `iso`). A new flag or text date column gets the same constraint in its migration (regression tests `reg_flag_check_constraints_p3_14` / `reg_date_format_check_constraints_p3_15` fail otherwise). Constraints are added `NOT VALID` and validated only when existing data is clean — never rewrite old rows silently to satisfy them; a repair needs a product-owner decision and records every old value (TD-231: `legacy_date_repairs`, shown by the financial health check).

10. **Text Date Columns Store Gregorian ISO, Users See Jalali:** Every business text date column stores `YYYY-MM-DD` Gregorian (constraint kind `iso`); server timestamps kept as text (`treasury_transactions.reconciled_at`, `project_stages.completed_at`, `users.last_failed_login_at`) use kind `isots` (Gregorian date-time, never Jalali). `journal_vouchers.date` is `iso` too since v7.0.137 (migration 0044; vouchers in a closed fiscal year were left as they were and recorded as refused). Write paths normalize input with `requireStorageDate` / `optionalStorageDate` (`src/lib/storageDate.ts`, invalid date → 422); a document's date (`documents.date`, a Tehran wall-clock timestamp) goes through `requireDocumentTimestamp` / `resolveDocumentTimestamp` in the same file (a non-existent day or non-date → 422, empty → business now), its numbering year comes from that stored date, and a draft or proforma moved to another fiscal year takes that year's next number; query-string date filters use `storageDateParam` (`src/middleware/validate.ts`). The single converter is `src/utils/calendarDate.ts` (`toStorageDate`, `isoToJalaliDate`; SQL twin `erp_text_date_to_iso`). The browser shows dates with `formatPersianDate`, takes today from `getTodayJalaliDate` / `getTodayIsoDate` (display time zone, never `new Date().toISOString()`; the dashboard banner's date, clock and greeting come from `displayClockNow`), fills pickers with `isoToJalaliDate`, uses `JalaliDateInput` (`src/components/common/JalaliDateInput.tsx`) instead of `<input type="date">`, and compares dates as ISO. A "month" in payroll, work reports, treasury trends and the stock movement chart (`monthlyTrends` of `/dashboard-bi-stats`, `getMonthlyMovementTrends`) is the Jalali month. A new text date column gets kind `iso` from day one. Server timestamps (UTC, no zone) go to the browser with a `Z` (`serverTimestampToUtcIso` in `src/lib/serverTimestamp.ts`), and a day filter over them is the business time zone's day turned into a UTC range with `zonedDayRangeUtc` (activity log). The events routes (`utcTimestampResponses` in `src/middleware/utcTimestampResponses.ts` with `EVENT_TIMESTAMP_KEYS`), the notification list and the WooCommerce order log send their server timestamps the same way (`withUtcTimestampKeys` in `src/lib/serverTimestamp.ts`, also used by the workflow routes), leaving stored event payloads, metadata and rule configuration as stored (`EVENT_OPAQUE_KEYS`), and the notification bell prints its relative time from UTC with Persian digits (`notificationRelativeTime`).

- **PostgreSQL Atomic Sequences:** Sequence IDs generated via `nextval('...')` or the `document_ref_counters` / `item_code_counters` counter tables.

- **Idempotency OCC Locks:** `IdempotencyService` uses `.onConflictDoNothing()` and OCC (`status` and `locked_until` in UPDATE WHERE clause).

- **Idempotency Key Contract:** The `idempotency` middleware stores only 2xx responses and releases the key on any other status (`releaseKey`), both before the response is sent; a key recorded for another method, path or body gets 422 `IDEMPOTENCY_KEY_REUSED` and is not executed; the key's lock is extended every third of its window while the request runs (`extendLock`). The browser derives the key from the submission's content (`submissionKeyFor` in `src/lib/submissionKey.ts`), keeps it until a definitive response (network errors, aborts and 502/503/504 keep it), never mutates the caller's options, and waits on 409 `IDEMPOTENCY_IN_FLIGHT` with the same key. After a network error only a GET is resent automatically; a POST / PUT / PATCH / DELETE is sent once and reports `UNCONFIRMED_MUTATION_MESSAGE` (check the result, then resend with the same key). When the waits on `IDEMPOTENCY_IN_FLIGHT` run out the key is kept too and the error is `IN_FLIGHT_STILL_RUNNING_MESSAGE`. A key keeps only the SHA-256 fingerprint of its request body (`requestFingerprint` in `src/services/idempotency.service.ts`; a key recorded before keeps its body and is still compared on it), and no answer of the `payroll` / `piecework` scopes or larger than `IDEMPOTENCY_RESPONSE_MAX_BYTES` (64 KB): a repeat of such a request runs nothing and gets the stored status with `IDEMPOTENCY_REPLAY_BODY` (`keptResponseBody` in `src/middleware/idempotency.ts`); a running request's lock is renewed until it answers, up to the key's lifetime; the browser keeps one key for a form with files (`FormData`, a file, URL parameters) as for a JSON body, from the field text and each file's name, size, type and last change; and a request without a key (a client outside the browser) passes the guard unchecked. The purge (`cleanupExpired`) keeps a `processing` key whose lock is still live, and a takeover of a timed-out key gives it a fresh lifetime, so a request still running past its key's expiry is not run a second time by a resend (#351 review I1). A screen that reads a field of a `payroll` / `piecework` answer checks `isIdempotentReplay` (`src/lib/idempotentReplay.ts`, the notice text the middleware sends too) and shows the notice and reloads instead (payslip and eidi issue, voucher sync, task import), and the schedule tab reads the log ids of a repeated log request from the saved plan (`scheduleLogIdOf`) (#351 review L1); an answer of any other scope over 64 KB is replaced by the same notice, so a screen that reads a large write answer handles it the same way (#351 review L2). A payroll or piecework write opens its own transaction with `idempotentTransaction` (`src/middleware/idempotency.ts`, shared kernel; the payslip, payment, void, eidi, statutory and eidi rate, draft edit and voucher services and `inTransaction` / `inWriteTransaction` of `piecework.service.ts`): inside a request of those scopes the middleware puts the key in the request context and the write completes it in the same commit with the notice, so a process that dies after the commit and before the answer no longer leaves a `processing` key that a resend takes over once its lock lapses and pays again; a service answer `{ error }` does not complete it, a failure after a committed write keeps it, and a new write of those scopes uses `idempotentTransaction`, not `orm.transaction`. Since 10.3 the middleware puts the key of every scope in the request context, and every money and stock write opens its transaction the same way (treasury, cheques, bank accounts, vouchers, chart of accounts, fiscal closing, documents and the document routes' own transactions, stock transfers and allocations, items, warehouses, raw material requests, procurement, projects and the workshop routes; `idempotentTransactionOn(executor, fn)` for a service that may also run inside a caller's transaction, where it is a savepoint that completes nothing), so a crash after the commit of a receipt, voucher, document or stock movement no longer records it twice on a resend, which gets the notice (status 200 with `IDEMPOTENCY_REPLAY_BODY`) instead of the first answer, as does a resend in the moment between the commit and the kept answer; the modules are `MONEY_STOCK_WRITE_MODULES` plus every route file that runs `idempotency()`, and a plain `orm.transaction` there is one of `PLAIN_TRANSACTION_WRITES` with its reason (`src/tests/security/resubmissionPolicy.ts`; a repair or rebuild that runs one transaction per row and finds its work done on a resend, item categories outside the money routes, the WooCommerce order sync under its locked order-log row and the shop pushes of absolute quantities and prices), test `sec_money_stock_writes_complete_key_in_tx`. The browser keeps each key still waiting for its answer in the tab's `sessionStorage` too (`SUBMISSION_KEYS_STORAGE_KEY` in `src/lib/submissionKey.ts`, under a hash of the method, path and body, never the body), so a resend after a reload carries the same key; and `fetchJson` turns a write answered with the notice into `ApiError` code `IDEMPOTENT_REPLAY` with the notice text, holds its key for half an hour after each notice (`holdReplayedSubmissionKey`: a form left open gets the notice again on the next click, never a second record, and a later identical write such as approving a payslip again is a new one) and sends `SUBMISSION_REPLAYED_EVENT` (every open query is read again, and a mutation hook shows the notice as information), unless the caller passes `acceptReplay` and checks `isIdempotentReplay` itself, as the payslip, eidi, voucher sync, task import and schedule log screens do. Every writer route (POST / PUT / PATCH / DELETE) behind the login in the money and stock sections (accounting, documents, inventory, items, raw material requests, piecework, procurement, projects, transfers, warehouses, WooCommerce, workshop) runs `idempotency()`, so a double click or a resend of one submission records once and the second send gets the first answer; only routes that write nothing are exempt, listed with their reason in `RESUBMISSION_EXEMPT_ROUTES` (`src/tests/security/resubmissionPolicy.ts`, the written resubmission rule; the route table carries `idempotent`, test `sec_money_stock_routes_idempotent_obs_r2_14`), and a new writer route there takes the middleware in the same change.

- **Customer Optimistic Lock:** `PUT /customers/:id` requires the record's `version` (400 without it) and writes with the version in its WHERE (409 `OCC_CONFLICT` when stale or changed meanwhile); the customer Excel export carries «نسخه» and an imported row with an `id` is applied only at the current version, otherwise listed in the import errors. A sales lead never changes an existing customer: creating, editing or converting a lead only links a customer (id, then exact phone, then exact name) or creates a new one (`linkCustomerForLead` in `src/services/crm/crmCustomerLink.ts`), and a differing phone or company name goes only into the lead's notes. Two active customers never share a name: the key is `lower(btrim(name))`, checked by `assertCustomerNameAvailable` (`src/services/customers/customerIdentity.ts`) and enforced by the partial unique index `uq_customers_name_active` (migration 0052, created only on data without duplicates; the financial health check lists duplicates as `customer_name_uniqueness`); an index violation is the same Persian duplicate-name error. In the customer Excel import an empty party-type cell leaves an existing party's type unchanged and makes a new party a customer; the cell is read only through `parsePartyTypeCell` (`src/lib/customers/partyTypeCell.ts`, shared by the server and the preview). A party is never deleted while it has open business: `deleteCustomer` locks the customer row and `assertCustomerDeletable` (`src/services/customers/customerDeleteGuard.ts`) refuses with 409 and Persian reasons a nonzero approved/permanent balance in any currency, draft voucher rows (both by `partyDetailedRowsCondition`), a draft or proforma document of the party (`documentPartyCondition`: its `party_id`, or a legacy document without one whose trimmed buyer name equals the party name), an active lead, a project not completed or cancelled, or a cheque in a status that still has a next step in `CHEQUE_TRANSITIONS`. A party's website, e-mail and Instagram username (`customers.website` / `email` / `instagram`, migration 0112) and each contact person's e-mail are checked and normalized by one rule shared by the server, the form and the Excel preview (`src/lib/customers/contactChannels.ts`: a website gets `https://`, Instagram is stored as the bare username): a wrong value is 422 `CUSTOMER_CONTACT_CHANNEL_INVALID` before any write (`resolveContactChannels` in `src/services/customer.service.ts`) and an import row error, a field not sent keeps its value and an empty import cell leaves it unchanged; the list, dossier and contacts show call and WhatsApp links (`whatsappLink`, the TD-296 phone key) and mail and page links (`ContactLinks.tsx`).

- **Stock Soft Delete & Reversal:** `is_deleted = 1` + reversal transaction + balance recalculation.

- **Negative Stock Guard:** Inventory deductions below zero are rejected (policy fixed to `forbidden`, enforced in `ItemWarehouseStockService.applyMovement` and by the DB CHECK constraint).

- **No Second Pool Connection Inside a Transaction:** Code running inside a transaction uses that `tx` only — never `orm` / `pool` (with a full pool it waits for the connection timeout). Pass `tx` to `logActivity` (an insert error then propagates instead of turning COMMIT into a silent ROLLBACK), `FiscalPeriodService`, `startInstance` and `maybeStartWorkflow` (both run inside a savepoint of that `tx`; default workflows are seeded only at startup, only when their code is missing, and never overwritten — v9.0.46). `maybeStartWorkflow` returns null only when the entity type has no active definition; any start error propagates and rejects the caller's operation, never read as «no workflow». `getDisplayTimezone` serves a stale cache without waiting and is warmed outside transactions (`warmDisplayTimezone`).

- **Stock Item Locks:** Every stock path (document create / finalize / void, sales return, transfer, BOM allocation, project delivery) locks ALL its items at once, in ascending id order, with `FOR NO KEY UPDATE` (`lockStockItems` in `src/services/inventory/stockItemLocks.ts`, or `withOrderedLocks`, which uses the same mode for items) BEFORE the document counter, the document row or any Kardex / line insert; a void locks items → project → document. Never lock an item row `FOR UPDATE` in these paths: inserting a Kardex row or document line takes a `FOR KEY SHARE` foreign-key lock on the item, which conflicts with `FOR UPDATE` and deadlocks concurrent voids. `withOrderedLocks` sorts by `LOCK_ORDER_MAP` in every environment and refuses a table without a lock level.

- **Atomic Migrations:** `src/db/migrator.ts` runs the official Drizzle migrator over `drizzle/*.sql` (journal: `drizzle/meta/_journal.json`) in an atomic transaction; applied migrations are tracked in `drizzle.__drizzle_migrations`. Every new migration MUST be registered in the journal. `runMigrations()` never throws: every caller MUST check `result.success` and stop on failure (TD-217 — `setupTestSchema`, `ensureTestDatabaseReady`/`assertTestDatabaseReady`, `runSeed`, `server.ts`).

- **Migrations Name Their Schema:** A migration never drops a schema object by a bare name with `IF EXISTS`; it names the current schema (`EXECUTE format('DROP INDEX IF EXISTS %I.<name>', current_schema())`), because an isolated test schema runs the migrations with the search path `"<test schema>", public` and a bare name missing there dropped the object of the same name in `public`. An existence check restricts its own schema too: a catalog lookup carries its schema column or table (`connamespace = current_schema()::regnamespace`, `schemaname = current_schema()`, `table_schema = current_schema()`, `conrelid` / `tgrelid = '<table>'::regclass`) and `to_regclass` takes `format('%I.%I', current_schema(), '<name>')`, because the catalogs hold every schema and a bare check found the object in `public` or another test schema and skipped it. Vitest `migrationSchemaQualified.test.ts` (scanner `src/tests/setup/migrationSchemaQualification.ts`) fails on such a statement.

- **Conditional Constraints Are Reported and Built by Hand:** A migration that leaves a constraint or index out on unclean data says so with `RAISE WARNING` (or a notice saying `SKIPPED`, `not created` or `left NOT VALID`); `runMigrations` listens to the notices of its connection and returns them in `warnings` and the log (`migrationNoticeWarning` in `src/db/migrationNotices.ts`). The FKs and unique indexes of 0001, 0012 and 0015 that are missing from the current schema are listed by the financial health check with their cause (`conditional_constraints_missing`, `CONDITIONAL_CONSTRAINT_RULES` in `src/services/system/conditionalConstraints.ts`), and the system admin builds them once the data is clean from «عملیات سامانه» (`GET /system/conditional-constraints`, `POST /system/conditional-constraints/build`: a preview unless `apply: true`, advisory lock `CONDITIONAL_CONSTRAINTS` 91040, one savepoint per constraint, audited with `tx`); data is never fixed automatically. A new conditional constraint without a health check of its own goes into that list.

- **Migration Journal and Session:** A new migration's journal `when` is greater than every earlier entry — the Drizzle migrator applies only entries newer than the database's last applied one and skips an older `when` silently. `runMigrations` compares the journal with `__drizzle_migrations` first (`planMigrations` in `src/db/migrationPlan.ts`) and refuses a skipped migration or a database newer than the build; Vitest `migrationPlan.test.ts` lints the journal (strictly increasing `when`, tag = idx, every `.sql` registered). Migrations run on one dedicated connection without the request statement timeout (`MIGRATION_STATEMENT_TIMEOUT`, default 0) under advisory lock 91008, so two runs queue instead of failing; a run waits at most `MIGRATION_LOCK_TIMEOUT` (default `10min`) for that lock and then stops with a clear error.

- **Released Migrations Stay as Released:** A migration file changes after release only to remove an upgrade blocker for databases that have not run it, or to name the current schema where it named an object without one; its previous sha256 goes into `AMENDED_MIGRATIONS` (`src/db/migrationAmendments.ts`) so databases that ran the old text get no hash warning. A data `UPDATE` in a migration runs through `erp_update_with_unvalidated_checks(table, sql)` (0047) when the table can hold NOT VALID CHECK constraints: they are dropped for the statement and re-added exactly as they were, because a NOT VALID CHECK still applies to every updated row and one refused legacy row would roll back the whole upgrade.

- **Foreign Keys of the Schema:** every reference declared with `references()` in the Drizzle schema has a database foreign key, except the columns listed with their reason in `FOREIGN_KEY_EXCEPTIONS` (`src/db/foreignKeyPolicy.ts`: step and action ids of an instance's own snapshot, the workflow engine's user ids, the TD-085 repair record). The regression test `reg_foreign_key_inventory_td_612` compares the schema with the migrated database; its list of references still without a constraint only shrinks, and a new reference gets its constraint in its own migration or an exception with its reason in the same change. A reader of a workflow step title uses the instance's snapshot (`snapshotStateTitles`), never the live step table, whose ids change on every design save. A new foreign key carries the `onDelete` its Drizzle declaration names, is added `NOT VALID`, is validated in its migration only when no row breaks it, and is registered with `addedNotValid` in `CONDITIONAL_CONSTRAINT_RULES` (`src/services/system/conditionalConstraints.ts`), so the health check lists it until the system admin validates it after fixing the data; old rows are never rewritten (TD-611: `fk_webhook_deliveries_subscription` CASCADE, `fk_event_action_logs_rule` SET NULL). Deleting a webhook subscription or a rule (`src/services/events/integrationParentDelete.ts`) runs in one transaction under the parent row lock (404 when missing), cancels its queued delivery jobs and writes one audit row with `tx`. The user columns declared as references to users have their foreign keys (migration 0091: `form_drafts.user_id` CASCADE, the other fifteen NO ACTION); users are only soft-deleted, and code that hard-deletes a user (the factory reset, test cleanup) removes or clears the referencing rows first. The thirty references between business tables have their foreign keys too, NO ACTION as declared (migration 0092); their parents are only soft-deleted, and a new declared reference gets its key in its own migration (`reg_foreign_key_inventory_td_612` refuses a declared reference without one). The Drizzle schema says what the migrations build: each foreign key's `onDelete`, each column's nullability, each index by name (a unique index or NOT NULL a migration builds only on clean data included) and each unique constraint; `reg_schema_drift_td_613` refuses any difference, so a migration that adds or changes one of them changes the Drizzle declaration in the same change. A NOT NULL left out over NULL rows is the conditional kind `not_null` (migration 0093: four `project_product_stage_progress` columns). Every foreign key column has an index that leads with it (migration 0094), partial on `<column> IS NOT NULL` for a nullable column; `reg_foreign_key_indexes_td_614` refuses a new foreign key or declared reference whose column has none.

- **Session-Level Timeouts:** `statement_timeout = 60000` ms and `idle_in_transaction_session_timeout = 60000` ms (defaults of `DB_STATEMENT_TIMEOUT` / `DB_IDLE_IN_TX_TIMEOUT`), sent in the pool's connection startup `options`. A bulk task extends the statement timeout of its own transaction with `extendStatementTimeout(tx)` (`src/db/drizzle.ts`, `SET LOCAL`, 5 minutes), never on another pool connection. The same `options` pin the session `TimeZone=UTC`, and `src/lib/processTimezone.ts` (the first import of `server.ts` and the test runner) sets the process `TZ=UTC`, so server timestamps (`defaultNow()`, `toISOString()`, stored without a zone) are UTC on every host; business «today» still comes only from `businessClock`.

- **Data-Safety Invariant:** Test cleanup gated on `NODE_ENV ∈ {test,development}` AND `ERP_ALLOW_TEST_CLEANUP=1`, scoped to synthetic test IDs only. `npm run db:cleanup-test` checks both before connecting, previews by default (rolled back) and deletes only with `--force`, and then only `ERP-TEST-MARKER` rows nothing else refers to; it never touches Kardex, treasury, users, audit logs, counters or sequences. `db:push` is BANNED; migrations come exclusively from the atomic migrator. `drizzle.config.ts` refuses every drizzle-kit command except `studio`, `check` and `export`, which only prints the schema's SQL (`drizzleKitCommandRefusal` in `scripts/drizzleKitGuard.ts`; `export` since v10.1.66).
