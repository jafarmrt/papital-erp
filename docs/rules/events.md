# Events, Outbox and Webhooks

Domain events, the outbox, deliveries, dead letters, webhooks and automatic rule actions.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md` at commit `c3c9858` (archives removed in v11.1.0), and a «§N» below refers to that file's numbering.

- **Event Catalog:** Domain events follow `BaseDomainEvent` contract (`eventId`, `eventType`, `aggregateType`, `aggregateId`, `payload`, `metadata`, `occurredAt`). A sales or purchase document event (`InvoiceCreated` / `InvoiceApproved` / `PurchaseCreated` / `PurchaseApproved`, on create and on finalize) carries the stored document's payable amount from `documentEventAmounts` (`src/services/documents/documentEventAmount.ts`, in the event's transaction): `totalAmount` in the document currency (net of active lines + VAT + service charge), `netAmount`, `vatAmount`, `serviceChargeAmount` and `totalAmountIrr` (null for a foreign document without a rate); the rule editor's field list (`src/lib/eventPayloadFields.ts`) follows the real payload of each published type. Voiding a sales invoice or proforma writes `InvoiceVoided` with the same amounts in the void transaction (`recordVoidEvents` in `src/services/documents/voidDependents.ts`), and each reversed Kardex row of a void, transfers aside, writes `StockReceived` / `StockIssued` (`applyStockReversal`), so an item's stock events add up to its stock A sales document recorded final directly writes `InvoiceCreated` before `InvoiceApproved`, like a proforma finalized later (same decision). A cheque status change writes `ChequeStatusChanged` (aggregate `Cheque`: old and new status, the party's type and id, the vouchers of the step, never the amount or the party's name since v10.3.20; migration 0135 removed them, and the treasury amount, description, reason and remaining balance, from the outbox, dead-letter and delivery-job rows written before, and the financial health check lists a rule that still reads them, `event_rule_cheque_private_fields`) after its audit row, a payslip's approval `PayrollApproved` and each payslip payment `PayrollPaid` (aggregate `Payroll`, with the payment's treasury row and whether it settled the payslip, never the personnel's name or an amount, which stay behind the payroll read keys; `recordPayrollEvent` in `src/services/piecework/payrollEvents.ts`), each in the change's own transaction, so rules and webhooks can react to them. A payment's void writes `PayrollPaymentVoided` and a payslip's delete `PayrollDeleted` the same way, and the `TreasuryTransactionApproved` of a payslip payment or of its void carries only the treasury row, its bank and the payslip, never an amount, the remaining balance, the employee's name or the free text that holds them (`payrollTreasuryEventPayload`, same file).

- **DomainEventBus:** Central singleton dispatcher (`src/services/events/domainEventBus.ts`) with non-blocking handlers. The live bus keeps only its newest `LIVE_EVENT_BUFFER_SIZE` (200) events in memory and its tab reads them all; the outbox, the rule execution log and the dead letters are read one page of 50 at a time with their total (`ListPager`), the outbox searched on the server (`outboxSearchCondition` in `src/services/events/outboxSearch.ts`: id, type, aggregate, error, payload text and the Persian type and aggregate names), and a filter or search starts again from page 1; the timeline's entity picker reads at most `AGGREGATE_SEARCH_MAX_LIMIT` (50) rows. An event recorded during a request carries that request's `requestId` and `correlationId` in its metadata, and a dispatch without a request (the outbox worker) runs its handlers under them (`eventRequestContext`), so the audit rows they write carry the origin trace id. «پردازش اکنون» (`POST /events/outbox/process-now`) drains the outbox outside the pressing request (`processPendingBatchAsWorker`), so each event's handlers carry that event's own ids, never the administrator's. The stock-issue reorder alert is written to the outbox once per stock event (`recordReorderAlertOfIssue` in `src/services/events/domainEventHandlers.ts`, id `<stock event id>_reorder`, `OutboxService.recordEventOnce`), never only published in process.

- **Transactional Outbox:** Write events atomically inside `tx` via `OutboxService.recordEvent(tx, event)`. `OperationalPurgeService` (`src/services/events/operationalPurge.service.ts`, started by `server.ts`, advisory lock 91100) deletes daily the expired idempotency keys and the completed events processed more than `OUTBOX_COMPLETED_RETENTION_DAYS` (90) days ago, in batches of `OPERATIONAL_PURGE_BATCH_SIZE` (`src/lib/batchDelete.ts`), never one whose dead-letter row is not yet replayed and never a dead-letter row, so the event timeline shows outbox events of the last 90 days only.

- **Exponential Backoff Worker:** Polls pending events, dispatches, retries (5s, 10s, 20s... max 5 attempts).

- **Tracked Dispatch:** `publish()` stays fire-and-forget (non-blocking, errors only logged). The outbox worker and DLQ replay MUST use `domainEventBus.dispatchTracked(event, completedHandlers)`, which awaits every handler and reports failures. Every handler is registered with a stable name (`subscribe(type, fn, name)`) and MUST rethrow its errors after logging; succeeded handler names are persisted in `outbox_events.completed_handlers` so retries never re-run a handler that already succeeded.

- **Durable Integration Deliveries:** Each delivery of an event to an integration has its own row in `integration_delivery_jobs` (migration 0086): a webhook subscription × event (`webhook`, at most the subscription's retry limit, a whole number from 1 to 10, default 3; the form keeps a stored value with `??`) and a matching rule's action × event (`rule_action`, `RULE_ACTION_MAX_ATTEMPTS` 5), unique per (kind, target, event), so a delivery that succeeded is never sent again. The outbox handlers only record these rows (their error goes back to the outbox); the first attempt runs at once (a rule's awaited, a webhook's not) and `IntegrationDeliveryService` (`src/services/events/integrationDelivery.service.ts`, worker started by `server.ts`) retries a failed one after `deliveryBackoffSeconds` (5, 10, 20 … at most 300 s). After the cap, or at once for a key the server cannot decrypt, the row is `failed` and moved to the DLQ on its own row (`<eventId>#webhook:<id>` / `#rule:<id>`, source `webhook` / `action_engine`, `metadata.deliveryJobId`); its replay runs only that delivery and the requeue puts it back in its own queue, not the outbox. A deleted or inactive subscription or rule closes the row (`cancelled`). One delivery keeps one `X-ERP-Delivery-Id` (`whd_<job id>`) across its attempts; never retry with in-memory timers. A rule's `execution_count` and a subscription's delivery counters are read under the row's lock (`FOR UPDATE`, taken before the log row is inserted) and written in the transaction of the attempt's log row.

- **Dead Letter Queue (DLQ):** Failed events transfer to `dead_letter_queue` with replay/dismiss endpoints. Replay and dismiss of one DLQ row run under that row's session advisory lock (`withDeadLetterRowLock`, `withRowAdvisoryLock` namespace 91007; never an open transaction around the handlers): a concurrent replay or dismiss is refused (409) and the outbox requeue skips a row being replayed. A replayed event is never replayed or dismissed again; a dismissed one may be replayed.

- **Automated Event Actions:** `EventActionEngineService` runs a rule's action: an in-app notification, a webhook or an audit-log row (`RULE_ACTION_TYPES` in `src/lib/events/ruleActionTypes.ts`, shared with the rule editor). The fake `workflow_trigger` and `sms_simulation` actions are removed: a rule is never created, activated or switched to them (422 `RULE_ACTION_TYPE_RETIRED`, `assertRuleActionTypeAllowed`); migration 0085 deactivated the earlier rules of those types and recorded them in `event_action_rule_retirements`, and the financial health check lists them (`event_rule_retired_action`) until their action changes. `POST /events/action-rules/test-draft` really evaluates a draft (`evaluateRuleDraft` in `src/services/events/ruleDraftEvaluation.ts`): an unknown event type or action type, an invalid condition or an incomplete action is 422 `RULE_DRAFT_INVALID`, otherwise the conditions are evaluated on the sample event (`ruleSampleEvent`) and what the action would do is only shown; nothing is sent or written. The rule execution log and the engine stats have one contract shared by the server and the «اقدام‌های خودکار» tab (`src/lib/events/actionLogContract.ts`: `GET /events/action-logs` answers `{ data, total, limit, offset }`, `GET /events/action-rules/stats` `logsTotal` / `avgLatencyMs` …).

- **HMAC-SHA256 Signatures:** Webhooks sign payload with HMAC-SHA256 and attach `X-ERP-Signature-256` and `X-ERP-Delivery-Id`.

- **Webhook SSRF Guard and Echo Simulator:** every outgoing webhook request, the connection test included (`pingTest`), uses `redirect: 'manual'` and refuses a 3xx; the echo-simulator exception of `assertSafeExternalUrl` holds only through `isLocalEchoTarget` (`src/lib/ssrfGuard.ts`): `NODE_ENV` test or development, a loopback host, this server's own `PORT` and the exact path `LOCAL_ECHO_PATH`; in production the simulator is unreachable. A host name is checked on both its A and AAAA records and every address it resolves to, each lookup waiting at most `DNS_LOOKUP_TIMEOUT_MS` (3 s, `withDnsTimeout`); an explicit port is 80, 443 or an unprivileged port outside `DISALLOWED_PORTS` (`isAllowedTargetPort`); and a name that does not resolve is accepted only under example.com in test and development (`isUnresolvedTestHost`), never by a substring; a test lets its in-process stand-in of a partner site through only by its exact loopback origin with `allowTestLoopbackOrigin`, only under `NODE_ENV` test. A webhook delivery, its ping and a rule's webhook action are sent only through `guardedWebhookFetch` (`src/services/events/guardedWebhookFetch.ts`, Node's http / https by hand, no library): the socket resolves the name with `guardedDnsLookup` (`src/lib/ssrfGuard.ts`), so a name that answers an inside address when it connects (DNS rebinding) is refused before anything is sent, a redirect is never followed and comes back as the 3xx the caller records as a failure, the answer body is cut at `WEBHOOK_RESPONSE_MAX_BYTES`, and the request keeps `Accept: */*` and a `User-Agent` (the caller's, else `Papital-ERP`, without the version since v10.3.20) as `fetch` sent them (`webhookRequestHeaders`); only the echo simulator and a test's own loopback origin connect without the check, and tests replace the network only with `setWebhookTransportForTests`.

- **No Rule Rewriting at Start:** `seedDefaultRules` only seeds an empty rule table and never reads or rewrites saved rules; its echo-simulator webhook rule is seeded only in test and development (`isEchoSimulatorEnvironment`). The system's echo token (`ERP_WEBHOOK_SECRET_TOKEN` / `erp_webhook_secret_token`) is sent as `X-ERP-Signature-Token` only to `isLocalEchoTarget`; a rule holding it sends no token to another address (`systemTokenWithheld` in the result).

- **Masked Webhook Key Never Stored:** a webhook edit changes the signing key only for an entered key (`isEnteredSecret` in `src/lib/secrets/maskedSecret.ts`: not empty and not a mask such as «********» or «****…abcd»), so the masked key a form holds is never saved. `POST /webhooks/ping` with `subscriptionId` signs with the stored key and sends the stored custom headers only to the stored address; a draft ping without an entered key is signed with a one-time `generateSecretKey()`, never a fixed key (`keySource` in the answer).

- **Server-Made Webhook Key and Timeout:** the browser never makes a webhook signing key; a webhook created without an entered key gets `WebhookSubscriptionService.generateSecretKey()` (`crypto.randomBytes`). Its timeout is `timeoutMs` (legacy `timeoutSeconds` × 1000) through `resolveWebhookTimeoutMs` (`src/lib/events/webhookTimeout.ts`, shared with the form), from 1,000 to 30,000 ms on create and edit (else 422 `WEBHOOK_TIMEOUT_INVALID`).

- **Webhook Event Patterns Are Published Types:** the event types the server publishes are listed once, with Persian labels, in `PUBLISHED_EVENT_TYPES` (`src/lib/events/eventTypeCatalog.ts`, shared by the server and the webhook form; Vitest `eventTypeCatalog.test.ts` compares it with every `createEvent` / `publishEvent` call, so a new event type is added there in the same change). A subscription's patterns are «*» or such types (`resolveEventPatterns` in `src/services/events/webhookEventPatterns.ts`; create, edit and activation refuse another with 422 `WEBHOOK_EVENT_PATTERN_UNKNOWN`). Migration 0088 converted stored dotted patterns with a mapping table, recorded each old list in `webhook_event_pattern_repairs` and deactivated a subscription left without a pattern or addressed to an example.com / .org / .net host; no webhook subscription is seeded. A rule's trigger event follows the same list: the rule editor offers only these types and «همه رویدادها»; `assertRuleEventTypeAllowed` (`src/services/events/ruleActionTypeGuard.ts`) refuses another type on create, on a switch, on activation and when an active rule is saved (422 `RULE_EVENT_TYPE_UNKNOWN`; an inactive legacy rule stays editable), the draft evaluation reads the same list, and stored rules of such types are only listed by the financial health check (`event_rule_unpublished_event_type`).

- **Webhook Secrets Masked in Every Answer:** every answer that carries a webhook subscription or an action rule goes through `webhookSubscriptionView` / `actionRuleView` (`src/services/events/integrationSecrets.ts`): the signing key, custom header values, rule `secretToken` and rule header values are «********» for every user, the system admin included; the key is shown once, in the create answer and `POST /webhooks/:id/rotate-secret` (`events.manage`, audited). On save «********» keeps the stored value only for the stored address (`resolveMaskedHeaders` / `resolveRuleConfigSecrets`; another address is 422 `INTEGRATION_SECRET_REENTRY_REQUIRED`, a mask with nothing stored 422 `INTEGRATION_SECRET_MASKED`), so a masked secret is never sent to an address the editor chose. Secret fields are `type="password"`.

- **A Failed Webhook Action Is Failed:** a rule's webhook action whose request fails (connection refused, DNS, timeout) is recorded as `failed` with the error, whatever its address; there is no simulated success, and the echo simulator is reached only through a real request.

- **No Demo Action Handlers:** boot (`registerDomainEventHandlers`) registers no `ActionHandlerService` handler; the framework (idempotency key per handler and event, «اکشن_هندلر:» audit row) stays for a handler that does real work, which a domain registers itself. A handler never writes an audit row for work another path did (the invoice voucher comes from `VoucherSync` in the document's transaction).

- **Test Tools Have No Effect:** a rule test (`POST /events/action-rules/:id/test`, `testStoredRule`) and a draft evaluation evaluate the conditions on a sample event and only describe what the action would do (`previewRuleAction` in `src/services/events/ruleDraftEvaluation.ts`); the event simulation (`simulateDomainEvent` in `src/services/events/eventSimulation.ts`, contract `src/lib/events/eventSimulationContract.ts`) takes only a published event type (else 422 `EVENT_SIMULATION_TYPE_UNKNOWN`), publishes nothing and lists the matching rules and receiving webhook subscriptions; the timeline replay is a dry run only (live replay 422 `EVENT_REPLAY_LIVE_REMOVED`). None of them sends, notifies or writes an audit row; the only real send is a subscription's connection test with the `system.ping` body.

- **Event Timeline of One Entity:** the timeline (`getAggregateTimeline` in `src/services/events/eventSourcingReplayService.ts`) reads an entity's outbox and dead-letter rows by its event aggregate types (`lower(aggregate_type)`) and exact id, and its audit rows only by the section's own audit entity names and exact id (`TIMELINE_AGGREGATE_SCOPES` in `src/services/events/timelineAggregates.ts`), never a description containing the id; audit rows go only to holders of `audit_logs.view` (`auditIncluded` in the answer), and the picker gives the id the events carry, never a document number.

- **Dead Letter Edit and Outbox Retry:** a dead-letter payload edit (`DeadLetterQueueService.editPayload`) runs under that row's lock in one transaction with an audit row (`tx`): a replayed row is never edited (409 `DLQ_EVENT_REPLAYED`), a non-object payload is 422 `DLQ_PAYLOAD_INVALID`, and the outbox row is rewritten only while it has not completed. «تلاش دوباره» of failed outbox events (`retryFailedOutboxEvents` in `src/services/events/outboxRetry.ts`) locks the failed outbox rows and their unresolved dead-letter rows, sets the events pending and marks their idle dead-letter rows replayed in the same transaction; one event that is not failed is 409 `OUTBOX_EVENT_NOT_FAILED` and one being replayed 409 `DLQ_REPLAY_IN_PROGRESS`.

- **Rule Switch Target State:** an automatic rule is switched on or off only with its target state (`POST /events/action-rules/:id/toggle` with `{ active }`, else 400): `setRuleActive` (`src/services/events/ruleActiveState.ts`) writes it under the rule row lock, a repeat changes nothing (`changed: false`), activation passes the same action and event type checks, and each change writes one audit row with before / after in its transaction; the rules tab disables a rule's switch and test button until their answer.
