# Online Shop (WooCommerce)

Orders, customers, product links and the automatic stock and price push.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md` at commit `c3c9858` (archives removed in v11.1.0), and a «§N» below refers to that file's numbering.

- **Public Route Exemption:** Webhook endpoints (`/api/woocommerce/webhook/order`) must be exempted from `authenticateToken` in `src/middleware/auth.ts` for ping/payloads (GET, POST, HEAD).

- **SKU Matching & Orders:** Match line items to ERP items via `items.code` (SKU); a SKU that is no live item's current code finds the item that held it as an earlier code in `item_code_history` (latest change wins, a current code always wins) and the order log names that old code (`resolveItemsByCode` in `src/services/items/itemCodeChange.ts`, `oldCodeOrderNote`). Route orders through `DocumentService.createDocument` (`docType: 'invoice'`, `status: 'final'`, `inOut: 'out'`).

- **Order Status Policy:** All order processing lives in `WooOrderSyncService` (`src/services/woocommerce/wooOrderSync.service.ts`). Only `processing` / `completed` issue a final invoice; other statuses are logged as `deferred`. `cancelled` / `failed` void the invoice through `DocumentService.deleteDocument`; `refunded` is only flagged `needs_review`, and so is an order moved to the trash or deleted in WooCommerce (status `trash`, or webhook topic `order.deleted`, whose body is only `{ id }` and never overwrites the stored order payload). An order with any unmatched SKU is rejected as a whole (no partial invoices). Each order is serialized by a row lock on its `woocommerce_order_logs` row; failures are persisted outside the rolled-back transaction. The webhook always answers HTTP 200 (WooCommerce never re-delivers and disables a webhook after 5 non-2xx responses); retries happen via manual order sync.

- **Rial Units of WooCommerce Orders:** An order's currency maps to IRR through `rialUnitMultiplier` (`src/lib/woocommerce/wcCurrency.ts`, shared with the price push): IRR ×1, IRT / TOMAN ×10, IRHR (thousand rial) ×1,000, IRHT (thousand toman) ×10,000; the invoice is in IRR. Any other currency stays a foreign-currency document and needs an exchange rate.

- **Namesake WooCommerce Buyers:** `resolveWooOrderCustomer` (`src/services/woocommerce/wooOrderCustomer.ts`) finds the order's customer by phone key, else (no phone) by the name key `lower(btrim(name))`, and the invoice takes the stored customer name; a new buyer whose name is another customer's (another phone, or that customer has none) gets a new customer «name (phone)» (`namesakeCustomerName`, audited), noted in the order log; a taken distinct name fails the order (422 `WOO_NAMESAKE_CUSTOMER_TAKEN`), never posts to the other customer.

- **Customer Match by Phone Key:** A WooCommerce order finds its customer by `phoneMatchKey` (`src/lib/search/phoneMatchKey.ts`, re-exported by `src/services/woocommerce/phoneMatchKey.ts`: Persian/Arabic digits to Latin, non-digits removed, the last ten digits; `phoneMatchKeySql` is the same key on the column), so +98…, 0098…, 0912… and spaced or Persian-digit forms of one number match one customer; without a phone the name is matched. The sales lead link, the customer form's duplicate check (on edit only when the number changes) and the customer Excel import match phones with the same key (`findActiveCustomerByPhone` / `assertCustomerPhoneAvailable` in `src/services/customers/customerIdentity.ts`).

- **Exact Line Totals:** An order line keeps its exact total on the invoice: when the total is not divisible by its whole quantity in the currency's smallest unit (rial without decimals, cents otherwise), `exactLineSplit` (`src/services/woocommerce/exactLineTotal.ts`) makes two lines, quantity − 1 at the rounded-down price and one unit at the remainder (1000 for 3 = 2 × 333 + 1 × 334). Never use a line discount for rounding (it would post to sales discounts).

- **Negative Fees Are Line Discounts:** Positive `fee_lines` and shipping are the invoice's service charge; the sum of negative `fee_lines` (an order discount) is spread over the invoice lines in proportion to their amounts as line discounts (`allocateFeeDiscount` in `src/services/woocommerce/feeDiscount.ts`, shares floored in the currency's smallest unit, remainder to the larger lines, exact sum), like a WooCommerce coupon; a discount larger than the lines rejects the order.

- **Changes to an Invoiced Order Need Review:** A webhook or manual sync of an already invoiced order is compared with the payload the invoice was issued from (`describeOrderChange` in `src/services/woocommerce/orderChange.ts`: line SKU / quantity / total, the order total and the sum of refunds). A difference sets the log to `needs_review` with the difference in its message and leaves the invoice untouched; an unchanged order (e.g. processing → completed) stays `processed`. Voiding and reissuing, or a sales return, is the accountant's decision.

- **Connection Test With Stored Keys:** the WooCommerce tab sends no empty or masked («********») key to `/woocommerce/test-connection` (`wcTestConnectionBody` in `src/lib/woocommerce/wcConnectionTest.ts`); the route takes a missing key from the stored settings (`resolveWcTestCredentials`, `readWcConnectionSettings` in `src/services/woocommerce/wcConnectionSettings.ts`) and then only at the stored store address (else 422 `WC_TEST_STORED_KEYS_OTHER_URL`; incomplete settings 422 `WC_TEST_SETTINGS_INCOMPLETE`), so stored keys never go to another site.

- **API Keys Only in the Header:** Requests to the WooCommerce REST API send the consumer key and secret only in the `Authorization: Basic` header over HTTPS; only a plain-HTTP store URL (where WooCommerce refuses Basic auth) gets them in the query string (`wcAuthQueryParams` in `src/services/woocommerce/wcRequestAuth.ts`). Every request to the shop, not only the connection test, passes `assertSafeExternalUrl` first and follows a redirect only by hand: at most `WC_MAX_REDIRECTS` (3) hops, only on the same site (`shopRedirectTarget`: the same host ignoring letter case and «www.», the same scheme or http → https, the same port; the query is built again for each hop) and each hop through the guard before anything is sent to it; any other redirect is 422 `WC_REDIRECT_REFUSED` / `WC_REDIRECT_LIMIT` asking for the final shop address (`followShopRedirects` in `src/lib/woocommerce/wcRedirect.ts`, called by `makeWcRequest` in `src/services/woocommerce/wcClient.ts` since v10.2.6).

- **Online Shop Warehouse:** The setting `wc_shop_warehouse` (an active warehouse code; empty = the default warehouse; an inactive or unknown code is refused on save) is the online shop's warehouse. WooCommerce invoices draw from it (`resolveShopWarehouseCode`) and the stock sync (`/woocommerce/sync-item`, `/woocommerce/sync-all-stocks`) pushes its sellable stock (`shopSellableStocks` in `src/services/woocommerce/shopWarehouse.ts`, the same `computeSellable` rule the invoice checks: min of that warehouse's stock and total stock minus reservations), never the total of all warehouses.

- **Shop Product Links and Batched Stock Push:** An item reaches the shop only through its live row in `wc_product_links` (migration 0128: one live link per item and per shop product or variation), made by «بازخوانی محصولات سایت» (`POST /woocommerce/refresh-products`, `woocommerce.manage`; `refreshWcCatalog` in `src/services/woocommerce/wcCatalog.service.ts`): it reads every catalog page in id order (100 per page, at most `WC_MAX_CATALOG_PAGES`, each product once; a refresh that reaches the cap says so and leaves untouched only the links of products above the largest id it read, and any other link whose product the shop no longer lists is closed; an empty catalog while items are linked is a failed run that changes no link (`EMPTY_CATALOG_MESSAGE`), and a reading that showed a product twice (an order with ties, such as date or menu order, which may also leave one out) or whose new ids did not come in ascending order and that was cut at the cap keeps every link it did not read and says so (`catalogUnordered`, `catalogOrderNotice`), while any other reading closes the links of products it did not list whatever its order; v11 phase 6.5 (#322 review notes 1 to 4): a list whose count (`X-WP-Total`) changed between two pages or that ended with more rows than its count (a product removed from a page already read moves the next pages up, so one is never shown) keeps every link it did not read too and says so (`shifted`, `catalogShifted`, `catalogShiftNotice`; a shop that sends no count is never marked; a product removed from a page already read while another is added before the last page leaves the count as it was and is not caught), a short or even empty page ends a list only once its count and its `X-WP-TotalPages` are reached (a shop that caps `per_page` sends more pages), and a count that stayed the same while fewer rows came (WooCommerce counts a row the key may not read and then drops it; a list that showed a row twice is not counted so) is a gap (`missing`; in a variation list, `gapVariationProducts`): the nightly re-read and the stock push keep the links of products they did not read (a variation list's gap: only that product's unread variations) and say so while that kept a link (`catalogMissing`, `catalogMissingNotice`), and a refresh by hand asks before closing one (`askOnGap`); a variation list cut at the cap, showing a row twice or whose count moved keeps the links of that product's unread variations only (`partialVariationProducts`, `partialVariationsNotice`), and a reading that would leave `WC_MASS_CLOSE_MIN` (5) or more items without a product (a product not read, or read with another SKU as from another shop with the same ids) and more than half the items whose links it compared, or a refresh by hand with a gap that would close a link it did not read, changes nothing and answers 409 `WC_MASS_CLOSE_CONFIRM` with `closedCount`, `liveCount` and `missingCount` until the user confirms that number in the tab (`POST /woocommerce/refresh-products` with the strict body `{ confirmClose: <closedCount> }`, recorded on the audit row; a reading that would then close more asks again, though the number confirmed names no particular links, and the button waits while the question is open); the nightly re-read and the stock push never confirm, so a mass closing fails them with that message) and the variations of variable products (at most `WC_VARIATION_READ_CONCURRENCY` at a time; a variation holding its parent's SKU is the parent), the whole read within `WC_CATALOG_DEADLINE_MS` (50 s, else a failed run; a failed read stops the other readers and no request outlives the refresh); an external or grouped product and a variation whose stock is the parent's (`manage_stock: parent`) get no link and are listed with their reason, never changed on the site; it links each product to the item its SKU finds with the order rule (`resolveItemsByCode`: the current code, else an earlier code); a SKU held by several shop products, a product without SKU, an unknown SKU and a second product of one item (the current code wins) get no link and are only listed, and a refresh creates or changes nothing on the site. The stock push (`/woocommerce/sync-all-stocks`, `/woocommerce/sync-item`; `src/services/woocommerce/wcStockPush.service.ts`) sends each link's whole, non-negative sellable stock (`siteStockQuantity`) in `products/batch` and `products/<id>/variations/batch` requests of at most `WC_BATCH_SIZE` (100) with `manage_stock: true`, says how many products had stock tracking turned on that way (`trackingEnabledCount`, `trackingEnabledNote`) and records each row's error on its link, all within `WC_PUSH_DEADLINE_MS` (50 s for the whole exchange: a refresh before it gets that less `WC_PUSH_MIN_BUDGET_MS` (5 s), a push left less than that is not started and is a failed run (`refreshBudgetMs` / `pushBudgetMs` in `src/lib/woocommerce/wcCatalog.ts`), and past the deadline nothing more is sent and the unsent products record why); an item without a link is 422 `WC_ITEM_NOT_LINKED` after one refresh. A catalog refresh and a stock push run under the session advisory lock `WOOCOMMERCE_SYNC` (91110; a second one at the same time is 409 `WC_SYNC_BUSY`); a push never sends a deleted item. Every exchange with the shop goes through the one client `makeWcRequest` in `src/services/woocommerce/wcClient.ts` (each connection's address is checked again when it opens (`guardedDnsLookup` in `src/lib/ssrfGuard.ts`, with its own HTTP and HTTPS agents, never through an environment proxy), an answer is at most `WC_MAX_RESPONSE_BYTES` (10 MB); a failing shop is 422 `WC_SHOP_REQUEST_FAILED` with a Persian message, never a 500) and a refresh or push writes a `wc_sync_runs` row (a failed one too) and one «فروشگاه اینترنتی» audit row of counts with its `tx` (no price, name or amount). The WooCommerce tab shows the links, the last refresh and push and the products and items left out (`GET /woocommerce/catalog`, `WcCatalogPanel`), and the synced-orders list reads the invoices the order log names (`erp_document_id`), never a search of the document notes.

- **Automatic Stock Push:** «ارسال خودکار موجودی» (setting `wc_auto_push`, off by default; `POST /woocommerce/auto-push` with the target state `{ enabled }`, `woocommerce.manage`, audited with `tx`; turning it on needs a complete connection) runs once a minute (`WcShopSyncWorker` in `src/services/woocommerce/wcSyncWorker.service.ts`, started by `server.ts`, which then runs the part C runs, each step on its own; `runAutoPushOnce` in `src/services/woocommerce/wcAutoPush.service.ts`), after the stock writes commit and never inside them. It skips its turn while the `WOOCOMMERCE_SYNC` lock is taken and reads nothing from the shop while no link's sellable stock moved since it last brought that link in line (held in memory, single process; after a restart or a changed shop stock the link is compared with its shop stock) and no order webhook named its product (an `order.deleted` webhook through the payload its order log keeps; `markOrderLinesDue` in `src/services/woocommerce/wcAutoPushDue.ts`, called by `WooOrderSyncService.handleOrder` after the order's transaction); once an hour, and first after a start, every tracked link is compared (`WC_AUTO_FULL_PASS_MS`), and a stock changed by hand in the shop is put right only by the nightly catalog refresh of part C. It then reads the shop's open orders and sends, in batches of 100 and without `manage_stock`, only links whose shop stock tracking is already on (`site_manage_stock = 1`) and whose number differs, at most `WC_AUTO_PUSH_MAX_PRODUCTS` (500) a run, the rest on the next run; untracked links and links stopped after `WC_AUTO_MAX_LINK_FAILURES` (5) failures in a row are listed in the tab (`getAutoPushView`, `WcAutoPushPanel`) and a manual push that succeeds puts a stopped link back. A failure of the shop (no answer, timeout, redirect, 5xx, 401, 403, 408, 429; `isShopLevelFailure` in `wcStockPush.service.ts`) never counts against a link and makes the next run wait 1, 2, 4 … 30 minutes (`autoPushBackoffMinutes` in `src/lib/woocommerce/wcAutoPush.ts`); any other 4xx of a batch (a product or a parent removed in the shop) counts against each of its products and the run is `partial`, never a wait. Its runs carry `trigger: 'auto'`, write no audit row except the first failure of a streak, and are removed after `WC_AUTO_RUN_RETENTION_DAYS` (30) by the daily operational purge (each registered purge runs on its own, so one failure skips no other) (`purgeOldAutoRuns` in `src/services/woocommerce/wcSyncRunPurge.ts`, registered with `OperationalPurgeService.register`); «آخرین ارسال موجودی» shows manual pushes only. Every push, automatic or manual, sends the sellable stock less what the shop's open orders hold (`siteStocks` / `openOrderQuantities` in `src/services/woocommerce/wcOpenOrders.ts`): on-hold and processing orders without a live invoice in the order log, and completed orders whose order log is `failed` without a live invoice completed in the last `WC_FAILED_ORDER_HOLD_DAYS` (30) days, counted from the order's `date_completed_gmt`, else from when its order log was made, never from the log's last change (`failedOrderHeldSince`; an older one was most likely entered by hand, and the card says to put «سفارش ووکامرس #<number>» in that invoice's notes before «صدور فاکتور» of «دریافت دستی سفارش با شماره سفارش», which then links it instead of issuing a second invoice: `findActiveInvoice` reads the tag's Persian and Arabic-Indic digits and Arabic kaf as typed, a no-break space as a space, drops the zero-width non-joiner and the LRM, RLM and ALM marks and needs the whole number after #; a completion dated in the future is treated as missing, so the hold counts from the order log's creation, and `updated_at` only pre-filters the logs read); a pending order holds no shop stock and is not read; read with the stock in one repeatable-read snapshot, matched through the links (a variation line without its own link counts for its parent product's link). Orders are read newest first, each reading after the first starting on the last order of the one before (`offset`), and within `orderReadBudgetMs` of the push's deadline, and orders that cannot be read in full (an order listed without its id included) stop the push with a failed run and nothing sent, naming only the button that was pressed: a reading whose first order is not the last of the one before, a repeated order, a shop count (`X-WP-Total`) that changes between the first and the last page or differs from the orders read, page 1 read again at the end of a longer list showing other orders, or a first page counting more than `WC_MAX_ORDER_PAGES` (25) pages of 100, which fails after that one request; the bulk push card says so (`BULK_PUSH_OPEN_ORDERS_NOTE`).

- **Price Push, SKU Rename and Nightly Re-read:** Two more automatic runs of the minute worker, each behind its own setting, off by default and written only through its route (`woocommerce.manage`, plus `products.edit_price` to choose a price list and `products.change_code` to turn the SKU rename on, checked with `can` in the route and asked by the tab too, which names the missing key; turning either off needs only `woocommerce.manage`; strict body, idempotent; the setting row locked, its «فروشگاه اینترنتی» audit row written with `tx`, turning a send on needs a complete connection; `src/services/woocommerce/wcFieldPush.service.ts`), under the `WOOCOMMERCE_SYNC` lock (taken: the run skips its turn). «ارسال خودکار قیمت» (`wc_price_list`, `POST /woocommerce/price-list` with `{ priceList }`: a configured price list, else 422 `WC_PRICE_LIST_NOT_CONFIGURED`; '' turns it off) sends that list's active price to each linked product's `regular_price` only, never the sale price (plan ق۲ / ق۳): the shop currency comes from `GET data/currencies/current` and its price decimals from `GET settings/general/woocommerce_price_num_decimals` (`readSiteMoney`; a 401 or 403 on the currency or the decimals setting, which only a key of a user who manages the shop may read, says the key must belong to a shop manager (`CURRENCY_FORBIDDEN_MESSAGE`, `DECIMALS_FORBIDDEN_MESSAGE`, the status kept so the run waits like any shop-level failure), kept `WC_SITE_CURRENCY_TTL_MS` for display, both read again fresh before any run that has something to send and at night, the run planned again when either changed; `src/services/woocommerce/wcSiteCurrency.ts`; a shop that answers either one unreadably fails the run), a rial price goes to a rial-unit shop divided by its `rialUnitMultiplier` and any other price only to a shop of its own currency, never rounded: the price must be exact at the shop's decimals, at most `WC_SITE_PRICE_PLACES` (4) (`sitePricePlaces`), in plain digits, else it is not sent and the shop's current price is left as it is, which the shop may show rounded to its own decimals (`inexact_unit`; `sitePriceOf` in `src/lib/woocommerce/wcShopSync.ts`), and a link is sent only when its stored shop price (`wc_product_links.site_regular_price`, the value last sent or read) differs; a variable parent (`variable` or any `variable-*` type, `isVariableParentType`), a link whose type was never read (`site_type` '', migration 0131), a price in another currency, a zero price and an item without a price are not sent and are listed in the tab, also after a restart (the shop currency and decimals of the last price run); the price run row lists what it changed (`changed`: product, variation, from, to; at most `WC_PRICE_CHANGES_KEPT` (200) with `changedTotal`), and the tab says a regular price changed by hand in the shop is overwritten while the send is on. «تغییر خودکار کد در سایت» (`wc_sku_rename` '1', `POST /woocommerce/sku-rename` with `{ enabled }`) gives a link whose shop SKU is not its item's current code (`renamedLinks`) that code; turning it on asks with the number of links it would change. Both send in batches of 100 (`sendLinkFields` in `src/services/woocommerce/wcBatchUpdate.ts`), at most `WC_AUTO_PUSH_MAX_PRODUCTS` a run, write a `wc_sync_runs` row of kind `price_push` / `sku_push` with `trigger: 'auto'` (purged after 30 days like the stock runs, and so are the nightly refresh rows), stop a product after `WC_AUTO_MAX_LINK_FAILURES` refusals in a row (`price_failure_count` / `sku_failure_count`; a shop-level failure never counts), wait 1, 2, 4 … 30 minutes after failed runs of their own kind (`autoRunBackoff` in `src/services/woocommerce/wcRunBackoff.ts`) and audit only the first failure of a streak. While any automatic send is on, once a business day from `WC_NIGHTLY_HOUR` (3) in the display time zone, the catalog is read again like «بازخوانی محصولات سایت» but with no audit row (`runNightlyOnce` in `src/services/woocommerce/wcNightly.service.ts`; a refresh run row with `trigger: 'nightly'`, its `businessDay` and the `siteCurrency` / `siteDecimals` its prices were compared in, which label the tab's price differences, at most `WC_NIGHTLY_MAX_ATTEMPTS` failed readings `WC_NIGHTLY_RETRY_MINUTES` apart): it lists each stock or regular price that differs from what the program sent or sends (`catalogDifferences` in `src/services/woocommerce/wcCatalogDrift.ts`), sends nothing itself (the changed shop stock makes the stock push compare that link again, the price push resends the price) and lets stopped price and SKU links try again; the tab shows all of it (`shopSync` of `GET /woocommerce/catalog`, `WcShopSyncPanel`).
