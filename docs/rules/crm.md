# Customer Relations

Sales files, activities and their attachments.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md` at commit `c3c9858` (archives removed in v11.1.0), and a «§N» below refers to that file's numbering.

- **Sales File and Activity Attachments:** A sales file (`crm_leads`) and an activity or follow-up (`crm_activities`) take image and PDF attachments through `GET` (`crm.view`), `POST` (`crm.manage`, the raw file body with `X-File-Name`) and `DELETE` on `/crm/leads/:id/attachments` and `/crm/activities/:id/attachments` (`src/routes/crmAttachments.routes.ts`, `CrmAttachmentService` in `src/services/crm/crmAttachments.service.ts`): JPG, PNG, WEBP or PDF whose content matches its type, at most 10 files per record and `MAX_ATTACHMENT_FILE_MB` per file (422 `CRM_ATTACHMENT_FORMAT` / `CRM_ATTACHMENT_TOO_LARGE` / `CRM_ATTACHMENT_LIMIT`; the rule is shared with the browser in `src/lib/crm/crmAttachments.ts`). They are stored through `file_attachments` (entity `crm_lead` / `crm_activity`, read permission `crm.view`) with the original kept and, for an image, a light WEBP of long side `MEDIA_LIGHT_LONG_SIDE` made by the media library's sharp pipeline (`file_attachments.light_storage_path`, migration 0127, served with `?variant=light`); each addition and removal is written under the record's row lock with its audit row in the same `tx`, and the files never enter the media library. The sales file window and each activity's paperclip button show them (`CrmAttachmentsPanel`), and a window does not close while a file is being sent or removed.

- **A Proforma From Any Open Sales File (v11 phase 6.3p, U17):** the screens offer «صدور پیش‌فاکتور» on every open sales file without a proforma, at any stage (`canIssueLeadProforma` in `src/lib/crm/leadProformaRule.ts`, shared with the server's `isClosedLead`); the saved proforma moves the file to «پیش‌فاکتور و پیشنهاد» (`markLeadProforma`). The conversion to a customer that comes before the form (`POST /crm/leads/:id/convert-to-customer`) only links the customer and keeps the stage, so a form left unsaved moves nothing. A closed file («فروش موفق» or «از دست رفته») takes none (422 `CRM_LEAD_CLOSED`) and a second proforma is refused. Before, the pipeline card, the table and the drawer offered it only at the proposal stage, and the quick button elsewhere only logged an activity; that button now reads «ثبت ارسال پیش‌فاکتور». A new sales file is «پرونده فروش» on every screen. Guard: `reg_lead_proforma_any_stage_v11_6_3p_u17`, `workflowPurchaseV11.test.tsx`.

- **A Lead's Outcome Follows Its Stage and Its Invoice (v11 phase 6.4, C3, C4, C6):** a lead's `status` follows its `stage` (`won` → `won`, `lost` → `lost`, an open stage → `active`); only `archived` is a status of its own, kept until the next stage change. `PUT /crm/leads/:id` with a status alone moves the stage the same way, so `{status:'lost'}` asks its reason and writes the stage history like the stage path; a stage and status that disagree, and `active` on a closed lead, are 422 `CRM_LEAD_STATUS_STAGE_MISMATCH` (`resolveLeadStageStatus` in `src/services/crm/crmLeadOutcome.ts`). When a lead's proforma is finalized into an invoice (any path through `DocumentLifecycleService.finalizeDocument`), the lead, locked before the items like the void, moves to «فروش موفق» in the same transaction (a link moved to another lead while the finalize waited is refused with 409 `DOCUMENT_LEAD_LINK_CHANGED`, to try again) with its stage history row, a note and the «معامله موفق» notice (written in a savepoint, so a failed notice never stops the sale) (`markLeadWonByInvoice`); while that invoice is final, the lead refuses any other stage, «از دست رفته» included, with 422 `CRM_LEAD_SOLD` (`assertSoldLeadStaysWon`), and voiding it moves the lead back to «پیش‌فاکتور و پیشنهاد» as before. Leads finalized before this version are not moved. The unpaged lead list (the board and the dashboard) takes the open files first, then the newest closed ones (`openLeadsFirst`), so the `CRM_BOARD_LEAD_CAP` cut drops old closed files and never an open deal; the dashboard calendar says so when the open files alone fill the list (`dashboardLeadCapNotice`). Guard: `reg_crm_lead_status_follows_stage_v11_6_4_c4`, `reg_crm_lead_won_by_final_invoice_v11_6_4_c3`, `reg_crm_unpaged_leads_open_first_v11_6_4_c6`, `salesCrmV11.test.ts`.
