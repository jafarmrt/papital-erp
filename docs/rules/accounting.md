# Accounting

Vouchers, fiscal years and closing, account mapping, the chart of accounts and money arithmetic.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md` at commit `c3c9858` (archives removed in v11.1.0), and a «§N» below refers to that file's numbering.

8. **Money Columns are Decimal on the Server (audit P2-6 / TD-210):** Money columns are declared with `moneyNumeric` (`src/db/schema/moneyColumn.ts`; done for every money column — accounting, treasury, document lines/VAT/exchange rate, WAC, Kardex, item prices, payroll and piecework). Report totals are summed in SQL (`SUM(...)::text` → `fin()`) or accumulated with `FinancialDecimal`, never with JS `+=` on numbers (TD-210 resolved).. Their value is `Money` (`src/lib/money.ts`, a `FinancialDecimal`): do arithmetic and comparisons with its methods or `fin()`, write with `money(x)` / `moneyOr(x, fallback)`, never through `Number()` or JS operators. API JSON stays numeric (`Money.toJSON`); DTOs typed `number` convert explicitly with `.toNumber()`.

- **Rial Cost Rows in Foreign Documents:** In a foreign-currency voucher, rows that carry a rial Kardex cost (cost of sales, inventory, donated goods) stay in the document currency and get their own exchange rate = rial value ÷ foreign amount (`foreignCostRow` / `rowExchangeRate` in `src/services/accounting/foreignCostRow.ts`), so amount × row rate equals the Kardex value exactly; cost of sales is the sum of the inventory rows so the voucher stays balanced in its currency. Never convert a rial cost at the document rate alone. Since v10.0.12 both the amount and the row rate are stored to 4 decimals, so each such row takes the 4-decimal rate nearest to rial ÷ amount at which amount × rate rounds to its rial value rounded to the rial, and the opposite row (cost of sales, work in progress, donated goods against the supplier at the document rate) is worth exactly their sum (`balancedCostRows` / `rateForRial` in `src/services/accounting/foreignCostRow.ts`): the voucher balances in rials under the TD-260 rule, so its year closes.

- **Fiscal Periods:** Whether a (Jalali) fiscal year is closed lives ONLY in `fiscal_periods` (`FiscalPeriodService`); never infer it from voucher reference numbers. Every voucher create/update/delete/reverse/finalize calls `VoucherService.checkFiscalPeriodOpen(date, tx)`, which locks the year's row `FOR SHARE`; `FiscalYearService.executeFiscalYearClosing` locks it `FOR UPDATE` before computing balances and marks it closed in the same transaction. No voucher type (including `closing`) bypasses the check. A sub-ledger write checks the same year lock whether or not it posts a voucher (v11 phase 3.1, M5 / S6 / M23): every treasury row (`postTreasuryRow`), a treasury transfer, a cheque and every cheque step, every stock movement (`assertStockMovementDate`, the warehouse transfer included), and a draft or final document created in, or moved into, a closed year (a proforma is exempt, since it takes the finalize day); `fiscalPeriod.service.ts` reads only infrastructure and is shared kernel for the package boundary ratchet. The double-entry balance tolerance is the single constant `VOUCHER_BALANCE_TOLERANCE = 0.01` in every path (`src/lib/voucherBalance.ts`; the voucher forms use `computeVoucherBalance` from the same file).

- **Manual Voucher Currency and Rial Balance:** A manual voucher (`POST` / `PUT /accounting/vouchers`, which pass `manualEntry`, never read from the body) and a correction voucher resolve each row's currency as the row's own, else the voucher's, else IRR, and need a positive rate on every non-rial row (422 `VOUCHER_ROW_RATE_REQUIRED`, never rate 1); rows of one currency at one rate balance on their own amounts, any other voucher in rials by the TD-260 rule (`computeVoucherCurrencyBalance` in `src/lib/accounting/voucherCurrencyBalance.ts`, `resolveManualVoucherRows` / `assertVoucherRowsBalanced` in `src/services/accounting/voucherRowBalance.ts`). Every path balances a multi-currency voucher in rials, and finalizing accepts one whose rows balance in rials (`isVoucherBalancedForFinalize`). The journal book filters rows by the TD-260 currency rule and shows the «all currencies» view in rials with the row's own amount and rate; the financial health check balances multi-currency vouchers in rials and lists vouchers with a non-rial row at rate empty, 0 or 1 (`voucher_foreign_rows_without_rate`), never rewriting them. The manual voucher form, its edit and the correction form send and keep each row's currency and rate: the voucher and row currencies come from `TREASURY_CURRENCIES` (no «تومان»; the manual voucher routes refuse another code with 400), an empty row currency follows the voucher and an empty rate of a row in the voucher currency takes the voucher rate (`withVoucherRowCurrency` in `src/lib/accounting/voucherFormCurrency.ts`), and the forms balance and add the balancing row with the server's rule (`voucherFormBalance`, `voucherBalancingAmount`). A voucher row's debit, credit and rate are read with `decimalInput`. Its detailed type comes from `VOUCHER_DETAILED_TYPES` (`src/lib/accounting/voucherDetailedTypes.ts`, shared by the schema and both forms through `VoucherDetailedPicker`; a legacy `custom` row is «متفرقه» `other`), and the project detail reads the project pick list, which `accounting.vouchers` opens. The voucher print follows the same balance rule (`voucherPrintAmounts` in `src/lib/accounting/voucherPrintAmounts.ts`: a single-currency voucher in its currency with its rate, a multi-currency one in rials with each row's own amount and rate), and voucher types are named only through `VOUCHER_TYPE_LABELS` (`src/lib/accounting/voucherTypes.ts`, settlement «تسویه» included). The voucher, correction and reversal forms and the accounting report filters keep ISO dates in `JalaliDateInput`; no accounting component imports `react-multi-date-picker` directly.

- **Manual Voucher Dates (v11 phase 6.1a, M9):** the date a user gives a manual voucher (create and edit from the voucher page, a reversal from it, a correction) lies between the first day of the books' first fiscal year and the business today: after today is 422 `VOUCHER_DATE_IN_FUTURE`, earlier is 422 `VOUCHER_DATE_TOO_EARLY` (`assertManualVoucherDate` in `src/services/accounting/manualVoucherDate.ts`). The first fiscal year is the year of the oldest live voucher, or last year when that is earlier, so last year's entries are still made on a new install. Sourced and system vouchers keep their own dates. The year-close preview subtracts trial balance turnovers in decimals rounded to 4 places (`netOf` in `fiscalYear.service.ts`, M15). Guard: `reg_manual_voucher_date_bounds_v11_6_1a_m9`, `reg_fiscal_close_preview_decimal_v11_6_1a_m15`.

- **Draft Vouchers at Closing and Void:** Automatic vouchers stay `draft` until an accountant approves them (`accounting.vouchers_approve`, which the accountant role template carries since v11 phase 6.1پ, U5). A fiscal year is never closed while a draft voucher dated in that (Jalali) year exists: `FiscalYearService.findDraftVouchersOfYear` runs after the year lock, `executeFiscalYearClosing` refuses with `FISCAL_YEAR_HAS_DRAFT_VOUCHERS`, and the preview returns `draftVouchers` / `draftVoucherCount` (the closing button stays disabled). Voiding a source — document/invoice, treasury transaction, cheque, payroll — goes through `VoucherService.voidSourceVoucher`: a draft voucher is soft-deleted (fiscal period checked), an approved or permanent one gets a reversal voucher; never issue an approved reversal for a draft. A voucher issued by a source (document, treasury transaction, cheque, payroll, BOM allocation, the opening voucher of a treasury account and the adjustments of its opening balance: the `source_*` columns, `cheques.voucher_id`, `treasury_transactions.voucher_id` and `reference_module = 'treasury_opening'` with a row on that account, a reversal taking its original's source; `voucherSourceKinds` in `src/services/accounting/voucherSource.ts`) is only approved and finalized from the voucher page: delete, a manual edit, back to draft (page or workflow), reverse, correction and void-and-repost are refused with 409 `VOUCHER_HAS_SOURCE` naming the source, which is voided instead (an opening balance is changed in the treasury account's form, and the start date of a draft opening voucher moves from there; v11 M2); the voucher list and detail carry `sourceKind`. A correction (`correctVoucher`) issues the reversal approved and the replacement as a manual draft through `createJournalVoucher` (`manualEntry`), so the replacement enters the journal voucher workflow and the maker-checker rule below and is in the books only once another holder of `accounting.vouchers_approve` approves it (v11 M1). `PUT /accounting/vouchers/:id` requires the voucher's `version` (400 without it) and writes with the version in its WHERE (409 `OCC_CONFLICT` when stale); a deleted voucher is neither read nor edited; voucher and account edit and delete audit rows carry before / after, rows included (`src/services/accounting/accountingAudit.ts`). Batch finalize answers the vouchers it made permanent and each refused id with its reason (`BatchFinalizeResult` / `batchFinalizeMessage` in `src/lib/accounting/voucherBatch.ts`), never the count of ids sent. The automation status (`getAutomationStatus` in `src/services/accounting/automationStatus.service.ts`, rules in `src/lib/accounting/automationStatus.ts`) counts final documents only, a stock count as needing a voucher only with a valued Kardex difference and a transfer never; its coverage is 100 only when every needed voucher exists. The voucher row menu offers only what the server accepts (`voucherRowActions` in `src/lib/accounting/voucherRowActions.ts`): edit and delete a draft, back to draft an approved voucher, reverse an approved or permanent one and correct an approved one, never reverse or correct a reversal; a voucher with a source or of a closing run shows only why it is locked and the workflow. A reversal voucher (`REV-V`, `VOID-REPOST-V`, `RE-REV-V`) never goes back to draft (409 `VOUCHER_REVERSAL_LOCKED` in `applyVoucherStatus`, page and workflow), and a voucher with an active reversal carries its number (`reversedByVoucherNumber`, `voucherActiveReversals` in `src/services/accounting/voucherSource.ts`), so its menu offers no reverse, correction or revert and says why. Approving, finalizing (one or a batch) and putting back to draft need `accounting.vouchers_approve` (requires `accounting.vouchers` and `workflow.approve`, which signs the journal voucher workflow; migration 0098 gave it to every role holding `accounting.vouchers`), and the creator or last editor (`journal_vouchers.updated_by_id`) of a manual voucher never approves or finalizes it (403 `VOUCHER_MAKER_CANNOT_APPROVE`; a batch skips it with its reason); a voucher with a source, a closing-run voucher and the system admin are exempt, a manual voucher is recorded as approved only by the system admin, and the default journal voucher workflow asks the same key, upgraded at boot only on an install still holding the old seed (`upgradeLegacySeedGuards` in `src/services/workflow/seedGuardUpgrade.ts`; `assertNotApprovedByMaker` in `src/services/accounting/voucherMakerChecker.ts`); the voucher list shows that maker «در انتظار تأیید دیگری» instead of the approve button (`isViewerVoucherMaker` in `src/lib/accounting/voucherListViewer.ts`).

- **Closing Dates Are the Year's Bounds:** A fiscal year is the Jalali year. Closing vouchers keep each balance's detail: one row per account and detail of the level-4 trial balance, a party, project or bank account with its type and id (`closingRowDetail` in `src/services/accounting/closingRowDetail.ts`), and the opening voucher mirrors them. Closing vouchers are always dated the year's last day (30 Esfand in a leap year, else 29 Esfand) and the opening voucher 1 Farvardin of the next year; balances are taken up to that last day. `resolveFiscalClosingDates` (`src/services/accounting/fiscalYear.service.ts`, built on `jalaliYearBounds` in `src/utils/calendarDate.ts`) derives them from the year and refuses any other date sent by a client (422); the closing form only displays them.

- **Closing Vouchers Are Linked to Their Year:** The closing and opening vouchers a fiscal-year closing issues carry `journal_vouchers.source_fiscal_year` = the closed year (migration 0069 linked the earlier runs of closed years); a closing voucher is only such a linked `closing` voucher, never a voucher found by type or reference number. The trial balance, income statement, balance sheet and ratios leave a linked closing voucher out when it is dated on or after the report's end date (income statement: its start date), unless `includeClosing` («همراه اسناد اختتامیه», `yearEndClosingVoucherSql` / `yearEndClosingCutoff` in `src/services/accounting/yearEndClosingVouchers.ts`); the opening voucher always counts, and the closing computation reads its balances with `includeClosing: true`. A manual voucher (`POST` / `PUT /accounting/vouchers`) never takes the type `closing` (the form offers «افتتاحیه», `opening`) nor a reference with a reserved prefix of the system (`isReservedVoucherReference` in `src/lib/accounting/manualVoucherRules.ts`); whether a year is closed is read only from `fiscal_periods`, never from reference numbers; a voucher of a closing run (its opening voucher included) is never reversed, corrected or put back to draft (409 `FISCAL_CLOSING_VOUCHER_LOCKED`), while a legacy manual `closing` voucher is an ordinary voucher listed by the financial health check (`manual_vouchers_closing_type`).

- **Close After the Year Ends, Reopen the Last Closed Year:** A fiscal year is closed only when the business today is past its last day (422 `FISCAL_YEAR_NOT_ENDED`, `assertFiscalYearEnded` in `src/services/accounting/fiscalYearOrder.ts`); the preview carries `yearEnded`, and the closing form takes its years from `GET /accounting/fiscal-closing/years` (ended years only, with status and whether they have vouchers; never the current or a future year). Only the last closed year (every later year open) is reopened, through `POST /accounting/fiscal-closing/reopen` with a required reason and the permission `accounting.fiscal_reopen` (granted to no role by default): `reopenFiscalYear` (`src/services/accounting/fiscalYearReopen.ts`) takes the fiscal-year sequence lock (`ADVISORY_LOCK_KEYS.FISCAL_YEAR_SEQUENCE` 91020, also taken by closing) and the year's `fiscal_periods` row lock, opens the year, voids the active vouchers of its latest closing run (linked by `source_fiscal_year`, neither reversals nor reversed) through `voidSourceVoucher` with a reversal on each voucher's own date, and writes the audit row with `tx`. Years closed before their end are only listed by the financial health check (`fiscal_year_closed_early`). Years close in order: a year closes only when every earlier year holding an active voucher of any status is closed (`assertEarlierYearsClosed`, same file, after the year row lock; else 422 `FISCAL_YEAR_EARLIER_OPEN` naming them); the preview carries `earlierOpenYears`, the form starts on the oldest open year with vouchers (`defaultYear`), and years closed before an earlier year with vouchers are only listed by the health check (`fiscal_year_closed_out_of_order`).

- **Voucher Accounts Come From the Account Mapping:** Automatic vouchers resolve inventory (raw materials, work in progress, finished goods), trade payables and trade receivables through `AccountMappingService` — sales, purchase, production receipt, remittance/waste and sales return alike; a hard-coded code is only the fallback when the mapped account is missing, and a stored mapping or disabled list that cannot be read is refused with 422 `ACCOUNT_MAPPING_UNREADABLE`, never replaced with the defaults. The project reports count approved and permanent vouchers only, and the accounting dashboard's cash and bank card sums each currency apart, `totalCashAndBank` being the rial accounts. The waste voucher debits «ضایعات و افت کیفی» (6004, mapping `wasteExpenseAccountCode`) and 6001 is «بهای تمام‌شده کالای فروش‌رفته». Only a project remittance debits work in progress (1402, detail the project), its project read only from `documents.project_id`, never from the notes; a remittance without a project debits «مصرف مواد بی پروژه» (mapping `unassignedConsumptionAccountCode`, default 6003) and a production receipt without a project credits it. A remittance or waste voucher posts the Kardex cost of its own `out` rows (`documentOutflowCost` in `src/services/accounting/outflowVoucherCost.ts`; an item without a Kardex row at its current WAC, never the line price), so re-syncing a draft never changes it. Payslip «other deductions» (loan instalments, fines) credit «سایر کسورات حقوق پرداختنی» (3205, mapping `employeeDeductionsPayableAccountCode`; insurance and income tax have their own rows since v10.0.210); migration 0077 adds 3205 to an existing chart and moves a stored mapping still at the old default 3202 «پیش‌دریافت‌ها از مشتریان» (with an audit row). Payslip vouchers posted to 3202 before are never moved: the financial health check lists each personnel's remaining 3202 balance (`payroll_deductions_in_customer_prepayments`) until a correction voucher with the personnel detail moves it.

- **Chart of Accounts Integrity:** An account that any active row of an active voucher (any status) uses is never deleted: `deleteAccount` locks the account row and refuses with 409 `ACCOUNT_HAS_VOUCHER_ROWS`, pointing to deactivation. `createAccount` always inserts a new row and never revives a deleted account by its code; deleted accounts that still carry rows are only listed by the financial health check (`deleted_accounts_with_voucher_rows`). A manual, edited or correction voucher row goes only on a posting account: active, subsidiary or detailed, without an active sub-account (`postingRefusal` in `src/lib/accounting/postingAccount.ts`, shared with the forms; `assertPostingAccounts` reads the accounts `FOR SHARE`, else 422 `VOUCHER_ACCOUNT_NOT_POSTABLE`), and the voucher forms offer only those; legacy rows elsewhere are listed by the health check (`voucher_rows_on_non_posting_accounts`). The account mapping concepts (label, default code, allowed account types) live in `src/lib/accounting/accountMappingConcepts.ts`, shared by the server and the page; `saveMappings` stores a code only when it is a posting account of the concept's types (else 422 `ACCOUNT_MAPPING_INVALID` naming each wrong concept; disabled concepts are not checked), and `resolveAccount` and the voucher sync fallbacks take the mapped code, else the concept's default code, never a group or general account; wrong mappings are listed by the health check (`account_mapping_invalid`). A treasury or cheque party row whose mapped account and its default are both missing gets no account and is refused, never the general account (`resolveContraAccount`, OWN-03). `updateAccount` locks the account row and checks only the fields that change: a system account takes only a new name and description (409 `ACCOUNT_IS_SYSTEM`), an account with voucher rows keeps its type, nature, level and parent (409 `ACCOUNT_HAS_VOUCHER_ROWS`), and a parent is a non-deleted account exactly one level up outside the account's own subtree (`assertAccountPlacement` in `src/services/accounting/accountPlacement.ts`, 422 `ACCOUNT_PARENT_INVALID` / `ACCOUNT_LEVEL_INVALID`); the tree and the trial balance roll-up make the accounts of a legacy cycle roots. An account code is Latin digits only, at most twenty (`ACCOUNT_CODE_PATTERN` in `src/lib/accounting/accountCode.ts`; Persian and Arabic digits are converted, anything else is 422 `ACCOUNT_CODE_INVALID`), unique among active accounts by its digit-normalized key (`assertAccountCodeAvailable` in `src/services/accounting/accountCodeGuard.ts`; a violation of `uq_accounts_code_active` is the same 409 `ACCOUNT_CODE_TAKEN`) and fixed after creation (422 `ACCOUNT_CODE_IMMUTABLE`; a legacy Persian-digit code turns Latin when its account is saved); codes still not Latin are listed by the health check (`account_code_not_latin`). Migration 0071 adds CHECK constraints on a live voucher row (non-negative debit and credit, one of them non-zero), a voucher's status and type and an account's level, type and nature (soft-deleted rows exempt), and the foreign key `fk_accounts_parent`, each `NOT VALID` and validated only on clean data; what is left is listed by the health check (`accounting_integrity_constraints`).

- **Transactional Voucher Generation:** `VoucherSync` calls triggered from documents/treasury MUST execute inside the same database transaction (`tx`).

- **Document ↔ Voucher Link:** Vouchers issued by `VoucherSync` for a document carry `journal_vouchers.source_document_id` (unique among active vouchers, migration 0017). Always find a document's voucher by `source_document_id`, never by (`reference_module`, `reference_id`) — reversal/correction/repost vouchers (`REV-V…`, `CORR-V…`, `VOID-REPOST-V…`, `REPOST-V…`) keep `reference_module='invoice'` but store the ORIGINAL VOUCHER id in `reference_id`. A piecework payroll's voucher is found the same way through `journal_vouchers.source_payroll_id` (migration 0035; `src/services/accounting/payrollVoucherLink.ts`), never by `reference_id`.

- **Unique Voucher Numbers:** `journal_vouchers.voucher_number` comes only from `journal_voucher_number_seq` (`VoucherService.getNextVoucherNumber`, also in test factories) and is unique through `uq_jv_voucher_number` (migration 0031, created only when existing data has no duplicate). Old voucher numbers are never renumbered automatically; duplicates are listed by the financial health check (`voucher_number_uniqueness`).

- **No Bulk Accounting/Inventory Work at Boot:** Server startup must not run bulk voucher sync or Kardex backfill. Bulk voucher issuance runs only manually via `VoucherSyncService.syncMissingDocumentVouchers` (missing vouchers only, never rewrites existing ones) under advisory lock 91001; Kardex initial backfill via `KardexBackfillService.runExclusive` under lock 91002 (`src/lib/advisoryLock.ts`).
