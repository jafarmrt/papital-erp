# User Interface and Wording

Dates and numbers on screen, the UI glossary and its ratchets, forms, dialogs, data fetching and component structure.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md`, and a «§N» below refers to that file's numbering.

- **Safe Extraction:** APIs return paginated `{ data: [...], total, page, limit }` or arrays `[...]`. Always extract safely:
 ```ts
  const rawData = Array.isArray(res?.data) ? res.data : (Array.isArray(res) ? res : []);
  ```

- **Guard Array Operations:** Always guard before calling array methods:
 ```ts
  const safeItems = Array.isArray(items) ? items : [];
  const filtered = safeItems.filter(...);
  ```

- **Dates & Numbers:** Server dates must use `src/lib/businessClock.ts`. UI dates are always Jalali (`formatPersianDate`, `JalaliDateInput`; storage rule in §1.10). Numbers formatted via `formatPersianPrice` or `formatPersianNumber`, which write the Persian thousands separator «٬» and decimal separator «٫»; browser number parsers (`parseCleanNumber` and the amount field, `src/lib/amountText.ts`) read them through `normalizeDecimalString` and never turn an invalid entry into 0. A number or amount field (`DecimalInput`, `FinancialAmountInput`) shows Persian digits, «٫» and «٬» between three-digit groups while typing, with any keyboard, keeps the caret after the same digit (and after a «٬» the user typed) and sends the Latin value (`decimalDisplayText` / `persianNumberText` in `src/lib/numberFieldDisplay.ts`; an identifier field takes `grouped={false}`); only the separators the field put there itself are dropped before reading (`withoutFieldSeparators`; an edit that inserts a separator keeps them all for the check and an accepted number is kept without separators, so «۱٬۲۵۰٬۰۰۰» typed key by key is 1250000), so a «٬» the user types or pastes outside three-digit groups («۱۲٬۵») is an error in the number and the amount field alike, never 125 (the amount field keeps it on the field like the number field and reports 0, meaning empty while the field is invalid, never a number; it blocks the form, Ctrl+S of the voucher form included, and any other value set from outside clears it, while a reset to the same 0 it reported keeps it, so a list of such fields keys its rows with a browser-only `rowKey` (`src/lib/rowKey.ts`) that no draft or request carries and that a restored draft renews; v10.2.4, TD-1291), and a screen picks a date only through `JalaliDateInput`, the one file that imports `react-multi-date-picker` (Vitest `persianNumberFieldsTd1288.test.tsx`). Iranian identifiers (national ID, phones) preserve leading zeros via `formatPersianPhone` and `formatPersianNationalId`. A national ID is exactly ten digits with a valid check digit and a form or the server never zero-pads it (`requirePersonnelNationalId`, 422 `NATIONAL_ID_INVALID`); only the Excel import pads 8 or 9 digits and lists the row as a warning (`readImportedNationalId` in `src/lib/personnel/nationalIdCell.ts`).

- **Dynamic Currencies:** Respect `currency` on records (IRR, USD, EUR, AED, GBP); do not hardcode "ریال". The `currency` setting is only the display unit of rial amounts, IRR or TOMAN (toman = rial ÷ 10, label «تومان»): a rial amount is shown through `useRialDisplay` / `rialDisplayOf` (`src/lib/rialDisplay.ts`: `number`, `amount`, `money(amount, currency)`), a record with its own foreign currency keeps it, amount inputs and Excel exports stay in rial, and no component labels or formats an amount with the setting itself (Vitest `rialDisplayUnitTd667.test.tsx`). Business settings are checked on save with the rules in `src/lib/settings/settingValues.ts`, shared by the server and the settings form: the movement days are whole numbers from 1 to 3650 with fast < slow < dead (422 `SETTING_MOVEMENT_DAYS_INVALID`, checked together with the stored values), `currency` is IRR or TOMAN (422 `SETTING_CURRENCY_INVALID`), and the dashboard reads a stored invalid set as the defaults 30 / 90 / 180 (`resolveMovementDays`).

Persian stays in UI text, API error messages for users, the changelog, `TECH_DEBT.md`, documents and `AGENTS.md`, text a script writes into a file, and test data. `npm run ratchet:terminal-english` (`scripts/terminal-english-ratchet.ts`, baseline `terminal-english-baseline.json`, run by Vitest `terminalEnglishRatchet.test.ts`) counts per file the places that still print Persian and fails when a file gains one; a lower count fails until the baseline is lowered with `-- --update`. Never raise the baseline. Since v9.0.450 the baseline is empty, so no counted place prints Persian; a runner test name held in a constant and the label or message of a test assertion helper (`check`, `expect…`, `assert…`) count too, and Persian a test compares with the application's output goes in a named constant. `errorHandler` logs an error on the terminal as `HTTP <status> <code> <method> <route>` (`errorLogEntry` in `src/middleware/logger.ts`; a 5xx adds its English message and stack frames), the user's Persian message goes only to the response and the JSON log file (`userMessage`), and the console transport prints each Persian run of a log line as `[Persian text in the log file]` (`terminalLine`).

Add a label to `FIELD_LABELS` for a new user-facing field, and write UI words in Persian (no transliteration).

- **Form Drafts:** A draft's type and key match `DRAFT_ENTITY_TYPE_PATTERN` / `DRAFT_KEY_PATTERN` (`src/lib/drafts/draftRules.ts`, else 400) and the drafts routes leave every other error to `errorHandler`, so no SQL text reaches the browser. A draft lives 1 to 90 days (`DRAFT_EXPIRY_DAYS`), an expired draft is never returned (a legacy row without `expires_at` lives 30 days from its last save) and `FormDraftService.startCleanup` soft-deletes expired drafts daily under advisory lock 91031. A user has one live draft per type and key (partial unique index `uq_form_drafts_live_user_key`, which set older live duplicates aside first): a save is one INSERT … ON CONFLICT and, in its transaction, soft-deletes the user's live drafts beyond the newest `DRAFT_MAX_PER_USER` (50); `DELETE /drafts/id/:id` removes only the user's own live draft, else 404 `DRAFT_NOT_FOUND`. A draft set aside (by migration 0133, the cap or a delete) gets the time it was set aside as its `updated_at` (`trg_form_drafts_updated_at`, as every soft delete of a draft), and past the cap the oldest live draft is set aside without a message, by design; nothing reads a set-aside draft (#350 review L1, L3).
