# Versions, Releases and GitHub

Changelog entries, series, the release tools, the debt registry, branches and dependencies.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md`, and a «§N» below refers to that file's numbering.

- **Mandatory Update Logging:** Whenever modifying code, adding features, optimizing, or fixing bugs, you MUST append a new release entry to the **active** changelog file (currently `src/data/changelogs/11.ts`, series `v11.x.y`) with Jalali date, version bump, title, summary, changes, and fixes. Small fixes of the same kind share one pull request and one version; a documentation-only change takes no version (v11 product-owner decision).

- **Short Entries, Important Points Only:** Every version still gets exactly one entry, but it records only important changes and important / critical bugs — no file lists, test names, debt bookkeeping or "version bumped" lines (those belong in the commit and `TECH_DEBT.md`). Limits in `src/data/changelogs/compactRule.ts` (title ≤ 90, summary ≤ 300 chars, ≤ 4 changes, ≤ 4 fixes, each ≤ 150 chars) are enforced by `npm run check:version`.

- **Every Claim Has a Test:** Every fix or behaviour change recorded in the changelog is backed by at least one automated test that fails on the previous version and passes on the new one. The test id is named in the commit message and, when the change has one, in its `TECH_DEBT.md` row (never in the changelog file, per the rule above). A claim without such a test (e.g. a refactor or a documentation change) is worded as such and never as a fix.

- **Active File:** For version 11.x releases, append to `src/data/changelogs/11.ts` and bump the version in all synced locations listed below.

- **Series Closure:** The active series and the closed series are declared once in `src/data/changelogs/index.ts` (`ACTIVE_CHANGELOG`; `CLOSED_CHANGELOG_SERIES` with final version, entry count and SHA-256 fingerprint). `npm run check:version` (`src/data/changelogs/seriesGuard.ts`) rejects a `package.json` major outside the active series, an entry of another series in the active file, and any change to a closed series file. Opening the next series repeats v8.0.0 / v9.0.0 / v10.0.0 / v11.0.0: freeze the current file with its fingerprint, add the new file, archive the roadmap with a closing report and open a new one; `scripts/release.ts` follows `ACTIVE_CHANGELOG` and needs no change.

- **Active Series (v11.x.y):** The active changelog file is `src/data/changelogs/11.ts` (`v11.x.y`, from v11.0.0). Historical changelogs reside in `0.ts` (`v1.0.0`), `archive_1_6.ts` (condensed `v1.x.y`–`v6.x.y`, finalized at `v6.0.28`), `7.ts` (`v7.x.y`, closed and frozen at `v7.0.140`), `8.ts` (`v8.x.y`, closed and frozen at `v8.0.128`), `9.ts` (`v9.x.y`, closed and frozen at `v9.0.461`) and `10.ts` (`v10.x.y`, closed and frozen at `v10.3.24`). Every change MUST append one unique, short `AIUpdateLog` entry to `src/data/changelogs/11.ts` and bump `package.json` `"version"`.

- **Core Mission of Version 11 (`docs/roadmap/V11_MASTER_ROADMAP.md`):** Phase by phase, each phase split into sub-phases of like work: 0 the server on v10.3.24 (done); 1 the series kickoff, a section-by-section review of these rules with the product owner (one decision card per section of this file) and then shorter rules plus a short lessons file in place of `TECH_DEBT_ARCHIVE.md`; 2 an independent evaluation in five parts (money and accounting, stock and production, security, using the app, the server) that reads no project document and looks for one action reachable by several paths, then sorting the findings and re-reviewing the plan; 3 the database base (one base migration, `mockPool.ts` out, time columns with time zone); 4 the server and CI; 5 the online shop package 6, the findings, and severance, overtime and child allowance (design first, build only on the product owner's approval); 6 closing with the user guide for 10.2, 10.3 and 11. Phases 1 and 2 are final; phases 3–6 stay provisional until the evaluation report. Removed from the plan by the product owner: online filing of insurance and payroll tax lists, phone push notifications, a postal code on party addresses, camera barcode counting, and the Ubuntu 26.04 upgrade of the production server. Insurance, payroll tax and VAT stay supported but never required. The V8–V10 method is unchanged: every finding proven by a test that fails first, its own `TD-###` row (from TD-1389; TD-1389 itself was closed in v11.0.0) and release.

- **CHANGELOG.md Archive:** Condensed markdown archive of major series milestones lives in root `CHANGELOG.md`.

- **Technical Debt Registry (TECH_DEBT.md):** Debt that remains after a change (a shortcut, a workaround, a known issue, work left for later) is registered with a unique `TD-###` in `TECH_DEBT.md`; a fix finished in the same pull request needs no row, its test is the record (v11 product-owner decision). Resolving a registered debt updates its row in the same change.

- **Release Paperwork (generic since v9.0.0):** `npm run release -- <spec.json>` (`scripts/release.ts`, spec fields documented at its top; series and file come from `ACTIVE_CHANGELOG`) writes one release's paperwork: the active changelog entry, the CHANGELOG.md line, the four version locations, the closed TD rows (`closes[]`) moved to the active series section of `TECH_DEBT_ARCHIVE.md` with the counts and «آخرین بازبینی», new open rows of a documentation release (`openRows[]`), the fixed known-findings classes replaced by a «رفع شد» comment, and exact-text edits of the roadmap, audit report and AGENTS.md; nothing is written when any step fails; then run `npm run check:version`. Covered by Vitest `releaseTool.test.ts`. Parallel lanes take versions, migration numbers and audit report section numbers at merge time: `npm run release:renumber -- origin/master` (`scripts/release-renumber.ts`) merges the base without committing, resolves the conflicts of the release files (changelogs, TECH_DEBT, migration journal, the four version locations; any other conflict is resolved by hand and the command run again), moves the branch's own ones after the base's, rewriting only lines the branch added (comment lines outside Markdown), stages the result and runs `check:version` and the migration plan test (Vitest `releaseRenumber.test.ts`).

- **Release Version Bump = 4 Synced Locations (enforced by `npm run check:version`):**
 1. `"version"` in `package.json` (single source of truth; dynamically resolved by `src/lib/version.ts` and `/health`).
 2. Top entry in active changelog `src/data/changelogs/11.ts` (`ACTIVE_CHANGELOG` in `src/data/changelogs/index.ts`).
 3. `deploy/k8s/erp-deployment.yaml` — both the image tag (`erp:vX.Y.Z`) and the `APP_VERSION` env value (it overrides `package.json` at runtime).
 4. Header line of `README.md` (`نسخه مستقر: \`vX.Y.Z\``).

- **Commit & Push:** Commit with descriptive English messages on a separate branch, one branch per topic, and open a draft pull request; never push directly to `master`. Before a merge: merge `master` into the branch, run `npm run release:renumber -- origin/master`, run the fast checks, push and wait for every CI job. A pull request merges only when every check is green, it has no conflict and `master` has not moved; an agent merges its own pull request only under the product owner's standing permission and after the coordinator's go. The same applies in local development whenever Git credentials allow a push.

- **Exclusions:** Never commit `.env`, local database directories (`/pgdata`, `/logs`), or source archives.

- **Vendored SheetJS (audit P2-13 / TD-173):** `xlsx` (a devDependency since v7.0.84) is installed from `vendor/xlsx-0.20.3.tgz` (the official SheetJS build, published only on cdn.sheetjs.com — the npm `xlsx@0.18.5` is vulnerable). This tarball is the one allowed third-party archive in the repository. Upgrade only by replacing it with a newer official tarball and updating the `package.json` reference and lockfile; never switch back to the npm package.

- **Runtime vs Dev Dependencies:** `dependencies` holds exactly the packages the server bundle requires (the Docker image installs only these with `npm ci --omit=dev`); frontend-only libraries (React, icons, fonts, xlsx …) go in `devDependencies`. Enforced by `npm run check:runtime-deps` and Vitest `runtimeDependencies.test.ts`. The audit gate (`npm run audit:gate`) reads `npm audit` over all dependencies so browser libraries stay covered, and fails when `npm audit` itself fails.

- **Conflict Handling:** When `master` has moved, merge it into the branch (never rebase a pushed branch) and resolve release files with `npm run release:renumber`; never force-push someone else's branch.
