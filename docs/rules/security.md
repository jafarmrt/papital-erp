# Security, Access and Audit

Sessions, permissions, read scopes, audit rows, secrets and log sanitization.

Core rules (one line each, with their guards) are in `AGENTS.md`. This file holds the full rules of the area; the history of each rule (versions, debt rows, decisions) is in `docs/rules/archive/AGENTS_V10.md` at commit `c3c9858` (archives removed in v11.1.0), and a «§N» below refers to that file's numbering.

- **HttpOnly Cookies:** JWT tokens are issued and stored exclusively via secure HttpOnly cookies (`auth_token`, `secure: true`, `sameSite: 'none'`, `path: '/'`). Browser JS MUST NOT store or read raw tokens in `localStorage`. All client fetch calls MUST specify `credentials: 'include'`.

- **No Token in Response Bodies:** Login/setup responses MUST NOT include the JWT by default. The only exception is the opt-in compatibility flag `EXPOSE_TOKEN_IN_BODY=true` for preview environments whose browsers block the iframe cookie (BUG-08); production deployments must leave it unset. In production the CSP lets only the app itself frame it and be connected to, plus the origins in `FRAME_ANCESTORS` / `EXTERNAL_API_ORIGINS` (`buildCspDirectives` in `src/lib/cspDirectives.ts`).

- **Login Lockout per Username + IP:** The progressive login lock (5 failures → 1, 2, 4 … at most 30 minutes) applies to the (username + client IP) pair, held in memory (single instance); the whole account (`users.locked_until`) is locked only after `ACCOUNT_LOCKOUT_THRESHOLD` = 50 failures from any address within 24 hours (`src/services/auth/loginSecurity.service.ts`). Unknown usernames behave identically; no CAPTCHA. Both 429 lock answers (this lock and the per-address login limiter, with the minutes left of its window) carry `locked: true` and `remainingMinutes` and the Persian-digit messages of `src/lib/auth/loginLockout.ts`; the login page counts down only from those two fields, never from the message text, and a 429 of the general request limiter is an error, not a lock. A wrong current password in the profile password change (`PUT /users/profile`) counts per user with the same progressive lock; while locked, even the right password is 429 `PASSWORD_CHANGE_LOCKED` with `locked` and `remainingMinutes` in `details`, and a right password ends the streak (`passwordChangeLockMinutes` / `recordPasswordChangeFailure` in the same service).

- **Session Verification & Logout:** Use `/api/auth/me` to verify session on load, and `/api/auth/logout` to clear the cookie. Login, logout and setup are exempt from CSRF, so they accept only the application's own origin (`sessionEndpointOriginGuard` in `src/middleware/sessionOrigin.ts`): the browser origin (`Origin`, else `Referer`) must be the request's own host, in `ALLOWED_ORIGINS` (never `*`) or `APP_URL`, plus localhost and Google preview hosts outside production; `Origin: null` is refused and a request with neither header (a non-browser client) passes. Logout with a valid session cookie requires that session's `x-csrf-token` (403 otherwise); an invalid or expired cookie is only cleared. Every login is one row of `user_sessions` (migration 0129: a random `sid` carried in the token, device user-agent, IP, sign-in and last-use time; `src/services/auth/sessionStore.ts`), and `authenticateToken` refuses a token whose session is closed or missing (`checkSession`, cached 30 s per sid and dropped from the cache when the session closes, so a close takes effect on that device's next request); a token from before it is adopted once under a key of its CSRF value, else its issue time (`legacySessionId`). Logout closes only this device's session, in one upsert so an old token's row adopted meanwhile is closed too, with the user's stored full name in its audit row, and its buttons say «خروج»; the profile lists the user's devices with this one marked and a name read from the user-agent without a library (`deviceLabelOf` in `src/lib/auth/deviceLabel.ts`), closes one other device (`DELETE /auth/sessions/:id`, this one is 422 `SESSION_IS_CURRENT`) or all the others (`POST /auth/sessions/close-others`, which reissues this device's cookie), and the users page closes one or all devices of another user with `users.manage` (`/users/:id/sessions`, the TD-520 grant rule, an admin account only by the system admin), each close audited with `tx` (`src/services/auth/userSessions.service.ts`, `UserSessionsPanel`, which warns an admin closing all devices of their own account there that this device signs out too); a token version raise (password reset, role change) still ends every session (it replaces the v10.1.60 «خروج از همهٔ دستگاه‌ها» logout of OBS-R1-27). The device that closes its other devices or changes its own password keeps its previous token for `TOKEN_VERSION_GRACE_MS` (60 s, set right after the change commits, only for that session row and only while the user's version is the one the change set; `src/services/auth/tokenVersionGrace.ts`), so a request it sent a moment before is not refused and the device is not signed out. A request let in this way is marked `req.user.tokenGrace` and gets 409 `TOKEN_GRACE_REFUSED` on anything that issues a token or manages sign-ins and users (`renewSessionCookie`, close-others, closing a session, `PUT /users/profile`, every write under `/users`, `/roles` and `/messenger`; `refuseTokenGrace`), so a stolen copy of the old cookie cannot keep the account a password change takes from it. The daily operational purge removes session rows that ended (closed or expired) more than 90 days ago and have expired (`purgeEndedSessions` in `src/services/auth/sessionPurge.ts`, `scripts/ratchets/HARD_DELETES.md`). Every password is at least `MIN_PASSWORD_LENGTH` = 8 characters (`src/lib/auth/passwordPolicy.ts`, shared by the routes and the forms). A password an administrator sets for another user (create, reset, restore) is temporary (`users.must_reset_password = 1`), one set for one's own account is not: until the user changes it from the profile, `authenticateToken` refuses every request except `/auth/me`, `/users/profile`, `/users/my-permissions`, `/csrf` and logout with 403 `PASSWORD_RESET_REQUIRED` (`src/lib/auth/passwordReset.ts`), and the browser shows only the password form, closed only by «خروج».

- **Route Middleware Order:** Administrative/utility/seed routes MUST be registered AFTER `router.use(authenticateToken)` and protected via `requireSystemAdmin` (system maintenance) or `requirePermission` (everything else).

- **Role vs Permission Namespaces:** Permission keys always contain a dot (`customers.manage`); role codes never do (`ROLE_CODE_PATTERN = /^[a-z0-9_-]+$/`, enforced on role creation). `authorizePermission` / `userHasRoleOrPermission` match the role's permissions only against permission keys; `admin` always passes.

- **No Role Codes in Route Guards:** `authorize` is gone and no route guard takes a role code. A route asks catalog permission keys (`authorizePermission` / `requirePermission`), or is one of the system maintenance routes in `SYSTEM_ADMIN_ONLY_ROUTES` (`src/tests/security/routeAccessPolicy.ts`: backup, clear data, activity-log purge, attachment cleanup and migration, orphan image cleanup, default categories and chart of accounts, system health, environment, date calendar report, event reconciliation, conditional migration constraints) guarded by `requireSystemAdmin`, and `/metrics` is for the system admin too; the policy test checks the list both ways. Defining warehouses needs `warehouse.manage`, running the fiscal-year close `accounting.fiscal_close`, deleting a material request `pending_materials.delete`, and the activity log `audit_logs.view`. A legacy `*` in a role's permissions grants nothing. Migration 0062 gave each seed role (`is_system = 1`) the guard permission it had passed only by its code, expanded a non-admin `*` into every catalog key, and logged each change in `activity_logs`; custom roles were left as they were. Only the system admin role is a system role: migration 0067 set `is_system` to 1 on the admin row and 0 on every other role, logged in `activity_logs`, and `DELETE /roles/:id` refuses only the system admin role (a role with active users or needed by a workflow step is still refused; deleted users do not count). The system admin role's permissions are computed, never stored or edited: `GET /roles` lists it with every catalog key, `PUT /roles/:id` refuses its permissions (409 `SYSTEM_ADMIN_ROLE_FIXED`) and lets only the system admin change its name and description, and the role form shows its ticks all set and locked.

- **Shared Permission Catalog With Dependencies:** The permission catalog lives only in `src/lib/permissions/permissionCatalog.ts`, shared by the server and the browser (`GET /api/permissions` serves it). A key that is useless without another names it in `requires`: every action key of a group requires that group's view key, and `accounting.treasury_no_voucher` requires `accounting.treasury`. `POST /roles` / `PUT /roles/:id` store `withRequiredPermissions(requested)` and record the added keys in the audit row (`addedByRequirement`); the role form ticks a key's requirements, unticks its dependents (`withoutPermission`) and shows what saving an older role will add. A new catalog key that needs another key declares it there.

- **One Permission Check and Ratchets:** `can(user, ...permissionKeys)` in `src/middleware/authorize.ts` is the one permission check: the system admin (`SYSTEM_ADMIN_ROLE`, the only role code that code may name) passes, any other user passes only when the role holds one of the keys, and a dot-less argument throws. `requirePermission(...keys)` is the route guard built on it and refuses, when the router is built, a key outside the catalog or a role code; `authorizePermission` is the same guard under its old name. New checks use `can` / `requirePermission`, never a role code. `npm run ratchet:permissions` (`scripts/permission-ratchet.ts`, baseline `permission-ratchet-baseline.json`, run by Vitest `permissionRatchet.test.ts`) fails when a production file gains a role-code literal, a permission-shaped literal is not a catalog key, or a catalog key is checked by no server code; a lower count fails until the baseline is lowered with `-- --update`. Never raise the baseline. Buttons follow the same rule: an action is shown by the permission its API asks (`useHasPermission`), never by a role code or `*` — the customers page by `customers.manage` (its delete button by `customers.delete`, the key `DELETE /customers/:id` asks), the documents list's row and details buttons by `accounting.treasury` (settlement), `documents.edit` (notes), `documents.delete` (void) and the workflow widget's keys (`INVOICE_ROW_ACTION_PERMISSIONS` in `src/lib/invoices/invoiceRowAccess.ts`, `WORKFLOW_WIDGET_PERMISSIONS`, `useHasAnyPermission`), a sales file's delete by `crm.delete` (the sales file lists render it only with a delete handler), the stock document form's item definition by `products.create` / `products.edit`, and the stock document page's directions, document types and submit button by the permission recording that type final asks (`stockPageAccess` in `src/lib/documents/stockDocumentAccess.ts`, built on `documentTypeRecordPermission`; a type the user cannot record is not offered and the button says which permission is missing), and the project screens (list, detail, inventory control, delivery, progress matrix, workshop schedule, material allocations) by the keys of `src/lib/permissions/projectPermissions.ts`, which their routes read too (`useProjectPermissions`). The events page opens with `events.view` (its route and API) and every change button of its sub-tabs (rules, outbox, dead letters, timeline replay, webhooks, event simulation) shows only for `events.manage`, the key each change route of `/events` asks. The top bar and the profile show the role's stored name, which `/users/my-permissions` returns to every user, the system admin included; no label is built from a role code. Code names the system admin only through `SYSTEM_ADMIN_ROLE` (server) or `userPermissions.isAdmin` (browser), and an unknown actor is recorded as «سیستم», never as `admin`.

- **Document Permissions by Type and Status:** One table says which permission records a document (`documentRecordPermission` in `src/lib/permissions/documentPermissions.ts`, shared with the invoice form): a sales document (`invoice`, `proforma`, `return`) as draft or proforma needs `documents.create`, final or finalized `documents.finalize`; a warehouse document `warehouse.in` / `warehouse.out` by the stock direction of its type (`stockDirectionOf` in `src/services/documents/documentRecordRule.ts`, the function the services move stock with); a stock count `audit.apply`; a production receipt `warehouse.production_receipt`. `POST /documents`, `PUT /documents/:id/finalize` and the workflow approval step (the document action's `requiredPermissions` reads the document) check it with `can`, never a role code. A draft stays a draft; an `invoice` proforma recorded by a user without `documents.finalize` is stored as type `proforma`, as before. Migration 0063 gave `documents.finalize` to the seed manager, warehouse keeper, accountant and CFO and to roles expanded from `*`, logged in `activity_logs`. Deleting a party needs `customers.delete` (requires `customers.view`) and the catalog has no `audit.create`, which opened nothing: migration 0123 gave `customers.delete` to every role holding `customers.manage` and removed `audit.create` from every role, each change logged in `activity_logs`.

- **Personnel and Payslip Bank Details by Permission:** Card, Sheba and account number and the Nobitex username are unmasked only for the system admin, the record's own linked user, and holders of `personnel.view_sensitive` or `personnel.manage` (personnel dossier) or `payroll.view_sensitive` or `personnel.manage` (payslips) — `canAccessSensitivePersonnelData` / `canAccessSensitivePayrollData` in `src/lib/piiMasker.ts`, through `can`; no role code and no `*` opens them. Migration 0064 gave both keys to the seed manager and the other key to roles holding one of them, logged in `activity_logs`.

- **Notification Recipients by Permission:** An event rule's in-app notification goes to one user (`targetUserId`), to the holders of a catalog permission (`targetPermission`: the system admin and every non-deleted user whose role holds the key, `permissionHolderUserIds` in `src/services/notifications/notificationRecipients.ts`; an unknown key is refused with 422), or to a role the admin chose in the rule (`targetRole`, data); without a target to the system admin. The default reorder alert targets `warehouse.view`, a won sales lead notifies the holders of `crm.manage` except its sender, and the rule editor picks the permission from the catalog. Code never names a recipient role other than `SYSTEM_ADMIN_ROLE`; rules already stored were left as they are.

- **Due Follow-up Reminders:** the notification bell reminds a user only of their own due follow-ups (`generateCrmDueReminders` / `ownDueFollowupCondition` in `src/services/notifications/crmDueReminders.ts`, on the follow-up condition of TD-428), scanning them at most once an hour per user (`generateCrmDueRemindersThrottled`, the workshop reminder's throttle with its own map): the assigned personnel's linked user (`personnel.user_id`), else, for a legacy row without a personnel id, the trimmed assignee (or logger when empty) equal to the user's full name or username; never «contains». Dismissing a notification (`DELETE /notifications/:id`) keeps its row and sets `notifications.dismissed_at`; the bell list and the unread count (in SQL) skip dismissed rows, and a due reminder is inserted with ON CONFLICT DO NOTHING on the partial unique index `uq_notifications_due_reminder` (user, type, link of `crm_due_task` rows, dismissed ones included; migration 0089, created only on data without duplicates, which the financial health check lists as `notification_reminder_uniqueness`), so a dismissed reminder never comes back and concurrent bell requests make one.

- **Read Scope by Section Permission:** Global search returns each section only to holders of its view permission (items `products.view`, customers `customers.view`, documents/invoices `documents.view`, projects `projects.view`; a section without permission is empty, never an error); it folds Arabic «ي» / «ى» / «ك» and Persian and Arabic digits on both sides with `normalizeSearchText` (`src/lib/search/searchText.ts`, also used by `SearchableSelect`) and ranks each section exact match, then starts with, then contains; its text is at most `GLOBAL_SEARCH_MAX_LENGTH` (100) characters, and a query of at least four digits also finds customers by the TD-296 phone key. Kardex list `GET /api/transactions`: `warehouse.view` OR `accounting.view`. Warehouse dashboard statistics (`/api/stats`, `/api/dashboard-bi-stats`) and the «وضعیت انبار» page: `reports.view` OR `warehouse.view`. Menu items and page routes use the same permissions as their API: menu links, page routes (`ProtectedRoute page=`), dashboard shortcuts, the accounting page tabs and the settings tabs read one table, `PAGE_ACCESS` / `SETTINGS_TAB_ACCESS` in `src/lib/permissions/pageAccess.ts`, where each page names its main API; every key that opens a page or tab passes the guards of those APIs and a system-admin page or tab has system-admin APIs (`sec_page_access_matches_api_td_668`, Vitest `pageAccessTable.test.tsx`), a settings tab the user cannot open is not rendered even from `?tab=`, and the WooCommerce tab edits the store URL and keys only for the system admin (`SYSTEM_ADMIN_SETTING_KEYS` in `src/lib/settings/settingKeyAccess.ts`, shared with `SystemSettingsService`). A key may name route parameters (`:name`, and `:name?` for an optional segment): `pageAccessRule` reads the key itself first, then the address without its query string, then matches a real address against the parametrised keys, so `/projects/:projectId/:tab?` and `/projects/7/progress` both reach the project row. A new page gets a row there with its main API; a tab inside a page is shown by the keys of its own API too (the «تخصیص مواد به پروژه‌ها» tab of `/audit` by `READ_PERMISSIONS.bomAllocations`, the guard of `GET /inventory/allocations`). There is no per-role menu hiding: the menu is built from permissions only, and the retired `menu_visibility` setting is ignored on save. The workflow widget `GET /workflow/instance/:entityType/:entityId` also requires the entity's own read permission (`WORKFLOW_ENTITY_READ_PERMISSIONS` in `src/lib/recordReadPermissions.ts`: document, journal voucher, item, bank account, purchase requisition; else 403). Daily work log statistics count only the logs the user may see in the list (`canSeeDailyLog`). Reviewing, editing or deleting another user's daily work log and reading private ones need `daily_logs.manage_all` (`canManageAllDailyLogs` in `src/services/dailyLogs/dailyLogAccess.ts`, never a role code; the review route is guarded by it), and every daily log write runs in one transaction with its notifications and its audit row (`src/services/dailyLogs/dailyLogWrite.service.ts`). A mention notifies only a mentioned user who may read the log (`mentionNotifies` in `src/lib/dailyLogs/dailyLogVisibility.ts`), so a private log notifies nobody and the form says so; an edit notifies only new mentions. Mentioned and allowed users and the project of a daily log are positive ids (400 otherwise) of existing, non-deleted rows (422 `DAILY_LOG_USER_NOT_FOUND` / `DAILY_LOG_PROJECT_NOT_FOUND`, nothing written), and the project name is the project's title. A daily log is never public: its visibility is `mentioned_only` (default), `private`, `managers` or `custom` (`DAILY_LOG_VISIBILITIES`, CHECK `chk_daily_work_logs_visibility`), the form offers the first two, and migration 0075 moved public, `all` and empty logs to `mentioned_only` with the old value recorded in `daily_log_visibility_repairs`. The daily log list and its statistics are read in SQL with the visibility rule (`listDailyLogs` / `dailyLogStats` in `src/services/dailyLogs/dailyLogRead.service.ts`): the list is paged (`page`, `limit` at most 100, `{ data, total, page, limit }`), today's hours count only logs whose work date is today, and the management summary reads one day or one Jalali month. A daily log's title (200), text (20,000), tags (20 of at most 50 characters) and manager notes (20,000) are capped by `src/lib/dailyLogs/dailyLogLimits.ts`, shared by the schemas and the form. Its start and end are times of day (Persian digits read) with the end after the start, so an overnight shift is two logs (422 `DAILY_LOG_WORK_TIME_INVALID`, `workTimeError` / `workHoursBetween` in `src/lib/dailyLogs/workHours.ts`, shared with the form). Its work mode is `onsite` or `remote` (`DAILY_LOG_WORK_MODES` in `src/lib/dailyLogs/workMode.ts`); legacy leave, mission and hybrid logs are kept, the summary counts them as «سایر» and a leave's hours are not work hours. `PUT /daily-logs/:id` requires the log's `version` (400 without it) and refuses a stale one under the row lock with 409 `OCC_CONFLICT`; the edit raises it, review and delete do not, and the form sends the version of the log it opened. User input in LIKE / ILIKE patterns goes through `containsLikePattern` / `startsWithLikePattern` / `escapeLikePattern` (`src/lib/sqlLike.ts`); a unit test rejects `%${…}`, `'%' +` and template literals passed straight to `like` / `ilike`.

- **Read Permissions for All Read Routes:** Every read route that returns business data is guarded with `authorizePermission(...READ_PERMISSIONS.<section>)` from `src/lib/recordReadPermissions.ts` (any one permission suffices: the section's view permission plus the permissions of pages/forms that pick from that list — add a page's visibility permission there when a new page consumes a list; a section with an options endpoint gives forms that endpoint instead, see Pick Lists for Forms). Payroll amounts: `piecework.payroll` / `piecework.pay` / `personnel.manage` / `accounting.treasury` (own payslips via `/piecework/payrolls/mine`; `piecework.pay` since v9.0.320). The personnel list and detail (`GET /personnel`, `/personnel/:id`) give pick-list readers only id, names, personnel code, job title, status and linked user id; the full dossier only to `personnel.view` / `personnel.manage`, the salary only to the payroll-amount permissions, and the Nobitex password only in the detail (`personnelReadScope` / `scopePersonnelRow` in `src/services/personnel/personnelFieldScope.ts`). The list is searched (only over the fields its reader sees, spaces, zero-width marks, «-» and «_» dropped and «ة» / «ۀ» read as «ه» on both sides, `compactSearchText` / `compactFoldedSearchSql`) and filtered in SQL (`activeOnly=1` leaves out personnel who left): with `page` it answers one page `{ data, total, page, limit, stats }` and without it the pick-list array, uncapped without a `limit` and capped at `PERSONNEL_PICK_REQUEST_LIMIT` (`listPersonnelRows` in `src/services/personnel/personnelList.ts`, contract `src/lib/personnel/personnelList.ts`); the personnel page reads one page (`usePersonnelPageQuery`, its range label following the rows shown) and every personnel only while its form or Excel window is open, whose user picker and file upload wait for that list; a pick list keeps `PERSONNEL_PICK_LIMIT` (5000, newest first; the sales seller list only personnel who have not left) and asks one row more, so only a list the server cut says so in Persian, once per session (`takePersonnelPick`), and a voucher row or sales file whose personnel the list does not hold keeps it as its chosen option with its stored name, else the name read by id (`usePersonnelPickName`). A system user is linked to at most one active personnel and only when the user exists and is not deleted: `resolvePersonnelUserLink` (`src/services/personnel/personnelUserLink.ts`) locks the user row in the personnel save transaction (422 invalid user, 409 linked elsewhere), backed by the partial unique index `uq_personnel_user_active` (migration 0053, created only on data without duplicates; the financial health check lists duplicates as `personnel_user_link_uniqueness`), and `/piecework/payrolls/mine` refuses a user with a legacy duplicate link with 409. In the personnel Excel import an empty gender, employment-status or nationality cell leaves an existing personnel's value unchanged and gives a new personnel the default (`src/lib/personnel/personnelImportCells.ts`, shared by the server and the preview). Every personnel create, edit, delete and Excel row writes its own audit row with `req` and `details` — `after` on create, `before` on delete, only the changed fields on edit (`personnelAuditChanges` in `src/services/personnel/personnelAudit.ts`); the Nobitex password never enters the audit, only `nobitexPasswordChanged`. A personnel's `monthlySalary` goes through `decimalInput` and is non-negative; an empty form field is 0 and a missing field on edit keeps the current salary. A non-empty personnel code is unique among active personnel: the key is `lower(btrim(personnel_code))`, checked by `assertPersonnelCodeAvailable` (`src/services/personnel/personnelCode.ts`, also the Excel import's lookup key) and enforced by the partial unique index `uq_personnel_code_active` (migration 0054, created only on data without duplicates; the financial health check lists duplicates as `personnel_code_uniqueness`). A non-empty national ID is unique among active personnel the same way, on create, edit (only when it changes) and each Excel row: key `btrim(national_id)`, `assertPersonnelNationalIdAvailable` (`src/services/personnel/personnelNationalIdUnique.ts`, 409 `PERSONNEL_NATIONAL_ID_TAKEN`), partial unique index `uq_personnel_national_id_active` (migration 0122, created only on data without duplicates; the health check lists them as `personnel_national_id_uniqueness`), and once the duplicates are gone the system admin builds a skipped index, this one or `uq_personnel_code_active`, from the missing-constraints card (`CONDITIONAL_CONSTRAINT_RULES`). A personnel is never deleted while it has open business: `DELETE /personnel/:id` locks the personnel row and `assertPersonnelDeletable` (`src/services/personnel/personnelDeleteGuard.ts`) refuses with 409 `PERSONNEL_HAS_OPEN_ITEMS` and Persian reasons a draft, approved or partially paid payroll, a work log free of a live payroll, a nonzero approved/permanent balance in any currency on non-temporary accounts of the personnel's detailed rows, or a draft voucher row; the message suggests «قطع همکاری». `PUT /personnel/:id` requires the record's `version` (400 without it) and writes with the version in its WHERE (409 `OCC_CONFLICT` when stale or changed meanwhile); the Excel import advances the version too. Persian personnel UI text has no English words or «اکانت» / «کلیپ‌بورد» (Vitest `personnelWording.test.ts`). A party's bank details (`bankInfo`: bank, account, Sheba, card) go only to admins and holders of `customers.view`, `customers.manage` or any `accounting.*` permission (`PARTY_BANK_INFO_PERMISSIONS` / `partyRowsForUser` in `src/services/customers/partyBankInfoAccess.ts`); `GET /customers` (list and `export=true`) and «تبدیل به مشتری» drop them for every other reader. The full treasury account list (`GET /accounting/bank-accounts`, `/accounting/banks`) with account, card and Sheba numbers and balances goes only to treasury readers (`READ_PERMISSIONS.bankAccounts`: `accounting.treasury`, `accounting.reports`, `accounting.view`); forms that only pick an account read `GET /accounting/bank-accounts/options` (id, code, title, type, bank name, currency, `hasLedgerAccount`; `READ_PERMISSIONS.bankAccountOptions`, `getBankAccountOptions` in `src/services/accounting/treasury/bankAccountOptions.ts`). Treasury receipts, payments, bank transfers, a cheque's issue date and every cheque action date go through `resolveTreasuryWriteDate` (`src/services/accounting/treasury/treasuryDate.ts`): empty is the business today, the date is read with `requireStorageDate` (a non-existent day such as 1404/12/30 is 422, never moved to another day or fiscal year) and a date after the business today is 422 `TREASURY_DATE_IN_FUTURE`; a cheque's due date may be in the future. The cheque status form sends the action date (default today). `jalaliToIsoDate` / `normalizeDateToIso` calls in `MONEY_STOCK_PATHS` only decrease (Vitest `looseDateConverters.test.ts`). A treasury account's currency comes from `TREASURY_CURRENCIES` (`src/lib/treasury/treasuryCurrency.ts`, the §6 list; the bank account form offers it, another code is 422 `BANK_ACCOUNT_CURRENCY_INVALID`) and is fixed once the account has a treasury row (voided ones included), a cheque or an opening balance: `updateBankAccount` refuses a change under the bank row lock with 422 `BANK_ACCOUNT_CURRENCY_LOCKED` (`assertBankCurrencyChangeAllowed` in `src/services/accounting/treasury/bankAccountCurrency.ts`). Its ledger account is fixed after the same first movement too (422 `BANK_ACCOUNT_LEDGER_LOCKED`, `assertBankLedgerChangeAllowed`, same file; an account without a ledger account may take one). An account that issued a paid cheque not yet cleared (received, in the treasury, in the safe or in collection) keeps a bank or cash type, since that cheque clears only from it (422 `BANK_ACCOUNT_TYPE_HAS_OPEN_PAID_CHEQUES`, `assertBankTypeChangeKeepsPaidCheques`, same file). A treasury account's ledger account, on create and when it changes, is an active, non-deleted subsidiary under general account 10 «موجودی نقد و بانک» (`requireBankLedgerAccount` in `src/services/accounting/treasury/bankLinks.ts`, else 422 `BANK_LEDGER_ACCOUNT_INVALID`), and a cheque's bank account is an active, non-deleted treasury account read `FOR SHARE` (`requireChequeBankAccount`, else 422 `CHEQUE_BANK_ACCOUNT_INVALID`). Treasury and cheque amounts, opening balances and exchange rates in `src/routes/accounting/accounting.schemas.ts` use `decimalInput` (a positive amount required) and their currency is `TREASURY_CURRENCIES` after `normalizeTreasuryCurrency`. Bank balances (`computeBankBalances`) are summed in SQL with `GROUP BY`, reading only the treasury accounts' ledger accounts and bank-tagged rows; `GET /accounting/treasury` with `page` / `limit` returns `{ data, total, page, limit }` filtered by type, method, account, date and search in SQL, with each row's running balance for a single-account filter (`pageTreasuryTransactions` in `src/services/accounting/treasury/treasuryTransactionList.ts`); the running balance counts the rows the bank's treasury balance counts — a voided row on its own date and its reversal on the void date, never a legacy cheque-method row — so the last row equals that balance, and the treasury page and the reconciliation window never load the whole list. Bank statement reconciliation (`POST /accounting/treasury/reconcile`, `reconcileTreasuryRows` in `src/services/accounting/treasury/bankReconciliation.ts`) refuses an id that is missing, of another bank or voided with 422 `TREASURY_RECONCILE_ROWS_INVALID` listing them and writes nothing; it writes and audits (with `tx`) only the rows whose state changes, and `reconciled_at` is the server UTC timestamp. A cleared cheque is a reconciliation candidate too: `GET /accounting/treasury/reconcile-cheques` lists the bank's cleared cheques with their clearing date (`listReconcilableCheques`, contract `src/lib/treasury/reconcilableCheque.ts`) and the same route reconciles them with `chequeIds` (`cheques.reconciled` / `reconciled_at` / `reconciled_batch`, migration 0108). A cheque status change and a cheque delete are audited inside their transaction with `before` / `after` (status, its Persian label from `CHEQUE_STATUS_LABELS` in `src/lib/treasury/chequeTransitions.ts`, bank account) and the vouchers issued, deleted or reversed (`src/services/accounting/treasury/chequeAudit.ts`). A treasury receipt or payment, a bank transfer, a treasury void, a new cheque, a treasury account's create, edit and delete and the bank balance sync write their audit row in their own service transaction with the request (`src/services/accounting/treasury/treasuryAudit.ts`; a refused audit row refuses the write), never from the route after commit. Cheque messages, the default history note and the cheque page name statuses only through `chequeStatusLabel`, never their codes; the history window reads `notes`. The treasury, transfer and cheque forms and the treasury and cheque date filters use `JalaliDateInput` with ISO state; a treasury form for an account without a ledger account says registration is impossible and does not submit; the treasury Excel export uses `treasuryExportRows` / `treasuryExportFileName` (`src/lib/treasury/treasuryExport.ts`: Persian party type and method, Jalali file date). Full user and role directory: `users.manage` / `roles.manage` / `personnel.manage` / `workflow.manage` / `settings.manage`; the «مدیریت کاربران و نقش‌ها» page and menu open for `users.manage` or `roles.manage`, each tab offers only its own permission's actions, and the forms apply the TD-520 grant rule (only roles whose keys the user all holds, own account's role locked, no unheld key ticked); `/users/list-simple` (id, user name for mentions, full name, picture and `role_name`, the role's stored Persian name — never the role code), categories, warehouses and the user's own data stay login-only, and so does `GET /settings`, which gives the system admin and holders of `settings.manage` every setting (secrets masked for all but the system admin) and any other user only the shared settings (company, currency, time zone, price lists, movement days, project presets), plus the WooCommerce connection with its keys masked for `woocommerce.view` (`isSettingReadable` in `src/lib/settings/settingReadScope.ts`).

- **Pick Lists for Forms:** A form that picks a record of another section reads that section's options endpoint, which carries only what picking needs (URLs and fields in `src/lib/permissions/pickLists.ts`, permissions in `READ_PERMISSIONS`); the section's full list opens only with the section's own keys. Vitest `pickLists.test.ts` fails when a full list gains another section's key or browser code outside the section fetches the full list. Customers: `GET /customers/options` (contact card without notes or version; bank details by the TD-433 rule) for document, warehouse, CRM, project, procurement, reorder and accounting forms; `GET /customers` needs `customers.view`. Items: `GET /items/options` (code, name, unit, category, attributes and per-warehouse stock; the average cost only for `products.view`) for document, warehouse, stock count, project, procurement, CRM and transfer forms; `GET /items` and `/items/next-code` need `products.view` or `products.edit_price`, `/items/reorder-alerts` the page's keys. Projects: `GET /projects/options` (code, title, status, customer name) for stock document, project inventory, material allocation, piecework and daily log forms; `GET /projects` needs `projects.view` and is one summary page (`page`, `limit` default 50 and at most 200, `search`, `status`, `priority` in SQL; `{ data, total, page, limit, statusCounts }`, each row only `PROJECT_LIST_ROW_FIELDS` and its stage summary; `listProjectPage` in `src/services/projects/projectList.ts`, contract `src/lib/projects/projectList.ts`), whose products, inventory control, schedule and attachments come only with the project record; a project record and its attachments need `projects.view` or `warehouse.view` (project inventory page). Documents: the full list needs a `documents.*` view, create or edit key and always answers one page (`page`, `limit`; default and `limit=0` give 50, `{ data, total, page, limit, totalPages }`; the whole list only with `export=true`; the stock count history and transfer tabs page through it with `typedDocumentListUrl` in `src/lib/documents/documentListPage.ts`); a record and its attachments also open for `workflow.view`; `audit.view` lists and reads only stock count and transfer documents (`readableDocumentTypes` in `src/services/documents/documentReadScope.ts`, else 403 `DOCUMENT_TYPE_NOT_READABLE`); the stock count sheet needs `audit.view`; a party's documents `documents.view`, `customers.view` or `crm.view`; a document's treasury rows (`settlements`: number, method, tracking number, bank account, description) go only to treasury readers (`READ_PERMISSIONS.treasuryTransactions`), other readers get its paid amount, balance and settlement status (`documentForReader` in `src/services/documents/documentReadScope.ts`). Item prices: all prices and the price history need `products.view` or `products.edit_price`; one item's sale prices also open for `documents.create` / `documents.edit` (invoice and remittance form). - **Audit Logging & Snapshots:** All state mutations (customers, items, prices, documents, stocks, permissions) MUST log via `logActivity` in `src/lib/auditLogger.ts` with before/after snapshots. Every audit row carries the trace id of the request that wrote it (`activity_logs.trace_id`, migration 0102, filled by `logActivity` from `req.requestId` or the request context), the id of the error answer and the log files. A document's create, edit, finalize, notes change and void each write one audit row with the change's own `tx`, holding the stored document before and after it (`documentAuditSnapshot` / `documentAuditDetails` in `src/services/documents/documentAudit.ts`; the edit reads «before» under the document row lock, `updateDocument` / `updateDocumentNotes` / `finalizeDocument` return the pair, a finalize of an already final document writes none, and the void's single `DELETE` row is written by `deleteDocument` with the caller's actor and note). Order delivery and «دریافت کالا» write the same finalize row, with the same `tx`, for each order they finalize (entity «اسناد انبار», the document id, `documentAuditDetails` of the pair `finalizeDocument` returns, plus their `operation`), so delivery writes one row per order. The audit purge (`POST /activity-logs/purge`, system admin) deletes only rows older than the fixed 90 days whose entity is one of the operational sections in `PURGEABLE_AUDIT_ENTITIES` and whose action is not in `CRITICAL_AUDIT_ACTIONS` (`src/lib/audit/auditRetention.ts`, shared with the purge form); every other entity name (financial, security, role and user events, old or unknown names) is never purged, and the API has no option to turn that off or to go below 90 days. Every entity name the code writes is classified there (Vitest `auditEntityRetention.test.ts`), so a new name is classified in the same change. The activity log's text search compares one expression of description, user full name, username and entity joined by `E'\x1f'` (`activityLogSearchText` in `src/db/schema/auth.ts`), which the GIN trigram index `activity_logs_search_trgm` covers (migration 0132), so a search never matches across two columns and reads the index; the search text drops NUL and the separator (`activityLogSearchTerm`) and a search page is read in its own transaction with `work_mem` 64 MB (`withActivityLogSearchMemory`).

- **Third-Party Secrets Encrypted at Rest:** Passwords of third-party accounts (the personnel Nobitex password) are stored only through `encryptSecret` / read through `decryptSecret` (`src/lib/secretBox.ts`, AES-256-GCM, key `ERP_SECRETS_KEY` separate from `JWT_SECRET`, format `enc:v1:`). Without the key a new secret is refused (503), never stored in plain text; ciphertext never leaves the server; the personnel form and detail view show the Nobitex password masked until «نمایش رمز» (`NobitexPasswordFields.tsx`); plain-text legacy values are encrypted with `npm run secrets:encrypt -- --apply`. `install.sh` writes a random `ERP_SECRETS_KEY` and `ERP_WEBHOOK_SECRET_TOKEN` through `scripts/ensure-env-secrets.sh` (adds only missing keys; `update.sh` runs it for `ERP_SECRETS_KEY` alone before its backup when that key is missing, an `export` or indented line counting as present) and `go-live-verify.sh` fails without the key; the financial health check warns while the key is missing (`secrets_key_missing` in `secrets_at_rest`, also with no stored secret). The same rule covers integration secrets: the WooCommerce consumer key, consumer secret and webhook secret (`ENCRYPTED_SETTING_KEYS` in `src/services/settings/settingSecrets.ts`) and each webhook subscription's signing key and custom header values (`src/services/events/webhookSecretStorage.ts`; header names stay plain), and an action rule's webhook token and header values (`actionConfigJson.secretToken` / `headers`, `sealRuleConfig` / `openRuleConfig` in the same file), are written with `encryptSecret` and opened only inside the server; a rule whose token or header the key cannot open fails without a retry, and the financial health check counts plain rule values with the webhooks (`secrets_at_rest`); the system admin's settings answer carries them decrypted (one that cannot be decrypted as «********»). A value the current key cannot decrypt is never sent: the webhook delivery is recorded as failed without a retry, the webhook ping and the WooCommerce connection read are 503 `INTEGRATION_SECRET_UNREADABLE`, and the WooCommerce webhook fails. `npm run secrets:encrypt` also encrypts their legacy plain values (`IntegrationSecretEncryptionService`), and the CI test jobs run with a test `ERP_SECRETS_KEY`.

- **Route Access Policy:** The route → permission table is built from the Express routers (`buildRouteGuardTable` in `src/lib/routeGuardTable.ts`; `npm run routes:permissions` writes `docs/security/ROUTE_PERMISSIONS.md`). Test `sec_route_access_policy_td_298` requires: every unauthenticated route is in `PUBLIC_ROUTES` and every login-only route in `LOGIN_ONLY_ROUTES` (`src/tests/security/routeAccessPolicy.ts`; add a route there only when it reads or writes the user's own data, is a public pick list, or checks permission in its handler); no POST/PUT/PATCH/DELETE route passes with a `*.view` permission alone; every permission key in a guard is in `PERMISSION_CATALOG`. Only an admin grants or removes the `admin` role or changes or deletes an admin account; a non-admin holder of `roles.manage` never edits its own role and gives a new or another role only keys it holds, and a non-admin holder of `users.manage` never changes its own account's role, gives a user only a role whose keys it all holds, and changes (password included) or deletes no account whose role holds a key it lacks (403 `OWN_ROLE_CHANGE_REFUSED` / `GRANT_BEYOND_OWN_PERMISSIONS`, `src/services/users/grantBoundary.ts`, rule shared in `src/lib/permissions/grantBoundary.ts`); the last active admin is neither deleted nor moved to another role: user edit and delete run in one transaction under the admin-set lock (`lockSystemAdminSet`, advisory key 91030) and `assertAnotherActiveAdmin` (`src/services/users/lastAdminGuard.ts`) refuses with 409; a username starting with `test_`, `e2e_` or `testuser_` (any case, `isSyntheticTestUsername` in `src/lib/syntheticUsers.ts`) is refused by `POST /users` and `/setup` with 422, the user lists show every non-deleted user, only setup detection skips such names, and the financial health check lists active ones as `synthetic_test_users`; a new username (`POST /users`, `/setup`, the user form and the setup wizard) is 3 to 50 Latin letters, digits, «.», «_» or «-» (`usernameFormatError` in `src/lib/users/usernameRules.ts`, else 422 `USERNAME_FORMAT_INVALID`) and is unique by `lower(btrim(username))`, so «Ali» beside «ali» is taken: a new user takes no key another user holds, deleted ones included, a deleted user is not restored while a live user holds its key (409 `USERNAME_HELD_BY_LIVE_USER`), and the partial unique index `uq_users_username_key` over live users (migration 0124, built only on clean data) backs it; the financial health check lists live duplicates as `username_case_uniqueness` until one account is deleted; old usernames are never changed and log in as stored; a new user always gets a new id: `POST /users` refuses the username of a deleted user with 409 `USERNAME_OF_DELETED_USER` naming that user and leaves the deleted row as it is, and restoring that same person is the separate `POST /users/:id/restore` (`users.manage`; a new role and a temporary password that must be changed, a new token version, the admin-account and TD-520 rules; the user form offers it); a role gets only catalog permission keys. A user's role code references its role (`fk_users_role` on `roles.code`, ON UPDATE CASCADE, migration 0100); only a soft-deleted user may hold no role (`chk_users_role_active`), and deleting a role clears the role of its soft-deleted users in the delete transaction and names them in the audit row (`clearedDeletedUserIds`). A role is created, edited and deleted only through `src/services/users/roleAdmin.service.ts`, in one transaction under the role row lock with its audit row written with the same `tx`, so a refused audit row changes nothing (part of TD-960).

- **Log Sanitization:** Sensitive fields (`password`, `token`, `secret`, `jwt`, `cookie`) MUST be sanitized to `[PROTECTED]`. In audit details (`sanitizeSensitiveData` / `sanitizeAuditValue` in `src/lib/audit/auditSanitizer.ts`) a secret key is recognised by "contains" in any spelling (`password`, `secret`, `token`, `apiKey`, `cookie`, `jwt`, `authorization`; camelCase, snake_case, kebab-case) and its text value becomes `[PROTECTED]` (boolean and numeric flags stay), and card, account and Sheba numbers keep only their last four digits (`****5678`), field-by-field changes included, so a Sheba change stays visible.

- **Soft Deletes:** Always filter with `.where(eq(table.isDeleted, 0))` on reads — including `journal_voucher_items.is_deleted`: editing or re-syncing a draft voucher soft-deletes its old rows, which stay under the voucher after approval.
