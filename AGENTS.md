## 1. Drizzle ORM & PostgreSQL Rules
1. **NO RAW SQL FOR MUTATIONS:** Never use `tx.execute(sql\`UPDATE ...\`)` or raw SQL with bindings for inserts/updates (prevents `operator is not unique: unknown * unknown` in node-postgres).
2. **Update Pattern (Read-Calculate-Update):** Always fetch row via `tx.select()`, compute mutations in TypeScript, and save via `tx.update().set()`.
3. **Row Locking:** For data updated within the same transaction, use `.for('update')` (NOT `.forUpdate()`).
4. **Explicit Text Casting for WHERE Queries:** For code columns (e.g. `project_code`), cast with `sql\`${table.projectCode} = ${String(code)}::text\``.
5. **Drizzle CamelCase Mapping & Standard Serialization (TD-170):** Express API endpoints for production projects and stages use standardized `camelCase` keys matching the Drizzle schema and typed contracts via `formatProject` and `formatStage` (with backward compatibility aliases for safe consumption).
6. **Atomic Sequence Numbering:** Sequential numbers (vouchers, treasury transactions, document references, project codes — `assignProjectCode` in `src/services/projects/projectCode.ts`, v8.0.80, TD-350) MUST use PostgreSQL Sequences (`SELECT nextval('...')`) or atomic counter tables (`document_ref_counters` / `item_code_counters`, row lock or UPSERT), NEVER `COUNT(*)` or `MAX() + 1`.
7. **Module Resolution (`/src/db/drizzle.js`):** Subdirectory services MUST import Drizzle instance explicitly from `../../db/drizzle.js` (or `.ts`) to ensure clean production bundling.
8. **Money Columns are Decimal on the Server (v7.0.67, audit P2-6 / TD-210, product-owner decision):** Money columns are declared with `moneyNumeric` (`src/db/schema/moneyColumn.ts`; done for every money column — accounting, treasury, document lines/VAT/exchange rate, WAC, Kardex, item prices, payroll and piecework (v7.0.68)). Report totals are summed in SQL (`SUM(...)::text` → `fin()`) or accumulated with `FinancialDecimal`, never with JS `+=` on numbers (v7.0.71, TD-210 resolved).. Their value is `Money` (`src/lib/money.ts`, a `FinancialDecimal`): do arithmetic and comparisons with its methods or `fin()`, write with `money(x)` / `moneyOr(x, fallback)`, never through `Number()` or JS operators. API JSON stays numeric (`Money.toJSON`); DTOs typed `number` convert explicitly with `.toNumber()`.
9. **Flag and Date CHECK Constraints (v7.0.73 / v7.0.75, audit P3-14 / P3-15, product-owner decision — no type change):** Integer `is_*` / `has_*` flags carry `chk_<table>_<column>_flag CHECK (col IN (0,1))`; text date columns carry `chk_<table>_<column>_datefmt CHECK (erp_date_text_ok(col, 'iso' | 'any'))` (migrations 0028 and 0030; `*_iso` columns are `iso`). A new flag or text date column gets the same constraint in its migration (regression tests `reg_flag_check_constraints_p3_14` / `reg_date_format_check_constraints_p3_15` fail otherwise). Constraints are added `NOT VALID` and validated only when existing data is clean — never rewrite old rows silently to satisfy them; a repair needs a product-owner decision and records every old value (v7.0.82, TD-231: `legacy_date_repairs`, shown by the financial health check).
10. **Text Date Columns Store Gregorian ISO, Users See Jalali (v7.0.131–v7.0.136, TD-232, product-owner decision):** Every business text date column stores `YYYY-MM-DD` Gregorian (constraint kind `iso`); server timestamps kept as text (`treasury_transactions.reconciled_at`, `project_stages.completed_at`, `users.last_failed_login_at`) use kind `isots` (Gregorian date-time, never Jalali). `journal_vouchers.date` is `iso` too since v7.0.137 (TD-248, migration 0044; vouchers in a closed fiscal year were left as they were and recorded as refused). Write paths normalize input with `requireStorageDate` / `optionalStorageDate` (`src/lib/storageDate.ts`, invalid date → 422); a document's date (`documents.date`, a Tehran wall-clock timestamp) goes through `requireDocumentTimestamp` / `resolveDocumentTimestamp` in the same file (a non-existent day or non-date → 422, empty → business now), its numbering year comes from that stored date, and a draft or proforma moved to another fiscal year takes that year's next number (v8.0.50, TD-313, product-owner decision); query-string date filters use `storageDateParam` (`src/middleware/validate.ts`). The single converter is `src/utils/calendarDate.ts` (`toStorageDate`, `isoToJalaliDate`; SQL twin `erp_text_date_to_iso`). The browser shows dates with `formatPersianDate`, takes today from `getTodayJalaliDate` / `getTodayIsoDate` (display time zone, never `new Date().toISOString()`, v8.0.49, TD-312; the dashboard banner's date, clock and greeting come from `displayClockNow`, v9.0.293, TD-683), fills pickers with `isoToJalaliDate`, uses `JalaliDateInput` (`src/components/common/JalaliDateInput.tsx`) instead of `<input type="date">`, and compares dates as ISO. A "month" in payroll, work reports, treasury trends and the stock movement chart (`monthlyTrends` of `/dashboard-bi-stats`, `getMonthlyMovementTrends`, v8.0.54, TD-316) is the Jalali month. A new text date column gets kind `iso` from day one. Server timestamps (UTC, no zone) go to the browser with a `Z` (`serverTimestampToUtcIso` in `src/lib/serverTimestamp.ts`), and a day filter over them is the business time zone's day turned into a UTC range with `zonedDayRangeUtc` (activity log, v8.0.53, TD-315).

## 2. API Response Handling & Array Safety Guard
- **Safe Extraction:** APIs return paginated `{ data: [...], total, page, limit }` or arrays `[...]`. Always extract safely:
  ```ts
  const rawData = Array.isArray(res?.data) ? res.data : (Array.isArray(res) ? res : []);
  ```
- **Guard Array Operations:** Always guard before calling array methods:
  ```ts
  const safeItems = Array.isArray(items) ? items : [];
  const filtered = safeItems.filter(...);
  ```

## 3. Inventory & Stock Management
- **Single Source of Truth for Stock (v7.0.45 / v7.0.48, audit P2-1 / TD-214, product-owner decisions):** Per-warehouse stock lives ONLY in `item_warehouse_stocks` (one row per item × warehouse, CHECK non-negative); a missing row means zero. The `items.stocks` JSONB column was dropped (migration 0021; old values kept in `items_stocks_archive`). `items.current_stock` is maintained ONLY by the database (`trg_iws_refresh_item_current_stock` on `item_warehouse_stocks` and `trg_items_current_stock_from_table` on `items`): application code must never write it — a direct write is replaced by `SUM(item_warehouse_stocks)`. API responses that need a per-warehouse map build `stocks` / `stock_<code>` from `ItemWarehouseStockService.getStocksForItems` (canonical warehouse codes via join); availability / count / transfer checks read the table.
- **Weighted Average Cost (WAC):** Updated ONLY on stock 'in' — including the return of a voided outflow, which comes back at that outflow's own Kardex cost (v8.0.11, TD-254, `applyStockReversal`; a cost of 0 leaves WAC unchanged). If current stock <= 0, new WAC equals the new unit price. An incoming movement at price 0 leaves WAC unchanged and its Kardex row records the current WAC as its cost (v8.0.12, TD-256); a production receipt voucher takes such an item's cost from the document's own Kardex `in` rows (`kardexInCostByItem`). A receipt or purchase line with no net price (free goods: price 0 or a full line discount) is posted at that Kardex cost — debit inventory, credit «درآمد کالای اهدایی» (5204, mapping `donatedGoodsIncomeAccountCode`; v8.0.17, TD-268, product-owner decision); the supplier is credited only with the priced lines. WAC and Kardex amounts are in IRR: a foreign-currency document's unit price is converted with the document's own exchange rate (`stockUnitPriceInIrr` in `src/services/documents/documentExchangeRate.ts`) before `applyStockMovement` (v7.0.69, TD-227, product-owner decision).
- **Purchase Line Discount in Cost (v8.0.9, TD-250):** An incoming line (receipt, purchase, production receipt — not a sales return) enters stock at its net unit price, (quantity × price − line discount) ÷ quantity floored at 0 (`netLineUnitPrice` in `src/services/documents/purchaseLineCost.ts`), the same net the purchase voucher posts; a foreign-currency line is converted on the net price without intermediate rounding.
- **No Outflow Without Cost (v7.0.46, audit P2-4, product-owner decision):** An `out` movement records the item's WAC as its cost. If WAC <= 0 the movement is rejected (`ValidationError`) — sales invoices, remittances/waste, project material allocation, WooCommerce orders — except stock-count and Excel adjustments (`documentType = 'audit'`), which are recorded at cost 0. The document price (sale price) or a price-list price is never used as cost. The financial health check values stock at WAC only too: an item with stock and no WAC counts 0 and is listed (v8.0.116, TD-401). A final sales invoice whose gross is zero (free sample, gift) still gets its voucher: cost of sales at the Kardex cost of its `out` rows against inventory, with no revenue or customer row (`syncSalesInvoiceVoucher` writes no zero row; v9.0.270, TD-772, product-owner decision ت۳ of package 8).
- **Sales Return Cost (v7.0.81, TD-230, product-owner decision):** A sales return (`return`, stock in) enters stock at the cost of the original sales invoice's Kardex `out` rows (`documents.return_of_document_id`, `resolveSalesReturnUnitCosts` in `src/services/documents/salesReturnCost.ts`), or at the item's current WAC when no original invoice is linked — never at the sale price. Its voucher reverses cost of sales with the return's own Kardex `in` cost. A return with an original invoice is capped per item at the invoice's active Kardex `out` quantity minus the active Kardex `in` quantity of that invoice's earlier returns (v8.0.8, TD-253, `assertReturnWithinSold`: items then the invoice are row-locked; checked on final create and on finalize; voided or draft returns do not count). An invoice with a sales return that is not voided, in any status, is not voided: `deleteDocument` refuses with 409 `DOCUMENT_HAS_ACTIVE_RETURNS` naming the returns, after the document lock and before any write (`assertVoidHasNoReturns` in `src/services/documents/voidDependents.ts`; v9.0.271, TD-773, product-owner decision ت۴ of package 8). Nor is a document with a live treasury receipt or payment (completed, not a reversal): 409 `DOCUMENT_HAS_TREASURY_ROWS` naming them (`assertVoidHasNoTreasuryRows`, same file); the treasury user moves such a row on account or to another active document of the same party and currency with `PUT /accounting/treasury/:id/document` (`relinkTreasuryDocument` in `src/services/accounting/treasury/treasuryDocumentRelink.ts`, `accounting.treasury`, the TD-501 link rules, bank → document → row locks, audited with `tx`; the voucher is unchanged; the treasury table offers «علی‌الحساب») (v9.0.272, TD-779, same decision). A return with an original invoice takes that invoice's currency, exchange rate and net unit price per item — (quantity × price − line discount, floored at 0) summed over the item's lines ÷ their quantity, rounded to four decimals (`invoiceReturnTerms` in `src/lib/documents/returnUnitPrice.ts`, shared with the stock page) — with no line discount; another currency, rate or price, a line discount or an item not on the invoice is 422 (`RETURN_CURRENCY_MISMATCH` / `RETURN_EXCHANGE_RATE_MISMATCH` / `RETURN_PRICE_MISMATCH`), and a field not sent is filled from the invoice (`enforceReturnInvoiceTerms` in `src/services/documents/salesReturnPrice.ts`, on create, on draft edit and on finalize, where a stored draft that differs is 422); the stock page fills and locks them. A return without an original invoice keeps the user's price (v9.0.273, TD-788, decision ت۱۰ of package 8).
- **Stock Count and Excel Adjustments Post a Voucher (v8.0.3, TD-255 / TD-262 / TD-263, product-owner decision):** A stock count (`audit` document) is recorded only as `final` — a draft is refused and `finalizeDocument` refuses an audit. Its shortages and surpluses are valued at the item's WAC (an item without WAC at 0, never a price-list or sale price), and `syncStockAdjustmentVoucher` (`src/services/accounting/stockAdjustmentVoucher.ts`) issues, in the same transaction, a draft voucher at the Kardex cost against «کسری و اضافات انبار» (7012, mapping `inventoryCountDifferenceAccountCode`), linked by `source_document_id`. Excel stock adjustments of existing items get one such voucher per import; the new Excel items with stock of one import share one draft opening voucher with one debit row per item at its opening Kardex value (`ItemOpeningService.issueImportOpeningVoucher`; v9.0.206, TD-663, product-owner decision ت۱۰), and the items of every opening voucher are recorded in `item_opening_voucher_items` (migration 0074, legacy vouchers backfilled from `reference_id`), the one lookup for an item's opening voucher (`itemIdsWithOpeningVoucher`). The item list builds the reservation report only for the items of its own page (`getReservedStocksMap({ itemIds })`) and an Excel import reads and locks the items its file names once, in id order (`ImportItemIndex` in `src/services/items/itemImportIndex.ts`). The item opening voucher (`ItemOpeningService.issueItemOpeningVoucher`, Dr inventory / Cr opening capital) is worth the item's opening Kardex rows — quantity × cost recorded at creation (`openingKardexValue` in `src/services/inventory/itemOpeningValue.ts`) — with or without the item workflow, never current stock × current WAC, and rewrites no Kardex row; an issued opening voucher that differs is only listed by the financial health check (`item_opening_voucher_value`) (v9.0.93, TD-481, product-owner decision ت۴). A new item's opening voucher (`POST /items`, when no item workflow starts) and its audit row are written in the item's own create transaction, so a voucher failure refuses the item and its opening stock (v9.0.169, TD-652, product-owner decision ت۶). Two active items never share a code (key `upper(btrim(code))`, letter case and surrounding spaces ignored) or a name (key `lower(btrim(name))`): `assertItemCodeAvailable` / `assertItemNameAvailable` (`src/services/items/itemIdentity.ts`) check the item form and the Excel import, and the partial unique indexes `uq_items_code_active` / `uq_items_name_active` (migration 0070, created only on data without duplicates; the financial health check lists duplicates as `item_identity_uniqueness`) turn a concurrent duplicate into the same Persian 409; a new Excel item without a name is a row error (v9.0.170, TD-653, product-owner decision ت۴). `PUT /items/:id` requires the item's `version` (400 without it) and writes with the version in its WHERE (409 `OCC_CONFLICT` when stale or changed meanwhile); a field missing from the body keeps its current value, the Excel import advances the version too, and the edit and its audit row (before / after / changes) run in one transaction (v9.0.171, TD-654, product-owner decision ت۷). Saving an item (form, code edit, Excel import) moves its code series counter in `item_code_counters` to at least the code's serial under the counter row lock, in the same transaction (`advanceItemCodeCounter` in `src/services/items/itemCodeCounter.ts`; a series without a counter row is left alone), so `/items/next-code` never suggests a saved code (v9.0.172, TD-656, product-owner decision ت۴). The item form's numbers (reorder point, cost, opening stock per warehouse, weight) go through `decimalInput` and are non-negative (`src/routes/items.schemas.ts`): text is 400, Persian digits are read, and `weight: null` clears the weight (v9.0.173, TD-657 item part, product-owner decision ت۹). Counts before v8.0.3 get no voucher. The stock-count sheet (`GET /documents/audit-items`) resolves its location by warehouse code or name like a document (`createWarehouseResolver`, empty = default warehouse, unknown = 422) and the page selects warehouses by code; each posted line carries the book stock the sheet showed (`system_stock`), and a count whose shown book stock differs from the stock under the item locks is refused with 409 `AUDIT_BOOK_STOCK_CHANGED` listing the items, nothing moves and the sheet reloads (`assertBookStocksUnchanged` in `src/services/inventory/stockCountSheet.ts`; v9.0.55, TD-480, product-owner decision ت۷). The Excel import never changes the WAC of an item that has stock (v8.0.5, TD-264, product-owner decision): such a row is not applied and is listed in the import errors; a value within 1 rial of the current WAC (`EXCEL_WAC_TOLERANCE`) counts as unchanged and the current WAC is kept; an item without stock takes the file's WAC.
- **Item Excel Import and Price Lists (v9.0.152, TD-647, product-owner decision ت۱):** Only the configured price lists (`pricing_strategies`) are prices: the unified Excel import, the pricing page quick import (`buildQuickPriceUpdates` in `src/lib/items/quickPriceImport.ts`) and `POST /items/:id/prices` / `batch-update` read price columns through `extractRowPriceColumns` / `priceListMatcher` (`src/lib/items/excelPriceColumns.ts`); another «قیمت …» column is a row error and is ignored, and setting a price for an unconfigured title is 422 `PRICE_LIST_NOT_CONFIGURED` (deleting one is allowed). The cost column is «میانگین موزون بها» (`ITEM_WAC_COLUMN`; old WAC headers are still read as cost, never as a price). `filterActivePrices` returns configured price lists only. Migration 0068 soft-deleted the active rows titled «میانگین خرید (WAC)», «موجودی کل» and «میانگین بهای خرید» and recorded them in `item_price_title_cleanup`; other unknown titles are only listed by the financial health check (`item_price_unknown_title`). An import never rewrites a price that is already the only active price of its list with the same amount and currency, and such a price is not counted in `pricesCount`; the price history shows when each row was created (`priceHistoryRegisteredAt`, `created_at` with a `Z`) (v9.0.153, TD-662). Each price list has its own currency column «ارز - قیمت <title>» in the item export, the pricing page export and the import template, and the unified and quick imports read it first (`priceCurrencyColumn` / `priceExportCells` in `src/lib/items/excelPriceColumns.ts`); a legacy row-wide «واحد ارز» is read only for a list without its own column (v9.0.207, TD-841). The import template comes from the server (`GET /items/excel-template`, `buildItemExcelTemplate` in `src/services/items/itemExcelTemplate.ts`): one sample row with the columns the import reads, 10 in each active warehouse and «موجودی کل» their sum, and every configured price list with its currency column; it reads no item and writes no export audit row (v9.0.208, TD-842). The items and pricing pages show each button and price field by the permission of the server route it calls (`products.create` / `products.edit` / `products.delete`, `woocommerce.manage`, `products.edit_price`), never by a role code; the average cost is always shown in IRR, and the pricing page's margin badge and markup buttons compare only rial prices with it (`priceMarginPercent` / `markupPrice` in `src/lib/items/priceMargin.ts`) (v9.0.209, TD-840). Each part of the import needs its own permission, computed in the route with `can()` and passed to `importItemsFromExcel` (`src/services/items/itemExcelImport.ts`) as `ItemImportPermissions` (`src/lib/items/itemImportPermissions.ts`), never read from the body: a new item with its opening stock `products.create`, fields of an existing item `products.edit`, prices `products.edit_price`, a stock increase of an existing item `warehouse.in` and a decrease `warehouse.out`; a part the user may not change is a row error and is skipped only when it would change something, and the Excel window says so before upload (v9.0.154, TD-648, product-owner decision ت۲). For an existing item a missing column or blank cell means unchanged and the type comes from the item unless the row has a type column; the page filter only sets a new item's type, and the code format is checked only for a new item, in the browser preview with the server's patterns (`codeFormatError` in `src/lib/items/itemCodeFormat.ts`) (v9.0.155, TD-650, product-owner decision ت۳). A row finds its item by code only (`ImportItemIndex.findByCode`: the exact code, else the single item whose code differs only in letter case; several such items are a row error), a name held by another active item is a «نام تکراری» row error for new and existing items alike, and the import never changes an item's code (v9.0.156, TD-651, product-owner decisions ت۳ / ت۵). Stock columns are planned before anything is written (`planStockChanges` in `src/services/items/itemExcelRow.ts`): a warehouse column sets only that warehouse and a filled «موجودی کل» must equal the sum of all warehouses; «موجودی کل» alone is accepted only for a new item (default warehouse) or an item whose whole stock is in the default warehouse, an equal total is unchanged, otherwise the row is refused («موجودی هر انبار لازم است»); a negative quantity or a change in an inactive warehouse is a row error, and a refused row writes nothing (v9.0.157, TD-649, product-owner decision ت۳). Every item the import creates or changes gets one «کالا» audit row (CREATE / UPDATE) with before / after / changes of its fields, `موجودی <warehouse code>` and `قیمت <title>` (`itemAuditSnapshot` / `logItemImportChange` in `src/services/items/itemExcelAudit.ts`), plus one IMPORT summary row, all written with the import's `tx` (v9.0.158, TD-655). A price is a decimal above zero (Persian digits accepted) in a currency of the §6 list (`parsePriceAmount` / `priceCurrencyOf` in `src/lib/items/priceInput.ts`, shared by the routes, the Excel import, the quick import and the pricing page): `POST /items/:id/prices` and `batch-update` refuse anything else with 400, `batch-update` removes a price only with `remove: true` (the pricing page sends it for an empty field and never sends an invalid amount), and an invalid price or currency refuses the whole Excel row; older rows are only listed by the financial health check (`item_price_invalid_amount_currency`) (v9.0.176, TD-657, product-owner decision ت۹).
- **Stock Movement Date and Kardex Replay (v8.0.4, TD-257 / TD-258, product-owner decision):** The date of a stock movement (document create, finalize, warehouse transfer) may not be earlier — by day — than the item's last ledger movement (rows of voided documents and their reversals do not count, so void + reissue with the original date stays possible). The only exception is the permission `warehouse.backdate` (granted to no role by default), computed in the route with `userHasRoleOrPermission` and passed as `allowBackdate` (never read from the request body); a backdated `out` is then accepted only when the warehouse's balance in (day, id) order stays non-negative from that date on (`assertStockMovementDate` in `src/services/inventory/stockMovementDate.ts`, called by `applyStockMovement` and the transfer service). No stock movement may be dated after the business today, for any user (422 `STOCK_MOVEMENT_FUTURE_DATE`, same function; v9.0.79, TD-483, product-owner decision); future-dated Kardex rows recorded earlier are never rewritten and are listed by the financial health check (`stock_future_movements`, `src/services/inventory/futureStockMovements.ts`), and a transfer date goes through `requireStorageDate`. The Kardex rebuild replays WAC with `replayKardexWac` (`src/services/inventory/kardexReplay.ts`): registration (id) order and exactly the live engine's formulas (voided rows in place, reversal via the `applyStockReversal` formula, transfers quantity-only), starting from WAC 0 — the item's current WAC is kept only when the replay reaches no positive WAC (v8.0.13, TD-269); the I13 invariant uses the same function. The rebuild («بازسازی موجودی از کاردکس») only rebuilds quantities and reports a WAC that differs from the replay (`replayWac`, `wacDifferences`); setting the WAC to the replay is the separate «اصلاح بهای میانگین» (`POST /inventory/correct-wac`, permission `inventory.wac_correct`, granted to no role by default), allowed only when the stock equals the Kardex balance, which issues in the same transaction a draft voucher for stock × (replay − old WAC) against 7012 (`correctItemWacFromLedger`, `src/services/accounting/wacCorrectionVoucher.ts`; v9.0.90, TD-487, product-owner decision ت۳). The initial Kardex backfill («ثبت موجودی اولیه کاردکس», `KardexBackfillService`) only adds rows for items with stock and no incoming Kardex row and never reprices an existing row (v9.0.92, TD-488). Voiding a document whose incoming rows were consumed by later-dated outflows is refused (v8.0.6, TD-265, product-owner decision): `assertVoidKeepsStockHistory` (`src/services/inventory/voidStockHistory.ts`, called first in `deleteDocument`) rejects a void that would make a warehouse's (day, id) balance negative and names the consuming documents; voiding an outflow is never refused.
- **Project Reservation Deduction (v7.0.102, TD-233, product-owner decision «کسر در سرور»):** A final `out` document with `projectId` deducts the project's reservation inside its own create/finalize transaction (`releaseReservationsForDocument` → `ItemStockReservationService.releaseProjectReservations`, project row lock + OCC); a failed deduction rejects the document, drafts deduct nothing. Each line is deducted across all matching reservation rows, from the quantity field the reservation report reads (`reservationQtyField`). The browser never writes `inventory_control` for this. Voiding/deleting such a document restores the same quantities to the same project in the void transaction (v7.0.105, TD-237, product-owner decision «برگردد»): each deduction is recorded in `project_reservation_releases` and `deleteDocument` locks the project before the document and calls `restoreReservationsForDocument`; deductions before v7.0.105 have no record and restore nothing. The reservation itself (`inventory_control.reservedItems`) is written only by the server (v8.0.66, TD-306, product-owner decision): project create/update ignore `reservedItems` / `isReserved` / `finalizedAt` from the body; finalizing (`isFinalized` false → true) builds the reservation from the inventory control sections and item stock (`buildProjectReservation` in `src/lib/projects/projectReservation.ts`, via `resolveServerInventoryControl`), saving a finalized project keeps its current (possibly deducted) reservation, and unfinalizing clears it; the project row is locked during the update.
- **Project BOM Allocation From a Receipt (v8.0.32, TD-287, product-owner decision):** Materials enter stock only through a purchase receipt and are then allocated. `allocateReceiptItemsForProjectBom` requires a registered active `in` movement of the same item (`receiptTransactionId`, or the receipt `documentId`) and then moves the quantity out exactly like `allocateMaterialsForProject` (the allocation's source movement is its own `out` row); without a receipt it is refused. `releaseAllocation` brings the materials back at the Kardex unit cost of the allocation's own `out` movement, never the current WAC; an allocation whose source movement is an `in` (a receipt allocation before v8.0.32) is released without a stock movement (v8.0.33, TD-288). Every allocation issues a draft voucher Dr work in progress (1402, detailed project) / Cr raw materials or finished goods (by item type) at the Kardex cost of its out movement, linked by `journal_vouchers.source_bom_allocation_id` (migration 0049, `src/services/accounting/bomAllocationVoucher.ts`); releasing the allocation voids it through `voidSourceVoucher`; consumption posts nothing, the materials stay in 1402 (v8.0.34, TD-286, product-owner decision). Delivering a project's finished goods to stock («ورود به انبار», `ProjectService.addProjectToInventory`) issues, in the same transaction, a final `production_receipt` document linked to the project, whose voucher debits finished goods and credits work in progress (detailed project), at the entered unit price, else the item's current WAC; it never moves stock directly (v8.0.35, TD-285, product-owner decision). Delivery is capped by the project's planned quantity (v8.0.72, TD-327, product-owner decision «با دلیل»): under the project lock the sum of the project's final `production_receipt` lines per item (`deliveredProjectQuantities` in `src/services/projects/projectDeliveryCap.ts`) plus this delivery may exceed the planned quantity (`products`, else the main item and quantity) only with `overDeliveryReason` (else 422 `OVER_DELIVERY_REASON_REQUIRED`, the «ورود به انبار» tab asks for the reason and resends); the reason goes into the receipt notes and the activity log; a cancelled project or an item outside the project's products is refused. A project with an open (`allocated`) BOM allocation is not deleted: `deleteProject` locks the project row and refuses with `PROJECT_HAS_OPEN_ALLOCATIONS` until the allocations are released (v8.0.121, TD-412, product-owner decision).
- **Centralized Stock Movements:** All stock operations, warehouse locations, and WAC calculations MUST route through `DocumentService.applyStockMovement` in `src/services/document.service.ts` (item creation and opening stock included). Warehouse-to-warehouse transfers that must not change WAC move both rows through `ItemWarehouseStockService.applyMovement` and then rebuild the cache. Every transfer is a final `transfer` document (own number series through `DocumentRefNumberService.assignDocumentRefNumber`, one line at the source warehouse, both Kardex rows linked by `document_id`; source and destination are read from those rows by `transferLocationsByDocument`) and is voided only through `deleteDocument`, whose reversal of transfer rows moves quantity only (`applyStockReversal` with `quantityOnly`, the same rule in `replayKardexWac`) (v9.0.80, TD-489, product-owner decision); transfers recorded before v9.0.80 stay without a document.
- **Procurement Delivery Is Stock-In Only (v8.0.10, TD-267):** `ProcurementService.deliverOrderToWarehouse` and the linked-document finalize of a requisition accept only incoming documents (`receipt`, `purchase`); a purchase proforma is a `receipt` with status `proforma` (never type `proforma`, which finalizes into a sales invoice); `finalizeDocument` treats `purchase` as stock-in like `createDocument`. Delivering an order finalizes it and updates its requisition in one transaction: the requisition row is locked first and the document status re-read under that lock (a repeated delivery adds nothing); each item's received quantity is the sum of all active document lines, filled across the requisition rows of that item in order (`applyDeliveredLines` in `src/services/procurement/requisitionReceipt.ts`; v8.0.36, TD-290). `POST /procurement/requisitions/:id/convert-to-orders` validates exactly the body the split-order form (`SplitOrderModal`) sends: the requisition row id is optional, and each package keeps its target warehouse, type and status (draft or proforma only; stock enters only through delivery) (v8.0.37, TD-291). Ordering more than a requisition's remaining quantity is allowed only with a reason (v8.0.38, TD-289, product-owner decision): `convertToPurchaseOrders` refuses it without `overOrderReason` (422, `OVER_ORDER_REASON_REQUIRED`, the message lists the items and excess; `findOverOrders` in `src/services/procurement/requisitionOrder.ts`), the split-order form warns and requires the reason (`OverOrderWarning`), and the reason is recorded on the requisition row (`overOrders`), in the requisition and order notes and in the activity log; the conversion runs in one transaction under the requisition row lock. A requisition workflow action (`executeWorkflowAction`) runs in one transaction under the requisition row lock too; «دریافت کالا» (`receive_items`, `receiveRequisitionItems` in `src/services/procurement/requisitionReceiveAction.ts`) finalizes the requisition's open orders and receives never-ordered items with one final receipt, a finalize error refuses the whole action, and the received quantity is rebuilt from the requisition's final documents; a received or rejected requisition is never received or converted to orders again (409) (v8.0.71, TD-326).
- **Default Warehouse (TD-203, v7.0.36):** The default warehouse is the ACTIVE warehouse with the LOWEST id. Any query that picks a default/first warehouse MUST `orderBy(asc(warehouses.id))` (or use `getDefaultWarehouseCode` in `src/services/inventory/warehouseResolver.ts`); PostgreSQL row order without `ORDER BY` changes after updates. The Kardex location codes `''` and `default` always mean the default warehouse (`LEDGER_RESERVED_WAREHOUSE_CODES` in the same file), so a new warehouse with such a code is refused with 422 `WAREHOUSE_CODE_RESERVED`, a void's reversal of a row without a location writes the default warehouse's code, and a legacy warehouse with such a code is left unchanged and listed by the financial health check (`warehouse_reserved_code`, v9.0.110, TD-482).
- **Warehouse Deactivation (v9.0.112, TD-490, product-owner decision ت۵):** Deactivating or reactivating a warehouse runs in one transaction with its audit row, under the transaction advisory lock `WAREHOUSE_ACTIVE_SET` (91010) and the warehouse row `FOR UPDATE`; every stock movement locks its active warehouse row `FOR KEY SHARE` in `ItemWarehouseStockService.applyMovement` (an inactive warehouse is 422 `WAREHOUSE_INACTIVE`), so the «no stock» check sees in-flight movements. The last active warehouse is never deactivated (422 `WAREHOUSE_LAST_ACTIVE`); only the system admin reactivates one (`POST /warehouses/:id/reactivate`, «انبارهای غیرفعال» in «مدیریت انبارها»), and creating an inactive warehouse's code again is 409 pointing to reactivation.
- **Document Statuses:** Supported document statuses in API and services: `'draft'`, `'proforma'` (پیش‌فاکتور), and `'final'`. A `proforma` document finalizes into an `invoice` dated the finalization moment (business now) that takes the invoice series' next number of that date's fiscal year (Kardex rows, the voucher and events carry both); the proforma number and Jalali date are kept in its notes (`proformaInvoiceTarget` in `src/services/documents/proformaInvoice.ts`; v8.0.51 / v8.0.119, TD-317 / TD-410, product-owner decisions). A sales lead is «won» only with a live proforma (TD-309): voiding the document a lead points to (`crm_leads.proforma_id`: its proforma, or the invoice finalized from it) releases the lead in the void transaction, its row locked before the items, and moves a `won` lead back to `proposal` / `active` with a note (`releaseLeadOfVoidedDocument` in `src/services/crm/leadProforma.ts`; v9.0.12, TD-423); a refused void leaves the lead unchanged. Only a sales document (`invoice` / `proforma` type) in `draft` or `proforma` status enters the approval workflow, inside its create transaction (`needsApprovalWorkflow` in `src/services/documents/documentApprovalScope.ts`, `maybeStartWorkflow({ tx })`; a start error rejects the document); the browser never starts it, and finalizing outside the workflow closes the document's open instance in the same transaction (`terminateOpenWorkflows` in `src/services/workflow/workflowTermination.ts`; v9.0.39, TD-446, product-owner decision ت۴). Voiding a document, deleting or voiding a draft journal voucher, and deleting an item, bank account or purchase requisition terminate the entity's running workflow in the same transaction, after the entity row lock: instance `TERMINATED`, pending tasks `canceled`, one `terminate` history row (v9.0.40, TD-447, product-owner decision ت۵). A proforma with `crmLeadId` is created in one transaction with its lead (v9.0.13, TD-424): `lockLeadForNewProforma` locks the lead row before the document and refuses a second proforma under that lock, the document is created with `externalTx`, and `markLeadProforma` writes the link and the note in the same transaction (`src/services/crm/leadProforma.ts`).
- **Stock Direction From the Document Type (v9.0.238, TD-770, product-owner decision ت۲ of package 8):** A document's stock direction comes only from its type (`DOCUMENT_STOCK_DIRECTIONS` / `documentStockDirection` in `src/lib/documents/documentDirection.ts`, shared by the server and the stock document page): receipt, purchase, production receipt and sales return move stock in; invoice, proforma, remittance and waste move it out; a stock count moves each line by its count. Create and finalize use it (`stockDirectionOf` in `src/services/documents/documentRecordRule.ts`), and every outgoing document recorded or finalized as final passes one sellable gate, `assertOutflowWithinSellable` (`src/services/documents/documentSellableGate.ts`, v9.0.239, TD-775): the quantities of each item and warehouse are summed and checked once against min(warehouse stock, total stock − other reservations), the reservation report is read for the document's items only and a report error refuses the document; the stock document page caps an exit with the same rule for its source warehouse (`itemReservationSummary` in `src/lib/documents/stockReservations.ts`, v9.0.242, TD-799); an `inOut` against the type is 422 `DOCUMENT_DIRECTION_MISMATCH` (`assertRecordableDocument`, checked by `POST /documents` before the permission and by `createDocumentWithDetails` for every caller), a transfer is never recorded there and a type without a stock direction (other than a stock count) takes no lines (`DOCUMENT_TYPE_NOT_RECORDABLE`; transfers only through `transfers.routes.ts`; the route accepts only recordable types).
- **Soft Delete & Reversal (DB-009):** Never HARD DELETE stock transactions. Set `is_deleted = 1`, issue an atomic reversal transaction with `reversal_of_id`, and recalibrate balances via `DocumentService.applyStockMovement`.
- **Negative Stock Policy (DB-006, TD-180):** Negative stock is **always forbidden** (product-owner decision, v7.0.22). Reductions (`out`) must fail with `InsufficientStockError` before committing; the database constraint `chk_iws_current_stock_non_negative` on `item_warehouse_stocks` is the final safeguard. The legacy `warning` / `allowed` options are removed and must not be reintroduced without dropping that constraint in a new migration.

## 4. WooCommerce Integration & Webhooks
- **Public Route Exemption:** Webhook endpoints (`/api/woocommerce/webhook/order`) must be exempted from `authenticateToken` in `src/middleware/auth.ts` for ping/payloads (GET, POST, HEAD).
- **Preview Domain Resolution:** Replace `ais-dev-` with `ais-pre-` in `window.location.origin` when displaying webhook delivery URLs in AI Studio preview environments.
- **SKU Matching & Orders:** Match line items to ERP items via `items.code` (SKU). Route orders through `DocumentService.createDocument` (`docType: 'invoice'`, `status: 'final'`, `inOut: 'out'`).
- **Order Status Policy (TD-190, v7.0.30):** All order processing lives in `WooOrderSyncService` (`src/services/woocommerce/wooOrderSync.service.ts`). Only `processing` / `completed` issue a final invoice; other statuses are logged as `deferred`. `cancelled` / `failed` void the invoice through `DocumentService.deleteDocument` (DB-009); `refunded` is only flagged `needs_review`, and so is an order moved to the trash or deleted in WooCommerce (status `trash`, or webhook topic `order.deleted`, whose body is only `{ id }` and never overwrites the stored order payload; v8.0.126, TD-407). An order with any unmatched SKU is rejected as a whole (no partial invoices). Each order is serialized by a row lock on its `woocommerce_order_logs` row; failures are persisted outside the rolled-back transaction. The webhook always answers HTTP 200 (WooCommerce never re-delivers and disables a webhook after 5 non-2xx responses); retries happen via manual order sync.
- **Rial Units of WooCommerce Orders (v8.0.39, TD-292):** An order's currency maps to IRR through `RIAL_UNIT_MULTIPLIERS` in `wooOrderSync.service.ts`: IRR ×1, IRT / TOMAN ×10, IRHR (thousand rial) ×1,000, IRHT (thousand toman) ×10,000; the invoice is in IRR. Any other currency stays a foreign-currency document and needs an exchange rate (TD-198).
- **Customer Match by Phone Key (v8.0.40, TD-296):** A WooCommerce order finds its customer by `phoneMatchKey` (`src/services/woocommerce/phoneMatchKey.ts`: Persian/Arabic digits to Latin, non-digits removed, the last ten digits; `phoneMatchKeySql` is the same key on the column), so +98…, 0098…, 0912… and spaced or Persian-digit forms of one number match one customer; without a phone the name is matched. The sales lead link, the customer form's duplicate check (on edit only when the number changes) and the customer Excel import match phones with the same key (`findActiveCustomerByPhone` / `assertCustomerPhoneAvailable` in `src/services/customers/customerIdentity.ts`; v9.0.7, TD-419, product-owner decision).
- **Exact Line Totals (v8.0.41, TD-297):** An order line keeps its exact total on the invoice: when the total is not divisible by its whole quantity in the currency's smallest unit (rial without decimals, cents otherwise), `exactLineSplit` (`src/services/woocommerce/exactLineTotal.ts`) makes two lines, quantity − 1 at the rounded-down price and one unit at the remainder (1000 for 3 = 2 × 333 + 1 × 334). Never use a line discount for rounding (it would post to sales discounts).
- **Negative Fees Are Line Discounts (v8.0.42, TD-295, product-owner decision):** Positive `fee_lines` and shipping are the invoice's service charge; the sum of negative `fee_lines` (an order discount) is spread over the invoice lines in proportion to their amounts as line discounts (`allocateFeeDiscount` in `src/services/woocommerce/feeDiscount.ts`, shares floored in the currency's smallest unit, remainder to the larger lines, exact sum), like a WooCommerce coupon; a discount larger than the lines rejects the order.
- **Changes to an Invoiced Order Need Review (v8.0.43, TD-294, product-owner decision):** A webhook or manual sync of an already invoiced order is compared with the payload the invoice was issued from (`describeOrderChange` in `src/services/woocommerce/orderChange.ts`: line SKU / quantity / total, the order total and the sum of refunds). A difference sets the log to `needs_review` with the difference in its message and leaves the invoice untouched; an unchanged order (e.g. processing → completed) stays `processed`. Voiding and reissuing, or a sales return, is the accountant's decision.
- **API Keys Only in the Header (v8.0.127, TD-408):** Requests to the WooCommerce REST API send the consumer key and secret only in the `Authorization: Basic` header over HTTPS; only a plain-HTTP store URL (where WooCommerce refuses Basic auth) gets them in the query string (`wcAuthQueryParams` in `src/services/woocommerce/wcRequestAuth.ts`).
- **Online Shop Warehouse (v8.0.44, TD-293, product-owner decision):** The setting `wc_shop_warehouse` (an active warehouse code; empty = the default warehouse; an inactive or unknown code is refused on save) is the online shop's warehouse. WooCommerce invoices draw from it (`resolveShopWarehouseCode`) and the stock sync (`/woocommerce/sync-item`, `/woocommerce/sync-all-stocks`) pushes its sellable stock (`shopSellableStocks` in `src/services/woocommerce/shopWarehouse.ts`, the same `computeSellable` rule the invoice checks: min of that warehouse's stock and total stock minus reservations), never the total of all warehouses.

## 5. Security, Authentication & Audit Logging
- **HttpOnly Cookies:** JWT tokens are issued and stored exclusively via secure HttpOnly cookies (`auth_token`, `secure: true`, `sameSite: 'none'`, `path: '/'`). Browser JS MUST NOT store or read raw tokens in `localStorage`. All client fetch calls MUST specify `credentials: 'include'`.
- **No Token in Response Bodies (TD-185, v7.0.27):** Login/setup responses MUST NOT include the JWT by default. The only exception is the opt-in compatibility flag `EXPOSE_TOKEN_IN_BODY=true` for preview environments whose browsers block the iframe cookie (BUG-08); production deployments must leave it unset. In production the CSP lets only the app itself frame it and be connected to, plus the origins in `FRAME_ANCESTORS` / `EXTERNAL_API_ORIGINS` (`buildCspDirectives` in `src/lib/cspDirectives.ts`; v9.0.145, TD-597, product-owner decision t3).
- **Login Lockout per Username + IP (v7.0.70, TD-187, product-owner decision):** The progressive login lock (5 failures → 1, 2, 4 … at most 30 minutes) applies to the (username + client IP) pair, held in memory (single instance); the whole account (`users.locked_until`) is locked only after `ACCOUNT_LOCKOUT_THRESHOLD` = 50 failures from any address within 24 hours (`src/services/auth/loginSecurity.service.ts`). Unknown usernames behave identically; no CAPTCHA. Both 429 lock answers (this lock and the per-address login limiter, with the minutes left of its window) carry `locked: true` and `remainingMinutes` and the Persian-digit messages of `src/lib/auth/loginLockout.ts`; the login page counts down only from those two fields, never from the message text, and a 429 of the general request limiter is an error, not a lock (v9.0.220, TD-539).
- **Session Verification & Logout:** Use `/api/auth/me` to verify session on load, and `/api/auth/logout` to clear the cookie. Login, logout and setup are exempt from CSRF, so they accept only the application's own origin (v9.0.77, TD-528, `sessionEndpointOriginGuard` in `src/middleware/sessionOrigin.ts`): the browser origin (`Origin`, else `Referer`) must be the request's own host, in `ALLOWED_ORIGINS` (never `*`) or `APP_URL`, plus localhost and Google preview hosts outside production; `Origin: null` is refused and a request with neither header (a non-browser client) passes. Logout with a valid session cookie requires that session's `x-csrf-token` (403 otherwise); an invalid or expired cookie is only cleared. Every password is at least `MIN_PASSWORD_LENGTH` = 8 characters (`src/lib/auth/passwordPolicy.ts`, shared by the routes and the forms; v9.0.217, TD-532). A password an administrator sets for another user (create, reset, restore) is temporary (`users.must_reset_password = 1`), one set for one's own account is not: until the user changes it from the profile, `authenticateToken` refuses every request except `/auth/me`, `/users/profile`, `/users/my-permissions`, `/csrf` and logout with 403 `PASSWORD_RESET_REQUIRED` (`src/lib/auth/passwordReset.ts`), and the browser shows only the password form, closed only by «خروج» (v9.0.219, TD-523, product-owner decision ت۵).
- **Route Middleware Order:** Administrative/utility/seed routes MUST be registered AFTER `router.use(authenticateToken)` and protected via `requireSystemAdmin` (system maintenance) or `requirePermission` (everything else).
- **Role vs Permission Namespaces (v7.0.51, audit P2-10):** Permission keys always contain a dot (`customers.manage`); role codes never do (`ROLE_CODE_PATTERN = /^[a-z0-9_-]+$/`, enforced on role creation). `authorizePermission` / `userHasRoleOrPermission` match the role's permissions only against permission keys; `admin` always passes.
- **No Role Codes in Route Guards (v9.0.107, TD-516, product-owner decision ت۱ and the approved system-admin list):** `authorize` is gone and no route guard takes a role code. A route asks catalog permission keys (`authorizePermission` / `requirePermission`), or is one of the system maintenance routes in `SYSTEM_ADMIN_ONLY_ROUTES` (`src/tests/security/routeAccessPolicy.ts`: backup, clear data, activity-log purge, attachment cleanup and migration, default categories and chart of accounts, system health, environment, date calendar report, event reconciliation) guarded by `requireSystemAdmin`, and `/metrics` is for the system admin too; the policy test checks the list both ways. Defining warehouses needs `warehouse.manage`, running the fiscal-year close `accounting.fiscal_close`, deleting a material request `pending_materials.delete`, and the activity log `audit_logs.view`. A legacy `*` in a role's permissions grants nothing. Migration 0062 gave each seed role (`is_system = 1`) the guard permission it had passed only by its code, expanded a non-admin `*` into every catalog key, and logged each change in `activity_logs`; custom roles were left as they were. Only the system admin role is a system role (v9.0.135, TD-885, permission model decision ت۹): migration 0067 set `is_system` to 1 on the admin row and 0 on every other role, logged in `activity_logs`, and `DELETE /roles/:id` refuses only the system admin role (a role with active users or needed by a workflow step is still refused; deleted users do not count, v9.0.179, TD-535). The system admin role's permissions are computed, never stored or edited (v9.0.136, TD-886, permission model rule 3): `GET /roles` lists it with every catalog key, `PUT /roles/:id` refuses its permissions (409 `SYSTEM_ADMIN_ROLE_FIXED`) and lets only the system admin change its name and description, and the role form shows its ticks all set and locked.
- **Shared Permission Catalog With Dependencies (v9.0.86, TD-880, permission model §4.2):** The permission catalog lives only in `src/lib/permissions/permissionCatalog.ts`, shared by the server and the browser (`GET /api/permissions` serves it). A key that is useless without another names it in `requires`: every action key of a group requires that group's view key, and `accounting.treasury_no_voucher` requires `accounting.treasury`. `POST /roles` / `PUT /roles/:id` store `withRequiredPermissions(requested)` and record the added keys in the audit row (`addedByRequirement`); the role form ticks a key's requirements, unticks its dependents (`withoutPermission`) and shows what saving an older role will add. A new catalog key that needs another key declares it there.
- **One Permission Check and Ratchets (v9.0.87, TD-881, permission model §4.5):** `can(user, ...permissionKeys)` in `src/middleware/authorize.ts` is the one permission check: the system admin (`SYSTEM_ADMIN_ROLE`, the only role code that code may name) passes, any other user passes only when the role holds one of the keys, and a dot-less argument throws. `requirePermission(...keys)` is the route guard built on it and refuses, when the router is built, a key outside the catalog or a role code; `authorizePermission` is the same guard under its old name. New checks use `can` / `requirePermission`, never a role code. `npm run ratchet:permissions` (`scripts/permission-ratchet.ts`, baseline `permission-ratchet-baseline.json`, run by Vitest `permissionRatchet.test.ts`) fails when a production file gains a role-code literal, a permission-shaped literal is not a catalog key, or a catalog key is checked by no server code; a lower count fails until the baseline is lowered with `-- --update`. Never raise the baseline. Buttons follow the same rule: an action is shown by the permission its API asks (`useHasPermission`), never by a role code or `*` — the customers page by `customers.manage`, a sales file's delete by `crm.delete` (the sales file lists render it only with a delete handler), the stock document form's item definition by `products.create` / `products.edit` (v9.0.148, TD-893), and the stock document page's directions, document types and submit button by the permission recording that type final asks (`stockPageAccess` in `src/lib/documents/stockDocumentAccess.ts`, built on `documentTypeRecordPermission`; a type the user cannot record is not offered and the button says which permission is missing; v9.0.241, TD-791). The top bar and the profile show the role's stored name, which `/users/my-permissions` returns to every user, the system admin included; no label is built from a role code (v9.0.149, TD-894). Code names the system admin only through `SYSTEM_ADMIN_ROLE` (server) or `userPermissions.isAdmin` (browser), and an unknown actor is recorded as «سیستم», never as `admin` (v9.0.177, TD-896).
- **Document Permissions by Type and Status (v9.0.125, TD-541 / TD-771, product-owner decision ت۱ of package 8):** One table says which permission records a document (`documentRecordPermission` in `src/lib/permissions/documentPermissions.ts`, shared with the invoice form): a sales document (`invoice`, `proforma`, `return`) as draft or proforma needs `documents.create`, final or finalized `documents.finalize`; a warehouse document `warehouse.in` / `warehouse.out` by the stock direction of its type (`stockDirectionOf` in `src/services/documents/documentRecordRule.ts`, the function the services move stock with; v9.0.238, TD-770); a stock count `audit.apply`. `POST /documents`, `PUT /documents/:id/finalize` and the workflow approval step (the document action's `requiredPermissions` reads the document) check it with `can`, never a role code. A draft stays a draft; an `invoice` proforma recorded by a user without `documents.finalize` is stored as type `proforma`, as before. Migration 0063 gave `documents.finalize` to the seed manager, warehouse keeper, accountant and CFO and to roles expanded from `*`, logged in `activity_logs`.
- **Personnel and Payslip Bank Details by Permission (v9.0.126, TD-882, permission model §4.2):** Card, Sheba and account number and the Nobitex username are unmasked only for the system admin, the record's own linked user, and holders of `personnel.view_sensitive` or `personnel.manage` (personnel dossier) or `payroll.view_sensitive` or `personnel.manage` (payslips) — `canAccessSensitivePersonnelData` / `canAccessSensitivePayrollData` in `src/lib/piiMasker.ts`, through `can`; no role code and no `*` opens them. Migration 0064 gave both keys to the seed manager and the other key to roles holding one of them, logged in `activity_logs`.
- **Notification Recipients by Permission (v9.0.127, TD-883, permission model §4.2):** An event rule's in-app notification goes to one user (`targetUserId`), to the holders of a catalog permission (`targetPermission`: the system admin and every non-deleted user whose role holds the key, `permissionHolderUserIds` in `src/services/notifications/notificationRecipients.ts`; an unknown key is refused with 422), or to a role the admin chose in the rule (`targetRole`, data); without a target to the system admin. The default reorder alert targets `warehouse.view`, a won sales lead notifies the holders of `crm.manage` except its sender, and the rule editor picks the permission from the catalog. Code never names a recipient role other than `SYSTEM_ADMIN_ROLE`; rules already stored were left as they are.
- **Read Scope by Section Permission (v7.0.53, audit P2-10, product-owner decision — existing permissions only):** Global search returns each section only to holders of its view permission (items `products.view`, customers `customers.view`, documents/invoices `documents.view`, projects `projects.view`; a section without permission is empty, never an error); it folds Arabic «ي» / «ى» / «ك» and Persian and Arabic digits on both sides with `normalizeSearchText` (`src/lib/search/searchText.ts`, also used by `SearchableSelect`) and ranks each section exact match, then starts with, then contains (v9.0.291, TD-675). - **Rial Cost Rows in Foreign Documents (v8.0.18, TD-261, product-owner decision):** In a foreign-currency voucher, rows that carry a rial Kardex cost (cost of sales, inventory, donated goods) stay in the document currency and get their own exchange rate = rial value ÷ foreign amount (`foreignCostRow` / `rowExchangeRate` in `src/services/accounting/foreignCostRow.ts`), so amount × row rate equals the Kardex value exactly; cost of sales is the sum of the inventory rows so the voucher stays balanced in its currency. The server computes the amount from `vat_percent`; an explicit amount sent with a positive percent must equal it, else 422 `VAT_AMOUNT_MISMATCH`, and the sales invoice form sends only the percent (v8.0.104, TD-381). The percentage amount is rounded to the document currency's smallest unit (`currencyScale` in `src/lib/currencyScale.ts`: rial without decimals, other currencies two decimals; v8.0.105, TD-382). A sales return carries VAT too (v9.0.274, TD-774, decision ت۵ of package 8): with an original invoice its percent is the invoice's and its amount the invoice VAT's share of the returned net, counted over the invoice's final returns — share(n) = min(invoice VAT, invoice VAT × n ÷ invoice net rounded like TD-382), this return's VAT = share(earlier + this) − share(earlier) — so returning the whole invoice in parts gives back exactly its VAT; another percent or amount is 422 `RETURN_VAT_MISMATCH` (`resolveReturnVatFromInvoice` in `src/services/documents/salesReturnVat.ts`, on create, draft edit and finalize). A return without an original invoice takes the user's percent. The return voucher debits sales returns with the net and VAT payable (3203) with the VAT and credits the customer with both. The sales voucher reads `vat_amount` only — NEVER parse amounts, rates or taxes out of free-text `notes`, and never write VAT into notes. Payable amount = net of lines + `vat_amount` (+ `service_charge_amount`, see below).
- **Line Discount Within the Line (v8.0.103, TD-380):** A document line's discount is at most its quantity × unit price; create and update refuse a larger one with 422 `LINE_DISCOUNT_EXCEEDS_AMOUNT` (`assertLineDiscountsWithinAmount` in `src/services/documents/lineDiscount.ts`), and the sales invoice form checks the same rule before adding a line (`lineDiscountError` in `src/lib/invoices/invoiceLine.ts`).
- **Service Charges (v7.0.103, TD-191, product-owner decision «ثبت کامل»):** A sales invoice's shipping and fee charges live only in `documents.service_charge_amount` (non-negative; set by the WooCommerce sync from `shipping_lines` / `fee_lines`, while the order's `total_tax` goes to `vat_amount`). The sales voucher credits them to «درآمد حمل و خدمات» (`serviceRevenueAccountCode`, default 5004). Payable amount = net of lines + `vat_amount` + `service_charge_amount`; a WooCommerce order whose invoice total differs from the order `total` is rejected as a whole.
- **Structured Exchange Rate (TD-198, v7.0.63, product-owner decision):** The exchange rate of a non-IRR document (IRR per one unit of its currency) lives only in `documents.exchange_rate` and is required on create, update and finalize (`src/services/documents/documentExchangeRate.ts`). Pre-v7.0.63 documents were not migrated. - **Attachments on Disk (v7.0.56, audit P2-9, product-owner decision):** Attachment files of documents, journal vouchers, cheques, treasury transactions, projects and payrolls live in `public/uploads/.attachments/` (never served by `/uploads`; `public/uploads` never enters `dist/`, the Docker image or a source package: `copyPublicAssets` in `scripts/publicAssets.ts`, v9.0.180, TD-588) and are registered in `file_attachments`; the JSONB `attachments` columns hold metadata and `/api/attachments/<id>` only — never Base64. ## 11. Modular Accounting Services & Facade Pattern
- **6 Sub-Services in `src/services/accounting/`:**
  1. `ChartOfAccountsService`: Coding hierarchy, standard accounts, tree generation.
  2. `VoucherService`: Journal vouchers, atomic sequence (`voucher_number_seq`), balanced debit/credit validation.
  3. `TreasuryService`: Bank accounts, cash funds, petty cash, Sayad cheques lifecycle, treasury transactions.
  4. `AccountingReportService`: Trial balance (2/4/6/8-col), detailed ledger, balance sheet, income statement.
  5. `VoucherSyncService`: Automated vouchers for sales, purchases, warehouse movements, payroll.
  6. `FiscalYearService`: Closing temporary/permanent accounts, opening/closing vouchers.
- **Unified Facade:** `AccountingService` in `src/services/accounting.service.ts` binds all sub-services for 100% backwards compatibility.
- **AccountNature Consistency:** Standard type is `AccountNature = 'debit' | 'credit' | 'both'`.
- **Fiscal Periods (v7.0.49, audit P2-5, product-owner decisions):** Whether a (Jalali) fiscal year is closed lives ONLY in `fiscal_periods` (`FiscalPeriodService`); never infer it from voucher reference numbers. Every voucher create/update/delete/reverse/finalize calls `VoucherService.checkFiscalPeriodOpen(date, tx)`, which locks the year's row `FOR SHARE`; `FiscalYearService.executeFiscalYearClosing` locks it `FOR UPDATE` before computing balances and marks it closed in the same transaction. No voucher type (including `closing`) bypasses the check. The double-entry balance tolerance is the single constant `VOUCHER_BALANCE_TOLERANCE = 0.01` in every path (`src/lib/voucherBalance.ts`; the voucher forms use `computeVoucherBalance` from the same file, v7.0.76).
- **Manual Voucher Currency and Rial Balance (v9.0.190, TD-551, product-owner decision ت۷):** A manual voucher (`POST` / `PUT /accounting/vouchers`, which pass `manualEntry`, never read from the body) and a correction voucher resolve each row's currency as the row's own, else the voucher's, else IRR, and need a positive rate on every non-rial row (422 `VOUCHER_ROW_RATE_REQUIRED`, never rate 1); rows of one currency at one rate balance on their own amounts, any other voucher in rials by the TD-260 rule (`computeVoucherCurrencyBalance` in `src/lib/accounting/voucherCurrencyBalance.ts`, `resolveManualVoucherRows` / `assertVoucherRowsBalanced` in `src/services/accounting/voucherRowBalance.ts`). Every path balances a multi-currency voucher in rials, and finalizing accepts one whose rows balance in rials (`isVoucherBalancedForFinalize`). The journal book filters rows by the TD-260 currency rule and shows the «all currencies» view in rials with the row's own amount and rate; the financial health check balances multi-currency vouchers in rials and lists vouchers with a non-rial row at rate empty, 0 or 1 (`voucher_foreign_rows_without_rate`), never rewriting them. The manual voucher form, its edit and the correction form send and keep each row's currency and rate (v9.0.191, TD-564): the voucher and row currencies come from `TREASURY_CURRENCIES` (no «تومان»; the manual voucher routes refuse another code with 400), an empty row currency follows the voucher and an empty rate of a row in the voucher currency takes the voucher rate (`withVoucherRowCurrency` in `src/lib/accounting/voucherFormCurrency.ts`), and the forms balance and add the balancing row with the server's rule (`voucherFormBalance`, `voucherBalancingAmount`). A voucher row's debit, credit and rate are read with `decimalInput` (v9.0.192, TD-557). Its detailed type comes from `VOUCHER_DETAILED_TYPES` (`src/lib/accounting/voucherDetailedTypes.ts`, shared by the schema and both forms through `VoucherDetailedPicker`; a legacy `custom` row is «متفرقه» `other`), and the project detail reads the project pick list, which `accounting.vouchers` opens (v9.0.193, TD-569). The voucher print follows the same balance rule (`voucherPrintAmounts` in `src/lib/accounting/voucherPrintAmounts.ts`: a single-currency voucher in its currency with its rate, a multi-currency one in rials with each row's own amount and rate), and voucher types are named only through `VOUCHER_TYPE_LABELS` (`src/lib/accounting/voucherTypes.ts`, settlement «تسویه» included) (v9.0.195, TD-573). The voucher, correction and reversal forms and the accounting report filters keep ISO dates in `JalaliDateInput`; no accounting component imports `react-multi-date-picker` directly (v9.0.196, TD-578).
- **Draft Vouchers at Closing and Void (v8.0.2, TD-252 / TD-251, product-owner decision):** Automatic vouchers stay `draft` until an accountant approves them. A fiscal year is never closed while a draft voucher dated in that (Jalali) year exists: `FiscalYearService.findDraftVouchersOfYear` runs after the year lock, `executeFiscalYearClosing` refuses with `FISCAL_YEAR_HAS_DRAFT_VOUCHERS`, and the preview returns `draftVouchers` / `draftVoucherCount` (the closing button stays disabled). Voiding a source — document/invoice, treasury transaction, cheque, payroll — goes through `VoucherService.voidSourceVoucher`: a draft voucher is soft-deleted (fiscal period checked), an approved or permanent one gets a reversal voucher; never issue an approved reversal for a draft.
- **Closing Dates Are the Year's Bounds (v8.0.47, TD-310, product-owner decision):** A fiscal year is the Jalali year. Closing vouchers are always dated the year's last day (30 Esfand in a leap year, else 29 Esfand) and the opening voucher 1 Farvardin of the next year; balances are taken up to that last day. `resolveFiscalClosingDates` (`src/services/accounting/fiscalYear.service.ts`, built on `jalaliYearBounds` in `src/utils/calendarDate.ts`) derives them from the year and refuses any other date sent by a client (422); the closing form only displays them.
- **Closing Vouchers Are Linked to Their Year (v9.0.159, TD-545, product-owner decision ت۳):** The closing and opening vouchers a fiscal-year closing issues carry `journal_vouchers.source_fiscal_year` = the closed year (migration 0069 linked the earlier runs of closed years); a closing voucher is only such a linked `closing` voucher, never a voucher found by type or reference number. The trial balance, income statement, balance sheet and ratios leave a linked closing voucher out when it is dated on or after the report's end date (income statement: its start date), unless `includeClosing` («همراه اسناد اختتامیه», `yearEndClosingVoucherSql` / `yearEndClosingCutoff` in `src/services/accounting/yearEndClosingVouchers.ts`); the opening voucher always counts, and the closing computation reads its balances with `includeClosing: true`. A manual voucher (`POST` / `PUT /accounting/vouchers`) never takes the type `closing` (the form offers «افتتاحیه», `opening`) nor a reference with a reserved prefix of the system (`isReservedVoucherReference` in `src/lib/accounting/manualVoucherRules.ts`); whether a year is closed is read only from `fiscal_periods`, never from reference numbers; a voucher of a closing run (its opening voucher included) is never reversed, corrected or put back to draft (409 `FISCAL_CLOSING_VOUCHER_LOCKED`), while a legacy manual `closing` voucher is an ordinary voucher listed by the financial health check (`manual_vouchers_closing_type`) (v9.0.160, TD-559).
- **Close After the Year Ends, Reopen the Last Closed Year (v9.0.161, TD-543, product-owner decisions ت۱ / ت۲):** A fiscal year is closed only when the business today is past its last day (422 `FISCAL_YEAR_NOT_ENDED`, `assertFiscalYearEnded` in `src/services/accounting/fiscalYearOrder.ts`); the preview carries `yearEnded`, and the closing form takes its years from `GET /accounting/fiscal-closing/years` (ended years only, with status and whether they have vouchers; never the current or a future year). Only the last closed year (every later year open) is reopened, through `POST /accounting/fiscal-closing/reopen` with a required reason and the permission `accounting.fiscal_reopen` (granted to no role by default): `reopenFiscalYear` (`src/services/accounting/fiscalYearReopen.ts`) takes the fiscal-year sequence lock (`ADVISORY_LOCK_KEYS.FISCAL_YEAR_SEQUENCE` 91020, also taken by closing) and the year's `fiscal_periods` row lock, opens the year, voids the active vouchers of its latest closing run (linked by `source_fiscal_year`, neither reversals nor reversed) through `voidSourceVoucher` with a reversal on each voucher's own date, and writes the audit row with `tx`. Years closed before their end are only listed by the financial health check (`fiscal_year_closed_early`). Years close in order (v9.0.162, TD-544, decision ت۱): a year closes only when every earlier year holding an active voucher of any status is closed (`assertEarlierYearsClosed`, same file, after the year row lock; else 422 `FISCAL_YEAR_EARLIER_OPEN` naming them); the preview carries `earlierOpenYears`, the form starts on the oldest open year with vouchers (`defaultYear`), and years closed before an earlier year with vouchers are only listed by the health check (`fiscal_year_closed_out_of_order`).
- **Cheque ↔ Voucher Link (v8.0.19, TD-271):** Every voucher of a cheque's lifecycle (registration, in collection, cleared, bounced, spent) carries `journal_vouchers.source_cheque_id` (migration 0047); find a cheque's vouchers by it, never by the cheque number (not unique). `deleteCheque` refuses while an unlinked legacy voucher of a number shared by another cheque remains. A cheque with a permanent voucher that has no reversal is never deleted (409 naming the voucher; v9.0.69, TD-502, product-owner decision ت۹), and the cheque row menu offers no status change or delete in a terminal status (`chequeHasNextStep` in `src/lib/treasury/chequeTransitions.ts`, the one transition table of the server and the browser). A bounced paid cheque posts Dr cheque payables / Cr the supplier (v8.0.21, TD-272); returning a bounced received cheque to its drawer posts Dr the customer / Cr the protested-cheques account (v8.0.22, TD-273, product-owner decision). ## 12. Kardex Event Sourcing & Inventory Reconciliation
- **Event-Driven Verification:** Calculate true stock balances from sequential `stock_movements` log.
- **Three-Way Invariant:** `item_warehouse_stocks` (truth) = `items.current_stock` (database-maintained sum) = Kardex ledger balance (active rows, excluding reversals of soft-deleted rows). Kardex locations and legacy JSON keys map to warehouses with one rule (`createLedgerLocationResolver`: '' / 'default' = default warehouse, then code, then name, all warehouses). The Kardex rebuild refuses (never silently drops) items with movements in an unresolvable location or a negative per-warehouse balance.
- **Running Kardex Report (v8.0.7, TD-266, product-owner decision «نمایش با برچسب»):** The item Kardex report (`buildItemRunningKardex` in `src/services/inventory/runningKardex.service.ts`, `GET /inventory/item-kardex/:itemId`) lists rows in (day, id) order and shows a voided document's original row on its own date (`isVoided`, label «باطل‌شده») and its reversal on the void date (`isReversal`, «معکوس ابطال»); the running balance counts both, the in/out totals count only ledger rows, each row's WAC is the live engine's WAC right after that row was registered (`createKardexReplayer`), and warehouses are keyed with `createLedgerLocationResolver`. The stock movement chart (`getMonthlyMovementTrends`) counts the same ledger: `LEDGER_ROW_FILTER`, only `in` / `out` rows, no warehouse transfer, from the first day of the window to the end of the current Jalali month (v9.0.94, TD-492). The warehouse dashboard counts the same ledger (`src/services/inventory/dashboardMovementStats.ts`): «recent documents» are distinct documents of `LEDGER_ROW_FILTER` rows, fast-moving, slow-moving and dead stock read only ledger `out` rows without warehouse transfers, and «the last N days» are the business today and the N − 1 days before it (v9.0.289, TD-671).
- **Warehouse Stock Reconciliation (TD-200, v7.0.33):** `WarehouseStockReconciliationService` compares `item_warehouse_stocks` with the Kardex ledger (active rows, excluding reversals of soft-deleted rows). Repairs are manual only, dry-run by default, correct quantities only (never WAC), never auto-adjust negative ledger balances or items with unresolvable Kardex locations, and log every change/refusal to `inventory_reconciliation_anomalies`. Data-fixing migrations must never clamp or overwrite silently: add (`existing + EXCLUDED`) and record anomalies.

## 15. Enterprise Domain Event Bus & Outbox Pattern
- **Event Catalog:** Domain events follow `BaseDomainEvent` contract (`eventId`, `eventType`, `aggregateType`, `aggregateId`, `payload`, `metadata`, `occurredAt`).
- **DomainEventBus:** Central singleton dispatcher (`src/services/events/domainEventBus.ts`) with non-blocking handlers.
- **Transactional Outbox:** Write events atomically inside `tx` via `OutboxService.recordEvent(tx, event)`.
- **Exponential Backoff Worker:** Polls pending events, dispatches, retries (5s, 10s, 20s... max 5 attempts).
- **Tracked Dispatch (TD-183, v7.0.25):** `publish()` stays fire-and-forget (non-blocking, errors only logged). The outbox worker and DLQ replay MUST use `domainEventBus.dispatchTracked(event, completedHandlers)`, which awaits every handler and reports failures. Every handler is registered with a stable name (`subscribe(type, fn, name)`) and MUST rethrow its errors after logging; succeeded handler names are persisted in `outbox_events.completed_handlers` so retries never re-run a handler that already succeeded.
- **Dead Letter Queue (DLQ):** Failed events transfer to `dead_letter_queue` with replay/dismiss endpoints. Replay and dismiss of one DLQ row run under that row's session advisory lock (`withDeadLetterRowLock`, `withRowAdvisoryLock` namespace 91007; never an open transaction around the handlers): a concurrent replay or dismiss is refused (409) and the outbox requeue skips a row being replayed. A replayed event is never replayed or dismissed again; a dismissed one may be replayed (v8.0.75, TD-342).
- **Automated Event Actions:** `EventActionEngineService` dynamically triggers webhooks, notifications, SMS, or workflows based on rules.
- **HMAC-SHA256 Signatures:** Webhooks sign payload with HMAC-SHA256 and attach `X-ERP-Signature-256` and `X-ERP-Delivery-Id`.

- **Guarded Background Polling:** Intervals (`setInterval`) must check active sub-tab state and clean up on unmount.

## 19. Concurrency, OCC & Database Stability Rules
- **PostgreSQL Atomic Sequences (DB-001, DB-003, DB-011):** Sequence IDs generated via `nextval('...')` or the `document_ref_counters` / `item_code_counters` counter tables.
- **Idempotency OCC Locks (DB-010):** `IdempotencyService` uses `.onConflictDoNothing()` and OCC (`status` and `locked_until` in UPDATE WHERE clause).
- **Idempotency Key Contract (v8.0.79, TD-329):** The `idempotency` middleware stores only 2xx responses and releases the key on any other status (`releaseKey`), both before the response is sent; a key recorded for another method, path or body gets 422 `IDEMPOTENCY_KEY_REUSED` and is not executed; the key's lock is extended every third of its window while the request runs (`extendLock`). The browser derives the key from the submission's content (`submissionKeyFor` in `src/lib/submissionKey.ts`), keeps it until a definitive response (network errors, aborts and 502/503/504 keep it), never mutates the caller's options, and waits on 409 `IDEMPOTENCY_IN_FLIGHT` with the same key. After a network error only a GET is resent automatically; a POST / PUT / PATCH / DELETE is sent once and reports `UNCONFIRMED_MUTATION_MESSAGE` (check the result, then resend with the same key) (v9.0.296, TD-670, product-owner decision ت۳ of package 16).
- **Customer Optimistic Lock (v8.0.122, TD-403):** `PUT /customers/:id` requires the record's `version` (400 without it) and writes with the version in its WHERE (409 `OCC_CONFLICT` when stale or changed meanwhile); the customer Excel export carries «نسخه» and an imported row with an `id` is applied only at the current version, otherwise listed in the import errors. A sales lead never changes an existing customer (v9.0.5, TD-418, product-owner decision): creating, editing or converting a lead only links a customer (id, then exact phone, then exact name) or creates a new one (`linkCustomerForLead` in `src/services/crm/crmCustomerLink.ts`), and a differing phone or company name goes only into the lead's notes. Two active customers never share a name (v9.0.8, TD-420, product-owner decision): the key is `lower(btrim(name))`, checked by `assertCustomerNameAvailable` (`src/services/customers/customerIdentity.ts`) and enforced by the partial unique index `uq_customers_name_active` (migration 0052, created only on data without duplicates; the financial health check lists duplicates as `customer_name_uniqueness`); an index violation is the same Persian duplicate-name error. In the customer Excel import an empty party-type cell leaves an existing party's type unchanged and makes a new party a customer (v9.0.9, TD-421); the cell is read only through `parsePartyTypeCell` (`src/lib/customers/partyTypeCell.ts`, shared by the server and the preview). A party is never deleted while it has open business (v9.0.10, TD-431, product-owner decision): `deleteCustomer` locks the customer row and `assertCustomerDeletable` (`src/services/customers/customerDeleteGuard.ts`) refuses with 409 and Persian reasons a nonzero approved/permanent balance in any currency, draft voucher rows (both by `partyDetailedRowsCondition`), a draft or proforma document whose trimmed buyer name equals the party name, an active lead, a project not completed or cancelled, or a cheque in a status that still has a next step in `CHEQUE_TRANSITIONS`.
- **Stock Soft Delete & Reversal (DB-009):** `is_deleted = 1` + reversal transaction + balance recalculation.
- **Negative Stock Guard (DB-006, TD-180):** Inventory deductions below zero are rejected (policy fixed to `forbidden`, enforced in `ItemWarehouseStockService.applyMovement` and by the DB CHECK constraint).
- **No Second Pool Connection Inside a Transaction (v8.0.77, TD-324):** Code running inside a transaction uses that `tx` only — never `orm` / `pool` (with a full pool it waits for the connection timeout). Pass `tx` to `logActivity` (an insert error then propagates instead of turning COMMIT into a silent ROLLBACK), `FiscalPeriodService`, `startInstance` and `maybeStartWorkflow` (both run inside a savepoint of that `tx`; default workflows are seeded only at startup, only when their code is missing, and never overwritten — v9.0.46, TD-453, product-owner decision ت۸). `maybeStartWorkflow` returns null only when the entity type has no active definition; any start error propagates and rejects the caller's operation, never read as «no workflow» (v9.0.36, TD-451). `getDisplayTimezone` serves a stale cache without waiting and is warmed outside transactions (`warmDisplayTimezone`).
- **Stock Item Locks (v8.0.67, TD-320):** Every stock path (document create / finalize / void, sales return, transfer, BOM allocation, project delivery) locks ALL its items at once, in ascending id order, with `FOR NO KEY UPDATE` (`lockStockItems` in `src/services/inventory/stockItemLocks.ts`, or `withOrderedLocks`, which uses the same mode for items) BEFORE the document counter, the document row or any Kardex / line insert; a void locks items → project → document. Never lock an item row `FOR UPDATE` in these paths: inserting a Kardex row or document line takes a `FOR KEY SHARE` foreign-key lock on the item, which conflicts with `FOR UPDATE` and deadlocks concurrent voids. `withOrderedLocks` sorts by `LOCK_ORDER_MAP` in every environment and refuses a table without a lock level (v9.0.189, TD-618).

## 22. Database Migrations, Base Data at Boot & Pool Timeouts
- **Atomic Migrations (DB-013):** `src/db/migrator.ts` runs the official Drizzle migrator over `drizzle/*.sql` (journal: `drizzle/meta/_journal.json`) in an atomic transaction; applied migrations are tracked in `drizzle.__drizzle_migrations`. Every new migration MUST be registered in the journal. `runMigrations()` never throws: every caller MUST check `result.success` and stop on failure (v7.0.50, TD-217 — `setupTestSchema`, `ensureTestDatabaseReady`/`assertTestDatabaseReady`, `runSeed`, `server.ts`).
- **Migration Journal and Session (v8.0.81 / v8.0.82, TD-364 / TD-366):** A new migration's journal `when` is greater than every earlier entry — the Drizzle migrator applies only entries newer than the database's last applied one and skips an older `when` silently. `runMigrations` compares the journal with `__drizzle_migrations` first (`planMigrations` in `src/db/migrationPlan.ts`) and refuses a skipped migration or a database newer than the build; Vitest `migrationPlan.test.ts` lints the journal (strictly increasing `when`, tag = idx, every `.sql` registered). Migrations run on one dedicated connection without the request statement timeout (`MIGRATION_STATEMENT_TIMEOUT`, default 0) under advisory lock 91008, so two runs queue instead of failing.
- **Released Migrations Stay as Released (v8.0.89, TD-368):** A migration file changes after release only to remove an upgrade blocker for databases that have not run it; its previous sha256 goes into `AMENDED_MIGRATIONS` (`src/db/migrationAmendments.ts`) so databases that ran the old text get no hash warning. A data `UPDATE` in a migration runs through `erp_update_with_unvalidated_checks(table, sql)` (0047) when the table can hold NOT VALID CHECK constraints: they are dropped for the statement and re-added exactly as they were, because a NOT VALID CHECK still applies to every updated row and one refused legacy row would roll back the whole upgrade.
- **Backup, Restore and Upgrade Rehearsal (v8.0.83–v8.0.88, TD-360..TD-363, TD-365, TD-367):** `scripts/backup.sh` locates the app directory itself and reads `DATABASE_URL` / `ATTACHMENTS_DIR` from its `.env` (cron from any directory), writes the dump and a content manifest (`scripts/sql/backup-manifest.sql`: rows and content hash of every table, every constraint) from one exported snapshot, and archives `public/uploads` — attachment records without the attachment directory fail the backup. A failed run removes the partial files it wrote and a database before its first migration is backed up (v9.0.184, TD-606). Backups are private: the backup directory is `0700` and every file `0600` (`umask 077`), and `scripts/go-live-verify.sh` fails readable ones (v9.0.122, TD-585). `scripts/restore.sh` drill compares the restored database with that manifest; creating databases needs `RESTORE_ADMIN_URL` or `sudo -u postgres` (the install.sh role has no CREATEDB); `apply` never restores over the live database: it builds and verifies a new one, refuses while sessions are connected, swaps names and keeps `<db>_before_restore_<ts>` and the previous uploads directory. `update.sh` reports success only when `/health/startup` answers on the `PORT` of `.env` and the running version is the built one (`scripts/verify-startup.sh`); a failed build puts the previous `dist/` back without restarting, and any failure after the source changed prints the rollback steps once, warning that restoring the backup erases later writes (v9.0.123 / v9.0.124, TD-586 / TD-587). The rollback step resets the branch to the previous commit (`git reset --hard <commit>`), never a detached checkout (v9.0.181, TD-603) `update.sh` and `scripts/go-live-verify.sh` read `.env` literally, like the service (`node --env-file`), and never run it as shell code (v9.0.183, TD-605). `update.sh --rehearse` / `scripts/upgrade-rehearsal.sh` run the new migrations on a restored copy first (`src/db/upgradeRehearsal.ts`, only on `erp_restore_drill_*` databases) and stop before the restart when they fail or change ledger totals per account, stock per item and warehouse, bank balances or the financial health check.
- **Base Data at Boot (DB-014):** The seed runs at every boot in every environment, production included (v9.0.134, TD-526, permission model decision ت۶; the old `ALLOW_SEED_IN_PRODUCTION` flag is retired and ignored), under advisory lock (`pg_try_advisory_lock(89345)`). It only inserts what is missing (v9.0.133, TD-591, package 1 decision ت۴): each kind of base data (the categories of `DEFAULT_CATEGORIES` in `src/data/defaultCategories.ts`, default settings, piecework tasks, the standard chart of accounts) is inserted only into a database that holds none of that kind, and no existing row (role permissions, category, account, setting) is ever edited, so nothing an admin removed or changed comes back. It creates no role: a fresh install has only the system admin role (migration 0066), and every other role is made by the admin with «ساخت نقش از الگو» from `ROLE_TEMPLATES` (`src/lib/permissions/roleTemplates.ts`; a template only fills the role form, and its permission list is closed under `requires`); test schemas get the template roles from the test bootstrap. `GET /categories` only reads. The boot data steps live in `prepareDatabaseAtBoot` (`src/services/system/bootData.ts`).
- **Session-Level Timeouts (DB-012):** `statement_timeout = 60000` ms and `idle_in_transaction_session_timeout = 60000` ms (defaults of `DB_STATEMENT_TIMEOUT` / `DB_IDLE_IN_TX_TIMEOUT`), sent in the pool's connection startup `options` (v7.0.39). A bulk task extends the statement timeout of its own transaction with `extendStatementTimeout(tx)` (`src/db/drizzle.ts`, `SET LOCAL`, 5 minutes; v9.0.188, TD-615), never on another pool connection. The same `options` pin the session `TimeZone=UTC`, and `src/lib/processTimezone.ts` (the first import of `server.ts` and the test runner) sets the process `TZ=UTC`, so server timestamps (`defaultNow()`, `toISOString()`, stored without a zone) are UTC on every host; business «today» still comes only from `businessClock` (v8.0.52, TD-314).
- **Single-Instance Deployment (v7.0.44, product-owner decision):** The system runs as ONE server process (one workshop, at most 20 concurrent users). In-memory caches, rate limiters and process-level locks assume a single process; do not add multi-replica infrastructure (Redis, object storage, cross-instance cache invalidation). The Kubernetes manifest uses `replicas: 1` with `strategy: Recreate` and no autoscaler.

## 24. GitHub Sync Policy
- **Commit & Push (v9.0.0, product-owner decision):** Commit with descriptive messages on a separate branch (`v9/<phase or package>-<topic>`) and open a draft pull request; never push directly to `master` — merging is the product owner's step. In local development the same applies whenever Git credentials allow a push.
- **Cloud & Sandbox Environments:** In environments without Git credentials, avoid executing failing push commands that interrupt workflow.
- **Exclusions:** Never commit `.env`, local database directories (`/pgdata`, `/logs`), or source archives.
- **Vendored SheetJS (v7.0.58, audit P2-13 / TD-173, product-owner decision):** `xlsx` (a devDependency since v7.0.84) is installed from `vendor/xlsx-0.20.3.tgz` (the official SheetJS build, published only on cdn.sheetjs.com — the npm `xlsx@0.18.5` is vulnerable). This tarball is the one allowed third-party archive in the repository. Upgrade only by replacing it with a newer official tarball and updating the `package.json` reference and lockfile; never switch back to the npm package.
- **Runtime vs Dev Dependencies (v7.0.84, TD-177):** `dependencies` holds exactly the packages the server bundle requires (the Docker image installs only these with `npm ci --omit=dev`); frontend-only libraries (React, icons, fonts, xlsx …) go in `devDependencies`. Enforced by `npm run check:runtime-deps` and Vitest `runtimeDependencies.test.ts`. The audit gate (`npm run audit:gate`) reads `npm audit` over all dependencies so browser libraries stay covered, and fails when `npm audit` itself fails (v9.0.185, TD-607).
- **Conflict Handling:** Always use `git pull --rebase` if remote has progressed; never force-push.
