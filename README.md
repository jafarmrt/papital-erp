# سامانه جامع ERP و CRM کارگاه — پاپیتال

سیستم یکپارچه مدیریت کارگاه تولیدی: انبارداری با کاردکس رویدادمحور، فاکتور و پیش‌فاکتور، حسابداری دوبل (کدینگ ۴ سطحی، دفتر روزنامه، تراز آزمایشی)، خزانه‌داری و چک صیادی، CRM و قیف فروش، کنترل پروژه‌های تولید با BOM، منابع انسانی و حقوق و دستمزد، موتور گردش کار (ورکفلو) با کارتابل تاییدات، گذرگاه رویدادها (Outbox/DLQ/Webhook) و گزارش‌های BI.

> **نسخه فعلی:** سری فعال `v10.x.y` (نسخه مستقر: `v10.3.11`) — نقشه راه: `docs/roadmap/V10_MASTER_ROADMAP.md` (سری‌های بسته‌شده: `docs/roadmap/archive/V9_MASTER_ROADMAP.md`، `docs/roadmap/archive/V3_V8_ROADMAPS_SUMMARY.md`) • تاریخچه تغییرات: `CHANGELOG.md` + `src/data/changelogs/10.ts`

## معماری

| لایه | تکنولوژی |
|---|---|
| Frontend | React 19 + Vite 6 + Tailwind CSS 4 + TanStack Query v5 + React Router 7 + Motion 12 + react-multi-date-picker |
| Backend | Node.js 24 + Express 5 + TypeScript 5.8 (tsx در توسعه / esbuild در بیلد تولید) |
| Database | PostgreSQL 14+ (پیشنهادی 16/17) با Drizzle ORM 0.45 — مهاجرت اتمیک داخلی (`src/db/migrator.ts`) |
| احراز هویت | JWT در کوکی امن HttpOnly (`auth_token`) |
| رویدادها | Domain Event Bus + Transactional Outbox + DLQ + Webhook با امضای HMAC-SHA256 |
| اعتبارسنجی و لاگینگ | Zod 4 + Winston Logger + prom-client (Prometheus Metrics) |

ساختار کلیدی: `src/routes` (API) • `src/services` (منطق کسب‌وکار، شامل `accounting/`) • `src/components` + `src/pages` (UI) • `src/db` (schema + migrator + seed) • `src/tests` (سوییت ۱۵ سناریوی بحرانی)

**قاعده طلایی مهاجرت:** ساختار دیتابیس فقط از migrator اتمیک داخلی اعمال می‌شود. اجرای `npm run db:push` در نصب/آپدیت **ممنوع** است.

## نصب — مسیر ۱: ویندوز محلی (شخصی)

اسکریپت آماده، PostgreSQL پورتیبل و سرور توسعه را یکجا بالا می‌آورد:

```powershell
# از ریشه پروژه
.\start-local.ps1
# → PostgreSQL روی پورت 5433 + اپلیکیشن روی http://localhost:3000
```

اجرای دستی (بدون اسکریپت):

```powershell
npm install
npm run dev          # سرور توسعه + API روی پورت 3000
```

مهاجرت‌ها و داده پایه (دسته‌ها، کدینگ استاندارد و تنظیمات پیش‌فرض) در هر محیط، تولید هم، به‌صورت خودکار در startup ساخته می‌شوند. نصب تازه جز «مدیر سیستم» نقشی ندارد؛ نقش‌های دیگر را مدیر در زبانه نقش‌ها با «ساخت نقش از الگو» می‌سازد.

## نصب — مسیر ۲: سرور / VPS لینوکسی

### روش ۱: نصاب خودکار (پیشنهادی)
اسکریپت نصاب خودکار `install.sh` تمام مراحل نصب پیش‌نیازها، تنظیم دیتابیس PostgreSQL، بیلد پروژه، راه‌اندازی سرویس systemd و زمان‌بندی بکاپ روزانه و پایش سرور را انجام می‌دهد. رونوشت رمزگذاری‌شده بکاپ در گوگل‌درایو و کانال هشدار یک بار دستی تنظیم می‌شوند: `docs/OFFSITE_BACKUP.md`.

```bash
git clone <repo-url> && cd <repo>
sudo ./install.sh
```

### روش ۲: راه‌اندازی دستی
```bash
git clone <repo-url> && cd <repo>
cp .env.example .env               # سپس مقادیر را ویرایش کنید
npm ci
npm run build                       # کلاینت + bundle سرور (dist/server.cjs)
NODE_ENV=production npm start      # مهاجرت‌ها هنگام startup اعمال می‌شوند
```

برای به‌روزرسانی خودکار سرور و سرویس‌های در حال اجرا در آینده نیز اسکریپت `update.sh` آماده است:

```bash
cd /opt/papital-erp
sudo ./update.sh --rehearse   # بکاپ + build + آزمایش مهاجرت‌ها روی رونوشت + restart + health
sudo bash scripts/go-live-verify.sh http://localhost:3000   # باید STATUS : READY بگوید
```

### تنظیمات اولیه پس از نصب

با مراجعه به `/setup` و وارد کردن `ERP_SETUP_TOKEN` (از `.env`) در فرم، حساب مدیر ارشد ایجاد و تنظیمات شرکت ثبت می‌شود؛ رمز در نشانی نوشته نمی‌شود.

## به‌روزرسانی

```bash
cd /opt/papital-erp
sudo ./update.sh --rehearse # پیشنهادی: پشتیبان پیش از استقرار، دریافت کد، ساخت، آزمایش مهاجرت‌های تازه روی رونوشت بازگردانی‌شده، ری‌استارت و بررسی نسخه
sudo ./update.sh            # همان، بی آزمایش مهاجرت‌ها
sudo bash scripts/go-live-verify.sh http://localhost:3000   # پس از هر به‌روزرسانی: باید STATUS : READY بگوید
```

`update.sh` پس از سنجش جای دیسک، پیش از تغییر کد خودش از پایگاه‌داده پشتیبان می‌گیرد (`pre-deployment`)، سرویس systemd (`papital-erp`) را ری‌استارت می‌کند و مهاجرت‌های تازه هنگام راه‌اندازی سرور اعمال می‌شوند. اگر گامی شکست بخورد، گام‌های بازگشت را با شناسه commit قبلی چاپ می‌کند.

- اگر `--rehearse` شکست بخورد، سرویس هنوز نسخهٔ قبلی را اجرا می‌کند ولی کد و ساخت تازه روی دیسک مانده‌اند: پیش از هر ری‌استارت، همان دستور `git reset --hard … && npm ci … && npm run build` را که چاپ شده بی‌درنگ اجرا کنید.
- دکمه «خروجی داده‌های کسب‌وکاری» در تنظیمات (`GET /api/export-backup`، فقط admin) یک فایل JSON برای گزارش و بایگانی است و **قابل بازگردانی نیست**؛ رمزهای عبور و کلیدهای محرمانه در آن نیست. پشتیبان واقعی فقط با `scripts/backup.sh` و بازگردانی با `scripts/restore.sh`.
- **هرگز `npm run db:push` اجرا نکنید** — تغییر اسکیما فقط از مهاجرت اتمیک builtin.
- **ارتقا به v10.2.22 و بالاتر (یک‌بار، سجل ممیزی):** نخستین راه‌اندازی پس از این به‌روزرسانی نمایهٔ جست‌وجوی سجل ممیزی را می‌سازد (مهاجرت 0132): حدود یک دقیقه برای هر میلیون ردیف سجل، و در این مدت برنامه صفحهٔ انتظار نشان می‌دهد. `--rehearse` پیش از آن یک رونوشت کامل از پایگاه‌داده بازمی‌گرداند و نمایه را روی آن هم می‌سازد، پس آن گام هم به همین اندازه طول می‌کشد. پیش از به‌روزرسانی هم‌اندازهٔ جدول سجل فضای آزاد دیسک لازم است؛ اندازه را این دستور می‌گوید: `sudo -u postgres psql -d papital_erp -c "SELECT pg_size_pretty(pg_total_relation_size('activity_logs'));"` (اگر نام پایگاه‌داده را هنگام نصب عوض کرده‌اید، همان نام را بنویسید). `update.sh` تا ۶۰۰ ثانیه منتظر بالا آمدن می‌ماند؛ اگر سجل بیش از حدود ۵ میلیون ردیف دارد، زمان بیشتری بدهید: `sudo STARTUP_TIMEOUT=1800 ./update.sh --rehearse`.
- **ارتقا به v7.0.56 و بالاتر (یک‌بار، پیوست‌ها):** از این نسخه فایل پیوست‌ها روی دیسک (`public/uploads/.attachments`، داخل همان پوشه‌ای که به‌روزرسانی و پشتیبان‌گیری نگه می‌دارند) ذخیره می‌شوند و پایگاه‌داده فقط مشخصات آن‌ها را دارد. پیوست‌های قدیمی تا انتقال، مثل قبل نمایش داده می‌شوند. پس از ارتقا و یک‌بار راه‌اندازی سرور: `npm run attachments:migrate` (اجرای آزمایشی، فقط شمارش) و سپس `npm run attachments:migrate -- --apply`. در استقرار Docker همان کار با `POST /api/attachments/migrate-inline` و بدنه `{"apply": true}` توسط مدیر سیستم انجام می‌شود.
- **ارتقا به v7.0.45 و بالاتر (یک‌بار):** از این نسخه موجودی هر انبار فقط از جدول موجودی انبارها خوانده می‌شود. مهاجرت 0020 ردیف‌های جاافتاده را از موجودی نمایشی قبلی می‌سازد و موجودی نمایشی همه کالاها را از روی جدول بازسازی می‌کند؛ هر تغییر با مقدار قبل و بعد در جدول `inventory_reconciliation_anomalies` (شناسه اجرا `migration-0020`) ثبت می‌شود. کالاهایی که پیش از این نسخه با دکمه «انتقال بین انبارها» جابه‌جا شده‌اند ممکن است موجودی نادرست داشته باشند. **بلافاصله پس از ارتقا** در «بررسی سلامت و تطبیق موجودی ← تطبیق موجودی انبارها با کاردکس» گزارش را بگیرید، ترمیم را ابتدا به‌صورت آزمایشی و سپس واقعی اجرا کنید تا موجودی از روی کاردکس اصلاح شود.

## عملیات (Runbook)

### Backup روزانه

`install.sh` (فقط برای نصب تازه؛ روی سرور در حال کار اجرا نکنید) زمان‌بندی را با `scripts/install-ops-cron.sh` در یک فایل `/etc/cron.d/papital-erp` می‌نویسد: `scripts/backup.sh` هر روز ساعت ۰۲:۳۰ و `scripts/monitor.sh` هر پنج دقیقه، با گزارش در `logs/backup.log` و `logs/monitor.log`. اگر `ls /etc/cron.d/papital-erp` چنین فایلی نشان ندهد، یا پس از به‌روزرسانی به v10.2.16 (برای افزودن بررسی شبانه)، یک بار اجرا کنید؛ فایل از نو نوشته می‌شود و دوباره اجرا کردن آن چیزی را دو تا نمی‌کند. کاربر سرویس را `systemctl show -p User --value papital-erp` می‌گوید (خالی یعنی `root`). ساعتی که در دستور نیاید از همان فایل پیشین خوانده می‌شود، ولی بهتر است ساعت پشتیبان را مثل نمونهٔ زیر صریح بنویسید:

```bash
cd /opt/papital-erp
sudo BACKUP_HOUR=2 BACKUP_MINUTE=30 bash scripts/install-ops-cron.sh root   # root را با کاربر سرویس عوض کنید
```

> `scripts/ensure-env-secrets.sh` را هرگز بی نام کلید اجرا نکنید: بی نام، `ERP_WEBHOOK_SECRET_TOKEN` و `METRICS_TOKEN` را هم به `.env` می‌افزاید. روی سروری که `METRICS_TOKEN` ندارد، هشدار «وضعیت صف رویدادها خوانده نشد (METRICS_TOKEN).» از `monitor.sh` و هشدار `METRICS_TOKEN` در `go-live-verify.sh` مورد انتظارند، و `audit-env.sh` (که `METRICS_TOKEN` را بررسی نمی‌کند) نبودن `ERP_WEBHOOK_SECRET_TOKEN` را خطا (`❌ MISSING`) می‌شمارد؛ این هم مورد انتظار است و آن کلید را نیفزایید. به همین دلیل هشدار `ERP_WEBHOOK_SECRET_TOKEN missing` در `go-live-verify.sh` هم مورد انتظار است.

رونوشت رمزگذاری‌شده بیرون از سرور و کانال هشدار: `docs/OFFSITE_BACKUP.md`.

همان فایل زمان‌بندی هر شب ساعت ۰۴:۰۰ (`NIGHTLY_VERIFY_HOUR` / `NIGHTLY_VERIFY_MINUTE`؛ دست‌کم ۶۰ دقیقه پس از ساعت پشتیبان) با کاربر root `scripts/nightly-verify.sh` را اجرا می‌کند: آخرین پشتیبان روزانهٔ موفق (همان که `.last_daily_ok` نام می‌برد و اگر بیش از ۲۶ ساعت از آن گذشته باشد، شب ناموفق است) روی یک پایگاه‌داده جدا بازیابی می‌شود، بررسی سلامت مالی و ناوردایی‌های حساب و انبار روی آن اجرا و با آخرین شب سالم مقایسه می‌شود، و نتیجه در `logs/nightly-verify.json` و کارت «بررسی شبانهٔ پشتیبان» صفحه سلامت سامانه دیده می‌شود. پایگاه‌داده برنامه دست نمی‌خورد.

- پیش از بازیابی، جای خالی دیسک داده و WAL پایگاه‌داده و پوشهٔ موقت با اندازهٔ پایگاه‌داده و اندازهٔ پشتیبان سنجیده می‌شود و ۱۰٪ هر دیسک خالی می‌ماند؛ جای کم، شب ناموفق است و چیزی بازیابی نمی‌شود. پرونده‌های موقت در `BACKUP_DIR/.nightly-verify-tmp` (روی دیسک پشتیبان) نوشته می‌شوند، نه `/tmp`.
- بازیابی و بررسی با اولویت پایین (`nice` و `ionice`) و حداکثر دو ساعت (`NIGHTLY_VERIFY_TIMEOUT` به ثانیه) اجرا می‌شوند. با این حال بازیابی نزدیک ساعت ۰۴:۰۰ دیسک را پرکار می‌کند و پایگاه‌داده هنگام بازیابی چند نقطهٔ ذخیره (checkpoint) می‌نویسد؛ اگر کسی آن ساعت کار می‌کند، ساعت دیگری بگذارید.
- اگر هم‌زمان پشتیبان‌گیری، تمرین ارتقا، `update.sh` یا بازیابی در کار باشد، بررسی آن شب انجام نمی‌شود. هر رونوشت تمرینی (`erp_restore_drill_*`) که بیش از ۱۲ ساعت از ساختش گذشته باشد، شب بعد پاک می‌شود؛ رونوشتی هم که با `RESTORE_KEEP=1` یا `REHEARSAL_KEEP=1` نگه داشته‌اید از این قاعده بیرون نیست، پس اگر لازمش دارید پیش از آن کارتان را با آن تمام کنید.
- اگر پشتیبان شب تازه نباشد و همان پشتیبانی که بیش از ۱۲ ساعت پیش بررسی شده دوباره نوبت بگیرد، شب ناموفق است («پشتیبان تازه‌ای گرفته نشده»).
- این بررسی هیچ هشداری نمی‌فرستد؛ نتیجه فقط در کارت صفحه سلامت سامانه و پروندهٔ گزارش دیده می‌شود. `NIGHTLY_VERIFY_TIMEOUT` و `NIGHTLY_VERIFY_MAX_DUMP_AGE_HOURS` از `.env` هم خوانده می‌شوند.
- چیزی که بدتر شده و سه شب پشت سر هم با همان شمار بماند، خودکار وضع عادی تازه شمرده و مبنای مقایسه می‌شود و کارت این را می‌گوید. اگر بدتر شدنی را بررسی کرده‌اید و درست است، زودتر با `cd /opt/papital-erp && sudo bash scripts/nightly-verify.sh --accept-baseline` بپذیرید. بررسی تازه‌ای که در شب سالم پیشین نبود، با چیزی مقایسه نمی‌شود و تنها نام برده می‌شود.
- اجرای دوبارهٔ `install-ops-cron.sh` بدون متغیر ساعت، ساعت‌های همان فایل را نگه می‌دارد و این را چاپ می‌کند؛ ساعت پیش‌فرض فقط وقتی نوشته می‌شود که فایل پیشین آن ساعت را نداشته باشد.

انواع backup در `scripts/backup.sh`: `daily` (نگه‌داری ۳۰ روز) • `pre-deployment` (۹۰ روز — `update.sh` خودکار می‌سازد) • `pre-migration` (۱۸۰ روز)

### بازیابی از Backup

```bash
ls -lt /var/backups/erp/*.dump.gz | head -3
# V3.0.8 (TD-059): تمرین بازیابی خودکار (drill) — dump در DB موقتی ایزاده بازگردانی
# می‌شود، شمارش ردیف‌های جدول‌های حیاتی اعتبارسنجی و سپس DB موقتی drop می‌گردد:
RESTORE_MODE=drill ./scripts/restore.sh [dump-file.dump.gz]
# (برای نگه‌داشتن DB تمرین جهت بررسی دستی: RESTORE_KEEP=1)

# restore واقعی روی DB هدف (مخرب — نیازمند تأیید صریح؛ نخست سرویس را بایستانید):
sudo systemctl stop papital-erp
RESTORE_MODE=apply RESTORE_CONFIRM=yes bash scripts/restore.sh <dump>.dump.gz papital_erp
sudo systemctl start papital-erp
curl -fsS http://localhost:3000/health/ready
```

> اصل: «backup موجود است» ≠ «قابل بازیابی است». drill فوق پس از هر تغییر بزرگ schema و به‌صورت دوره‌ای (مثلاً ماهانه) باید اجرا شود.

### Rollback نسخه اپلیکیشن

`update.sh` نسخهٔ تازه را در پوشهٔ کناری `.build-next` نصب و ساخته می‌کند و `dist/` و `node_modules/` سرویس در حال کار را فقط درست پیش از راه‌اندازی دوباره جابه‌جا می‌کند؛ ساخت قبلی به نام `dist.prev/` و `node_modules.prev/` تا به‌روزرسانی بعدی می‌ماند و پیام پایان کار می‌گوید ساخت قبلی از کدام commit است.

- **جای دیسک:** پیش از پشتیبان‌گیری و هر تغییر کد، `update.sh` جای خالی دیسک را می‌سنجد: رونوشت کد، `node_modules` و `dist` تازه و یک گیگابایت حاشیه، اندازهٔ پشتیبان پیش از استقرار (اندازهٔ تازه‌ترین پشتیبان قبلی، وگرنه پوشهٔ بارگذاری‌ها و یک گیگابایت؛ اگر پشتیبان روی دیسک دیگری است آن دیسک جدا سنجیده می‌شود)، با `--rehearse` دو برابر اندازهٔ پایگاه‌داده، و در به‌روزرسانی دستی یک رونوشت دیگر از کد. اگر کم باشد بی هیچ تغییری با نام دیسک و شمار مگابایت‌ها می‌ایستد؛ پس از دریافت کد دوباره می‌سنجد. پر شدن دیسک در میانهٔ نصب یا ساخت هم با همین پیام اعلام می‌شود.
- **یک اجرا در یک زمان:** اجرای دوم هم‌زمان بی هیچ تغییری رد می‌شود (`.update.lock`).
- **اجرای دوباره بی کد تازه:** اگر `dist/` از همین کد ساخته شده باشد، ساخت و جابه‌جایی انجام نمی‌شود و `dist.prev/` (ساخت پیشین) سر جایش می‌ماند؛ `--rebuild` ساخت را از نو انجام می‌دهد.
- **جابه‌جایی نیمه‌کاره:** اگر به‌روزرسانی درست در جابه‌جایی ساخت قطع شود (قطع برق یا بسته شدن ناگهانی برنامه)، `.build-next` و نشانهٔ `.update-swapping` می‌مانند و اجرای بعدی تا ترمیم نمی‌پذیرد؛ دستور ترمیم را خود پیام چاپ می‌کند و همان خط اول نمونهٔ زیر است (دوباره اجرا کردنش زیانی ندارد). سپس سرویس را راه بیندازید و به‌روزرسانی را دوباره اجرا کنید.
- **به‌روزرسانی دستی** (`--source` / `--zip`): کد قبلی در `.previous-source/` نگه داشته می‌شود (فقط یک سطح؛ به‌روزرسانی دستی بعدی آن را جایگزین و به‌روزرسانی موفق با git پاکش می‌کند). هر فایلی در پوشهٔ برنامه که در کد تازه نیست پاک می‌شود، جز `.env`، لاگ‌ها، بارگذاری‌ها، پوشهٔ رسانه و پشتیبان‌ها؛ فهرست پاک‌شدنی‌ها پیش از همگام‌سازی چاپ می‌شود. پوشهٔ کدی که درون خود پوشهٔ برنامه باشد پذیرفته نمی‌شود.
- **نخستین ارتقا به v10.2.23:** `update.sh` پس از دریافت کد، اگر خودش عوض شده باشد نسخهٔ تازه‌اش را اجرا می‌کند؛ این از v10.2.23 به بعد کار می‌کند، پس ارتقای خودِ v10.2.23 هنوز با روش قبلی (ساخت در جای خود) انجام می‌شود. برای این ارتقا هم همان دستور همیشگی `sudo ./update.sh --rehearse` را اجرا کنید و پیش از آن `git pull` نزنید.
- **قطع اتصال SSH:** اگر پنجره در میانهٔ جابه‌جایی ساخت بسته شود یا اتصال قطع شود، جابه‌جایی و ادامهٔ کار تا پایان انجام می‌شود و گزارش در پروندهٔ `update-*.log` نوشته می‌شود. در گام‌های دیگر قطع اتصال به‌روزرسانی را می‌ایستاند؛ در این حالت همان دستور را دوباره اجرا کنید.

در شکست پیش از جابه‌جایی، ساخت در حال کار دست نخورده و فقط گام کد لازم است. `update.sh` در شکست، گام‌هایی مانند این‌ها را با شناسه commit پیش از به‌روزرسانی چاپ می‌کند. پس از یک به‌روزرسانی موفق، commit پیشین `HEAD@{1}` است (`git reflog -5` نشانش می‌دهد). پس از برگشت، تا مشکل نسخهٔ تازه رفع نشده `update.sh` را دوباره اجرا نکنید: همان commit دوباره دریافت می‌شود.

```bash
cd /opt/papital-erp
git reflog -5                           # HEAD@{1}: commit پیش از به‌روزرسانی
sudo systemctl stop papital-erp
{ [ ! -d dist.prev ] || { rm -rf dist && mv dist.prev dist; }; } && { [ ! -d node_modules.prev ] || { rm -rf node_modules && mv node_modules.prev node_modules; }; } && rm -f .update-swapping   # ساخت قبلی، بی ساخت دوباره
git reset --hard <previous-commit>      # خود شاخه برمی‌گردد؛ checkout یک commit شاخه را جدا می‌کند و git pull بعدی شکست می‌خورد
# به‌روزرسانی دستی به جای git reset:  bash scripts/update-steps.sh restore-source /opt/papital-erp
# بی dist.prev/ (مثلاً پس از دو برگشت پیاپی):  NODE_ENV=development npm ci --include=dev && npm run build
sudo systemctl start papital-erp
curl -fsS http://localhost:3000/health/ready
```

> پشتیبان پیش از استقرار را فقط وقتی بازگردانید که نسخه تازه هنوز هیچ نوشتنی نپذیرفته است؛ بازگردانی هر تغییر پس از آن را پاک می‌کند.

### چرخش Secretها

| Secret | دوره | روش |
|---|---|---|
| `JWT_SECRET` | هر ۳ ماه | `sudo sed -i "s/^JWT_SECRET=.*/JWT_SECRET=$(openssl rand -hex 48)/" .env` → restart (مقدار چاپ نمی‌شود؛ نشست‌ها باطل می‌شوند) |
| `ERP_SETUP_TOKEN` | یکبار پس از setup | `sudo sed -i "s/^ERP_SETUP_TOKEN=.*/ERP_SETUP_TOKEN=$(openssl rand -hex 24)/" .env` → restart (مقدار چاپ نمی‌شود) |
| `DATABASE_URL` password | هر ۶ ماه | `ALTER USER` در PostgreSQL → `.env` → restart |
| `wc_webhook_secret` | هر ۶ ماه | regenerate در WooCommerce + تنظیمات سامانه (بدون restart) |

پس از هر rotation: `read -rsp 'auth_token: ' ADMIN_TOKEN; echo` (مقدار کوکی `auth_token` نشست مدیر را بچسبانید؛ روی صفحه دیده نمی‌شود و در تاریخچه نمی‌ماند)، سپس `ADMIN_TOKEN="$ADMIN_TOKEN" bash scripts/smoke-test.sh http://localhost:3000; unset ADMIN_TOKEN`
