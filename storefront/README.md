# برنامهٔ فروشگاه papitalgallery.com

برنامهٔ جدای سایت فروشگاه (فاز ۸ نسخهٔ ۱۱، مرحلهٔ ۸.۳). صفحه‌ها روی سرور ساخته می‌شوند و همهٔ داده را فقط از Storefront API برنامهٔ ERP می‌خوانند (`/api/storefront/v1`). کلید API فقط روی سرور این برنامه است و به مرورگر نمی‌رسد. برنامه‌های آغاز این کار: `docs/roadmap/V11_STOREFRONT_START_PLAN.md` و `docs/roadmap/V11_STOREFRONT_8_3_PAGES_START_PLAN.md`.

## اجرا روی رایانهٔ توسعه

```bash
cd storefront
npm ci
npm run mock-api          # API نمونه با دادهٔ ساختگی mock/sample روی درگاه 3901
STOREFRONT_API_URL=http://127.0.0.1:3901/api/storefront/v1 STOREFRONT_API_KEY=preview-key npm run dev
```

- برای دادهٔ دیگر، `FIXTURE_DIR` را به پوشه‌ای بدهید که `catalog.json` و پوشهٔ `media/` دارد. `settings.json`، `brand.json`، `seo.json` و `redirects.json` (مرحلهٔ ۸.۵) و `campaigns.json` (مرحلهٔ ۸.۵ب؛ `MOCK_CAMPAIGNS=0` برای هیچ) اختیاری‌اند.
- دادهٔ واقعی و عکس‌ها هرگز در این مخزن عمومی گذاشته نمی‌شوند.

## متغیرهای محیط

| نام | کار |
|---|---|
| `STOREFRONT_API_URL` | نشانی Storefront API برنامهٔ ERP |
| `STOREFRONT_API_KEY` | کلیدی که در ERP، در «فروشگاه سایت» → «کلید برنامه سایت» ساخته می‌شود |
| `STOREFRONT_SITE_URL` | نشانی عمومی سایت، برای پیوندهای canonical و کارت شبکه‌های اجتماعی؛ میزبان همین نشانی تنها جایی است که فرم‌های سایت از آن پذیرفته می‌شوند |
| `STOREFRONT_TRUST_PROXY` | با `1` نشانی بازدیدکننده از سرآیندهای وب‌سرورِ جلو (`X-Real-IP`، `X-Forwarded-For`) خوانده می‌شود؛ فقط وقتی بگذارید که آن وب‌سرور این سرآیندها را خودش بازنویسد |
| `STOREFRONT_PORT`، `STOREFRONT_HOST` | جایی که `npm start` گوش می‌دهد (پیش‌فرض: `127.0.0.1:3100`) |
| `STOREFRONT_PREVIEW_NOTICE` | نوار بالای صفحه، فقط در پیش‌نمایش |
| `STOREFRONT_NOINDEX` | با `1` موتورهای جست‌وجو هیچ صفحه‌ای را نمایه نمی‌کنند، مثلاً روی نشانی آزمایشی. بی `STOREFRONT_SITE_URL` یا با نوار پیش‌نمایش هم همین‌طور است. |
| `STOREFRONT_PWA` | با `1` سایت روی گوشی نصب‌شدنی می‌شود (manifest، آیکون‌ها و سرویس‌ورکر). سرویس‌ورکر هیچ صفحه، قیمت یا موجودی‌ای را نگه نمی‌دارد و فقط فایل‌های ساخت، فونت‌ها، آیکون‌ها و عکس‌های محصول را نگه می‌دارد. با خاموش کردن، در بازدید بعدی از گوشی‌ها پاک می‌شود. پیش‌فرض: خاموش. |

## نشانی‌های سایت قبلی و آمار بازدید (مرحلهٔ ۸.۵)
- درخواستی که به هیچ صفحه‌ای نمی‌خورد در فهرست «نشانی‌های سایت قبلی» ERP جست‌وجو می‌شود و با 301 به صفحهٔ تازه می‌رود؛ نشانیِ به شکل ووکامرس که در فهرست نیست با 302 به جست‌وجو یا فهرست محصولات می‌رود.
- کد تأیید گوگل و بینگ و سرویس آمار بازدید از تنظیمات «جست‌وجو و آمار بازدید» ERP می‌آیند. آمار فقط وقتی بار می‌شود که سایت قابل نمایه شدن باشد (نشانی عمومی تنظیم شده، پیش‌نمایش نیست و `STOREFRONT_NOINDEX` روشن نیست). سیاست امنیتی هر صفحه در `app/entry.server.tsx` نوشته می‌شود و فقط نشانی‌های همان سرویس را می‌افزاید.

## فید محصولات و صفحه‌های ویژه (مرحلهٔ ۸.۵ب)
- `/feeds/google.xml` همهٔ محصولات روی سایت را که عکس دارند به قالب فید گوگل می‌دهد (ده دقیقه نگه داشته می‌شود). روی پیش‌نمایش 404 است. صفحهٔ هر محصول برچسب‌های ترب (`product_price` به تومان) و فیلدهای محصول Open Graph را دارد.
- `/campaigns/<نشانی>` یک «صفحهٔ ویژه» است که در ERP نوشته می‌شود؛ فقط تا روشن و میان دو روزش است پاسخ می‌دهد. `/<نشانی>` (مثل `/yalda`) با 302 به آن می‌رود. صفحه‌ای که «بالای صفحهٔ اصلی» خواسته جای سرصفحهٔ صفحهٔ اصلی را می‌گیرد. فهرست صفحه‌ها یک دقیقه نگه داشته می‌شود و خطای آن صفحهٔ اصلی را نمی‌خواباند.

## بار روی ERP
همهٔ بازدیدکننده‌ها از راه همین برنامه به ERP می‌رسند، پس سقف درخواست Storefront API (۱۲۰۰ در دقیقه برای هر نشانی) میان همهٔ آن‌ها مشترک است. برای همین برنامه عکس محصولات را پس از اولین خواندن در حافظه نگه می‌دارد (تا ۹۶ مگابایت؛ نام هر عکس هش محتوای آن است و کهنه نمی‌شود)، پاسخ کاتالوگ را چند ثانیه نگه می‌دارد و نشانیِ ناموجود را یک دقیقه به خاطر می‌سپارد. در راه‌اندازی روی سرور (مرحلهٔ ۸.۶) nginx هم `/media` و `/assets` را نگه می‌دارد و درخواست صفحه‌های هر نشانی بازدیدکننده را محدود می‌کند.

از v12 (فاز ۷، بند ۱.۴ بررسی مستقل) جست‌وجو برای هر بازدیدکننده ۳۰ بار در دقیقه است (`app/lib/visitorLimit.server.ts`)؛ بیش از آن همان بازدیدکننده صفحهٔ «جست‌وجوی زیادی در یک دقیقه» (۴۲۹) را می‌بیند و دیگران هیچ اثری نمی‌بینند. جست‌وجویی که از حافظه پاسخ داده نشود نشانی بازدیدکننده را با `X-Storefront-Client-IP` به ERP می‌دهد و ERP هم برای هر بازدیدکننده ۱۲۰ خواندن کاتالوگ در دقیقه می‌پذیرد. خود ERP فهرست کالاهای روی سایت را ۵ ثانیه در حافظه نگه می‌دارد. سقف هر بازدیدکننده فقط با `STOREFRONT_TRUST_PROXY=1` کار می‌کند؛ بی آن نشانی بازدیدکننده دانسته نیست و فقط سقف مشترک ERP می‌ماند.

## حساب خریدار و نشانی بازدیدکننده (مرحلهٔ ۸.۴ب)
صفحه‌های `/account/sign-in`، `/account/sign-up`، `/account/set-password` و `/account/sign-out` همه فرم ساده‌اند و بی جاوااسکریپت هم کار می‌کنند؛ فقط صفحهٔ تعیین رمز کلید پیوند را از بخش پس از `#` می‌خواند. نشست خریدار در کوکی `sf_session` است (httpOnly، `SameSite=Lax`، و روی سایت https با `Secure`).

برای هر درخواست حساب، این برنامه نشانی خود بازدیدکننده را با سرآیند `X-Storefront-Client-IP` به ERP می‌دهد تا سقف‌های کد پیامکی و ورود برای هر خریدار جدا شمرده شوند. این نشانی از سرآیند `X-Real-IP` وب‌سرورِ جلوی برنامه خوانده می‌شود، و اگر نبود از آخرین بخش `X-Forwarded-For`. این سرآیندها فقط با `STOREFRONT_TRUST_PROXY=1` خوانده می‌شوند. پس وب‌سرور در راه‌اندازی (مرحلهٔ ۸.۶) باید `X-Real-IP` را خودش بازنویسد (مانند `proxy_set_header X-Real-IP $remote_addr;`) و `STOREFRONT_TRUST_PROXY=1` گذاشته شود؛ اگر وب‌سرور سرآیند را بازننویسد، هر مرورگری می‌تواند نشانی دلخواه بنویسد و سقف‌ها را دور بزند، و بی این متغیر همهٔ خریداران یک سقف مشترک دارند.

فرم‌های حساب فقط از خود سایت پذیرفته می‌شوند: React Router پستی را که `Origin` آن با سایت نخواند رد می‌کند (۴۰۰)، و این برنامه پستی را که مرورگر با `Sec-Fetch-Site` از سایت دیگری بداند (۴۰۳). چون وب‌سرور https را خودش تمام می‌کند و با http به این برنامه می‌رسد، `server.mjs` میزبان `STOREFRONT_SITE_URL` را مبدأ مجاز فرم‌ها می‌گذارد؛ پس وب‌سرور باید سرآیند `Host` را همان‌طور که هست بفرستد (`proxy_set_header Host $host;`).

## سبد، تسویه و سفارش (مرحلهٔ ۸.۲)
تا «ثبت سفارش» در ERP روشن نباشد (فیلد `ordering` تنظیمات سایت) هیچ‌کدام از این‌ها دیده نمی‌شود. برای دیدن آن‌ها با API نمونه: `MOCK_ORDERING=1 npm run mock-api`.

- `/cart`: سبد در کوکی `sf_cart` (httpOnly) است و فقط نام محصول و تعداد را دارد؛ قیمت را ERP هنگام هزینهٔ ارسال و ثبت سفارش دوباره حساب می‌کند.
- `/checkout`: یک فرم برای گوشی؛ نخست روش‌ها و هزینهٔ ارسال برای همین سبد و استان، سپس ثبت سفارش. کلید درخواست یک بار در هر تسویه ساخته می‌شود تا ضربهٔ دوباره سفارش دوم نسازد.
  کد تخفیف (۸.۲ج) هم در همین فرم است: با هزینهٔ ارسال سنجیده می‌شود و کدی که نمی‌نشیند زیر فیلدش گفته می‌شود. API نمونه فقط کد `YALDA` (۱۰٪) را می‌پذیرد.
- `/corporate-gift`: فرم «هدیهٔ سازمانی» (۸.۲ج)؛ در ERP یک پرونده فروش در CRM می‌سازد. بودجه به تومان نوشته و به ریال فرستاده می‌شود.
- `/orders/:number`: وضعیت، جای پرداخت و فرم رسید کارت‌به‌کارت (عکس رسید پیش از فرستادن روی گوشی کوچک می‌شود). کلید پیگیری سفارش در کوکی `sf_orders` (httpOnly، فقط زیر `/orders`) می‌ماند و هرگز در نشانی نمی‌آید؛ از گوشی دیگر با `/orders/track` و شماره و کلید باز می‌شود.
- `/account`: حساب خریدار، گروه خرید و سفارش‌های حساب. سفارش حساب از هر گوشی‌ای که وارد حساب است رسید می‌گیرد.
- همهٔ این صفحه‌ها فرم ساده‌اند و بی جاوااسکریپت هم کار می‌کنند.
- فرم رسید عکس می‌گیرد؛ این برنامه پستی را که `Content-Length` آن از سقف عکس (۳ مگابایت) و کمی بیشتر بگذرد نمی‌خواند. در راه‌اندازی (۸.۶) وب‌سرور جلو هم باید سقف بدنه بگذارد (مانند `client_max_body_size 5m;`) تا پست بی `Content-Length` هم بزرگ‌تر از این نشود.

## راه‌اندازی روی سرور (مرحلهٔ ۸.۶)
سایت سرویس دومی کنار ERP است، با اسکریپت‌های `deploy/storefront/`: `storefront.sh` (نصب، به‌روزرسانی با برگشت خودکار، برگشت دستی، وضعیت و ساخت بسته برای سروری بی مخزن و npm، مثلاً در ایران) و `storefront-nginx.sh` (دامنه، https، `www.` و http به نشانی اصلی، کش عکس‌ها، سقف بدنه و سقف درخواست). قاعده‌های بالا (`Host` دست‌نخورده، `X-Real-IP` بازنویسی‌شده، سقف ۵ مگابایت) در سایت nginx همان اسکریپت نوشته شده‌اند. راهنمای قدم‌به‌قدم، سوئیچ از ووکامرس و برگشت: `deploy/storefront/RUNBOOK_FA.md`؛ چک‌لیست: `deploy/storefront/GO_LIVE_CHECKLIST_FA.md`.
